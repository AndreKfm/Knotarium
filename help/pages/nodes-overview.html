How to read this reference

Every node in the reference is documented the same way: what it does, its parameters with types, and its output ports. This page explains what those columns mean — where a node's identity comes from, why the palette group rarely matches the category in the catalog, which fields accept expressions, and why a property form is blank even when the code behind it has a sensible default. Read it once; the six pages that follow assume it.

Where a node's facts come from

A node is described by a manifest: a small record holding its id, display name, category, parameters, output ports, capability tags, timeout and retry policy. The built-in manifests are registered in code when the application starts. The property form, the palette entry, the ports drawn on the canvas and the compiler's socket validation are all generated from that one record, which is why an entry in this reference can be trusted to match what you see on screen.

What the manifest does not describe is behaviour. The value a node emits, the shape of its payload and every fallback it applies to a missing parameter live in the executor — a separate piece of code. Where the two differ, this reference documents the executor, because that is what actually runs.

Display name and internal id

Each entry's heading is the display name — what the palette, the canvas and the properties panel call it. Immediately after it, in monospace, is the internal id: the string stored in the workflow file, quoted in compiler diagnostics and journal entries, and used by the REST API. They frequently disagree, and the id is the one that matters when you are reading an error message. Cron Scheduler is stored as scheduler; Email Send (SMTP) is smtpSend; Parallel For-Each is parallelForEach.

Ids are matched case-insensitively throughout the engine, but they are written in the workflow exactly as the palette produced them. Renaming a node on the canvas changes only its label; the id of the node type never changes, and the per-node instance id (httpRequest-3 and the like) is what expressions reference.

Palette category

The category in the manifest is not the group you see in the sidebar. The palette normalises nine manifest categories down to six sections, and the collapsing is lossy: Utility, Scripting, Annotations, External and anything it does not recognise all land in a single Utility section. This is why Inline Code — category Scripting in the catalog — appears under Utility in the palette.

Three nodes are registered and fully executable but never offered in the palette. Sticky Note and Group are editor-only annotations inserted from the canvas toolbar instead. Manual Trigger is hidden because it is redundant with Start — both are manual-run entry points — so new workflows get one obvious choice. An existing workflow that already contains a Manual Trigger still loads, renders and runs; only the palette stopped offering it.

Palette search matches the display name, the one-line description and the palette section. It deliberately does not match the internal id, so searching for x no longer surfaces External Device through the x in externalDevice. If you know the id and not the name, use this reference rather than the search box.

A manifest can also mark a node secondary, which routes it out of its normal section into a collapsed Advanced panel at the bottom of the palette. No built-in node sets that flag today, so the Advanced panel appears only when a custom or imported package uses it.

Parameters

A parameter is configuration you fill in on the node; it is not the same thing as data arriving over a wire. Every parameter carries a name, a type, and a required flag. The Required column in this reference reflects the manifest's own flag — the publish gate uses it to refuse a workflow with an unconfigured required field, so a missing required value fails at publish time rather than mid-run.

Some parameters never appear in the form even though they exist in the manifest. A parameter named end is always hidden, because it is the loop-back input port of a container node and is wired with an edge rather than typed in. On a node with a mode parameter the form shows only the fields that mode uses, so switching For Loop from count to foreach swaps count for collection instead of showing both.

Which parameters accept expressions

Each parameter carries an expression flag, listed in the Expr column of every parameter table. When it is set, the engine resolves {{ }} placeholders in the value before handing it to the node: 

# an upstream node's output
{{ $node.httpRequest-1.output.body }}

# a workflow variable, including a nested path
{{ $variables.customer.email }}
{{ $variables.rows[0].id }}

When the flag is clear, the raw value is handed over untouched. That is not an oversight — it is load-bearing. Inline Code's code parameter must not be rewritten, or a {{ }} sequence inside a C# string literal would be mangled before the compiler ever saw it. Condition's logic is handed over unresolved so the node can resolve each operand itself and tell a genuinely missing reference apart from one that resolved to null. The practical consequence is simple: typing {{ ... }} into a field whose Expr column is empty stores those characters literally, and the node will use them as text.

Manifest parameters carry no default values

The manifest record has no field for a default. The property form asks for one, finds nothing, and falls back to an empty string — so every field starts blank, including the ones the executor has a perfectly good default for. Delay does not show 0, Parallel For-Each does not show 8, HTTP Request does not pre-select GET.

A blank field is therefore not the same as a field set to the default — it is a field that is absent, and absence is exactly what makes the executor apply its own fallback. The defaults are documented in the prose of each node entry rather than in the parameter tables, because putting them in a "Default" column would imply the form shows them.

Output ports

Ports are the sockets on the right edge of a node card. The manifest declares them, the canvas draws one handle per declared port, and the compiler checks that every edge names a port that exists. Three shapes occur.

A single result port is the common case: the node did its work and the run continues. Branch ports mean the node chooses one wire. Condition emits on true or false; HTTP Request on success or error; container nodes on start for each pass through the body and success once the loop is done. Only the chosen port's edges are followed, so a branch node with nothing wired to the port it selected simply ends that path.

Dynamic ports are the exception. Two nodes declare no outputs at all, which makes the compiler skip socket validation for them, and the editor derives the handles from the node's own properties instead. AI Router splits its categories value on commas, semicolons and newlines, trims each label, drops empties, de-duplicates case-insensitively keeping the first spelling, and draws one port per surviving label plus a permanent otherwise fallback. External Device draws one source pin per selected event (evt:<type>) and per selected incoming action (act:<type>); it is a purely inbound surface and has no input pins.

Because dynamic ports are derived from configuration, editing that configuration changes the node's shape. Removing a category label or unticking a device pin drops the corresponding port, and any edge attached to it is pruned. There is no warning — the wire is simply gone the next time the graph loads.

Capabilities and what "privileged" means

A manifest lists the privileged resources its node touches as capability tags. Five of them are classed as privileged, meaning a workflow containing such a node can reach past ordinary data flow and touch the host itself. That classification is what drives the warning shown before you install an imported template or bundle, and before you accept an AI-generated graph.

TagPrivilegedEnforcement
filesystem.read Privileged Checked against the file access policy on every call. Deny-all until directories are permitted.
filesystem.write Privileged Same policy, separate permission.
code.execute Privileged Gated by the instance capability switch, off until an administrator enables it.
database Privileged Same switch.
aiAgent Privileged Same switch. The agent loop can invoke other workflows as tools, so it is treated like code execution.
network Descriptive Not switchable. Outbound requests are governed by the egress policy instead.
credentials Descriptive Not switchable. Marks a node that resolves stored secrets.

The capability switch is secure by default: an instance with nothing enabled denies code execution, database access and the agent loop outright. A node whose capability is denied fails when it runs, not when you publish, so a workflow that passes validation on your machine can still fail on a locked-down instance. The vocabulary is an open list of plain strings, shared with binary and custom node packages, so a third-party package may declare a tag not listed here.

Credentials

Any parameter typed credentialRef stores nothing but the id of a credential saved under Settings › Credentials. The secret is decrypted and injected at run time. This is why exporting a workflow never leaks a password, and equally why importing one onto a different instance leaves the credential reference dangling until you point it at a local credential.

Timeouts

Every manifest carries a default timeout in seconds, listed in each node entry. The engine starts from that value and applies two adjustments:

  • A timeoutSeconds (or timeout) property on the node overrides it, clamped to between 1 and 3600 seconds.
  • A manifest timeout of 0 means "not specified"; a node that actually executes then gets a 5-second timeout. Most nodes declaring 0 are triggers, which never execute a task at all, so the fallback rarely bites.

Delay is special-cased: its timeout is raised to the configured wait plus two seconds, so a long deliberate pause can never trip a limit that exists to catch a hung node. Inside a Parallel For-Each body the rules differ — each body node's manifest timeout is clamped to between 1 and 600 seconds, and a body node whose manifest declares 0 gets 30 seconds rather than 5.

Retry behaviour

A node is retried automatically only when both manifest flags allow it: its recovery mode must be "retry automatically" and its side effect must be idempotent. Declaring only the first is not enough, and that combination is easy to misread. HTTP Request asks for automatic retry but is marked as having a non-idempotent side effect, so a failed HTTP Request is never retried by the engine — a POST that may have already been delivered must not be replayed on the run's behalf. The same applies to Database Query, Email Send and MQTT Publish.

The nodes that genuinely retry are File Read, Email Fetch (IMAP), Resource Picker, AI Prompt, AI Router, AI Verify and AI Semantic Diff. Everything else fails immediately and hands control to the workflow's own error path.

No built-in node declares a custom retry policy, so all of them use the same defaults: at most 3 attempts, a 2-second initial delay, doubling each time, with random jitter of up to ±15% and a 30-second ceiling on any single delay. While waiting, the run is parked rather than blocking a worker.

Imported operations are nodes too

Importing an OpenAPI specification generates node types of its own, one per operation. They are not part of the catalog above and are not documented node by node here — their parameters come from the specification. They behave like any other node otherwise: same port rules, same timeout handling, same expression flags.

Trigger nodes
How a run starts: schedules, webhooks, polling and the global error handler.
Logic nodes
Branching, waiting, looping in sequence or in parallel, and calling another workflow.
Data nodes
Extracting a value from JSON, combining arrays, and picking a live resource.
