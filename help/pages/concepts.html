Core concepts

This page names the moving parts and explains how they relate. It is the page the rest of the manual leans on: once you know what a version is, what arms a trigger, and how one node reads another's output, most of the interface stops needing explanation. Read it after you have run something once — the vocabulary lands better with a run behind you.

Workflows, nodes and edges

A workflow is a directed graph. In code it is a WorkflowDefinition: an identifier, a name, a list of nodes, a list of edges, and a little metadata. Two booleans ride along — whether it is enabled, and whether it has been archived — and both are covered below.

A node is one step. Structurally it is almost nothing: an identifier, a type string naming which node package it is, and an untyped bag of properties. Everything you configure in the property inspector lands in that bag.

Position is a property, not a field

A node's place on the canvas is not part of the graph model. Coordinates, size and group membership live inside the same property bag under a reserved _metadata key. This is why moving nodes around counts as an edit to the workflow, and why a graph exported and re-imported keeps its layout.

An edge connects a specific output of one node to a specific input of another. It carries four pieces of information: the node it leaves, the output port it leaves from, the node it arrives at, and the input port it arrives at. When the editor does not name them explicitly, the output defaults to result and the input defaults to in.

Ports

Ports are where the model earns its keep. A node package declares its outputs, optionally with a type, and the editor draws one handle per declared output. Most nodes declare a single output called result and behave like a straight line. The interesting ones do not.

NodeOutput ports
Conditiontrue, false
HTTP Requestsuccess (object), error (string)

Switch and AI Router are the two whose ports are not fixed: they are derived from configuration, which is why adding a category to the router immediately grows a new handle on the node.

Fan-in is restricted on purpose. Most input ports accept exactly one incoming edge — wiring a second one replaces the first rather than merging. The exceptions are the End node and the Join node, which are the two places where several branches are meant to converge.

Expressions

Nodes pass data to each other through expressions written in double braces. There is no general scripting language here — the evaluator is a small hand-written parser with a fixed grammar, which is deliberate: expressions are configuration, and configuration that can do anything is a security problem.

The two reference forms

There are exactly two rooted references. Everything else is a literal, an operator or one of four functions. 

# Read an earlier node's output
{{ $node.<node-id>.output.<field> }}

# Read a variable
{{ $variables.<name> }}

The field part is a path, not just a name. It walks into nested objects with dots, indexes arrays with brackets, and accepts quoted keys when a key contains something awkward: 

{{ $node.fetch-user.output.success }}
{{ $node.fetch-user.output.payload.user.name }}
{{ $node.fetch-user.output.payload.user.roles[0] }}
{{ $node.n1.output.result["a key with spaces"] }}
Why node identifiers may contain hyphens

The tokenizer treats a hyphen as a delimiter almost everywhere, which would normally break an identifier like fetch-user. The $node. form is scanned specially: everything between $node. and the literal .output. is taken as the identifier, whatever it contains. That is also why the .output. segment is not optional — an expression without it resolves to nothing.

A bare name with no prefix is treated as a variable lookup, so {{ myValue }} and {{ $variables.myValue }} reach the same place. The prefixed form is clearer and worth preferring.

There is no $json, $run, $env or $trigger

Only $node and $variables exist. Names borrowed from other automation tools do not resolve — and because a miss returns nothing rather than raising an error, a mistyped root produces an empty value quietly instead of a failed node. When a field is unexpectedly blank, check the root name first.

What the grammar supports

Comparison with == and !=, arithmetic with +, -, * and /, boolean && and ||, parentheses, and string, number, boolean and null literals. The + operator concatenates when either side is a string. Division by zero yields zero rather than failing.

Four functions are allowed, and the names are matched case-insensitively:

FunctionReturns
now()The current UTC time in round-trip format.
uuid()A fresh identifier.
coalesce(a, b, …)The first argument that is neither null nor an empty string.
length(x)String length, array length, or a collection count; zero otherwise.

Anything else is refused outright with a message saying the function is not in the allowed set. This is a real error that fails the node, unlike a missing reference. Note also that while ! is recognised as a character, there is no negation operator in the grammar — write x == false rather than !x.

Typed values versus interpolation

This distinction matters more than it looks. When a field contains nothing but a single expression, the result keeps its type — a number stays a number, an object stays an object. When the expression is mixed with any surrounding text, every value is converted to a string and concatenated. 

# Passes a real number through
{{ $node.calc.output.result }}

# Passes the string "Total: 42"
Total: {{ $node.calc.output.result }}

A downstream node expecting a number and receiving "42" is a common and confusing failure. If a value must stay typed, the field must contain only the expression.

Some fields never evaluate expressions

A node package can declare a parameter as non-expression, and the engine then hands that value to the node untouched. The Inline Code node's code field and the Condition node's logic are the important cases: rewriting {{ }} inside a C# source file would corrupt it, so the node resolves its own references instead.

Variables

A variable is a named value living in a bag attached to one run. The Set Variable node writes to it; expressions and nodes read from it.

Variables do not survive the run that created them

There is no workflow-level or instance-level variable store. The bag is created when a run starts and is discarded with it. A workflow that needs to remember something between runs must write it somewhere real — a file, a database, an external service. This surprises people coming from tools with persistent workflow state.

Reads resolve in three steps: a direct key in the bag, then a dotted path into a structured value already in the bag, then the promoted-output convention, where a name of the form nodeId_outputName resolves to that node's recorded output. The third step is what makes the editor's "promote this output to a variable" gesture work without copying data.

Writes accept paths as well as flat names, so a node can set user.address.city or items[0] and the engine builds the intermediate structure, leaving neighbouring keys intact. A write whose path conflicts with the existing shape fails the node with a message naming the variable.

The engine also snapshots the whole variable bag immediately before each node runs, and stores that snapshot on the node's recorded state. That snapshot is what the time-travel inspector shows you under Variables at this step, and it is why inspecting an old run does not require replaying it.

Secrets are not variables

Passwords, tokens and API keys live in a separate credential store, encrypted at rest. A node does not receive a secret through a variable; it holds a reference, and the engine resolves the reference at the moment of use. This is what makes a workflow safe to export: the exported file names the credential slot it needs, never the secret itself.

Triggers

A trigger is the entry point of a run. Six node types are marked trigger-only, meaning they can start a graph but cannot sit in the middle of one.

NodeStarts a run when
StartSomeone runs the workflow manually.
Manual TriggerThe same thing. It duplicates Start and is hidden from the palette.
Cron SchedulerA cron expression matches in the configured time zone.
Webhook TriggerAn inbound HTTP call arrives.
Polling TriggerA watched source reports a change.
Error TriggerAny other workflow fails. This is the entry point of a global error handler.

Every run records where it came from as a trigger origin — manual, schedule, webhook, poll, error and a few more for replays and agent invocations. The origin is not merely a label: when a run starts, the engine picks the trigger node matching that origin as the entry point. A graph with both a Start node and a Cron Scheduler therefore begins in different places depending on how it was started.

Inbound device and external-system signals are a seventh surface, but they work differently: they are dynamic pins on an External Device node rather than a trigger-only node of their own.

End is not a trigger, despite the category

The End node is filed under the same category as the triggers in the node catalog, which is confusing. It is an ordinary node with no outputs at all. It matters most inside a sub-flow, where the compiler requires both a Start and an End node to know where the boundary is.

Runs and journaling

One execution of a workflow is a run. It records which workflow and which version it used, when it started, what started it, its variable bag, and a status.

StatusMeaning
PendingQueued, not started.
RunningIn progress.
SuspendedPaused awaiting something external.
WaitingForRetryA node failed and will be retried.
CompletedFinished successfully. The timeline labels this Success.
FailedFinished unsuccessfully.
CancelledStopped deliberately, including by disabling the workflow.
DiscardedA failed run triaged away in the dead-letter view and no longer treated as actionable.

Each node in the run gets its own recorded state: a status, the inputs it received, the outputs it produced, an error message if it failed, how many times it executed, and the variable snapshot described above.

Alongside that, the engine writes a journal — an ordered stream of events with types such as WorkflowStarted, NodeExecutionStarted, NodeExecutionCompleted, NodeExecutionFailed, VariableUpdated and WorkflowCompleted. The journal is the timeline; the per-node state is the detail.

Where the inspector gets its data

Stepping through a finished run is not a re-execution. The inspector reads the persisted node states and journal groups and scrubs across them. That is why it works on a run from weeks ago, why it costs nothing to open, and why it cannot show you anything the engine did not record at the time.

Replay is a new run

Replaying picks a node as a cut point. The engine creates a brand-new run that inherits the recorded state of everything upstream of that node and re-executes the cut point and everything downstream of it. The original run is never modified — it stays as evidence, and the two are linked so you can navigate between them.

Because downstream nodes really do run again, replay warns you about any of them that perform a non-idempotent side effect. Sending an email twice is a decision, not an accident, so the engine makes you take it knowingly.

Drafts, versions and activation

This is the concept people most often get wrong, and it has three states, not two.

The draft is what the canvas edits. It is stored as an indented JSON file on disk rather than in the database — deliberately, so that drafts are readable and can be kept under version control alongside other configuration.

Publishing compiles the draft and, if it compiles cleanly, freezes it as a numbered, immutable version in the database. If compilation fails, nothing is written at all and you get the diagnostics instead.

Publishing an unchanged graph does not create a version

Before creating a version the engine compares the serialised nodes and edges against the latest existing version. If they are identical it reuses that version. Version numbers are therefore a count of meaningful changes, not a count of times you pressed the button, and the history stays readable.

Activating points the workflow at one particular version. There is no active-version column on the workflow; the pointer is a separate record carrying a concurrency token that rotates on every activation, so two people activating different versions at the same moment produce a conflict rather than a silently lost update. Every activation is also appended to a permanent log, which is what lets the system answer which version was live at a given moment.

In practice publishing and activating are one act: publishing auto-activates the version it just created. Activation becomes a separate operation when you roll back — you activate an older version without touching your draft.

The draft never executes

This is the part that trips people up, and it is worth stating flatly: every run executes the active version — a manual click included. There is no execution path that reads the graph you are currently editing. The endpoint that starts a run rebuilds the workflow from the active version's nodes and edges, and refuses outright when no version is active.

Pressing Run in the editor therefore does two things in order: it activates the version chosen in the toolbar's runtime-version picker, and only then starts a run. The button's tooltip says so — Activate the selected version and run it. On a workflow that has never been published there is nothing to activate, so the button is disabled and its tooltip reads Publish a version (Save & Publish) before running. instead.

Pressing Run changes what your schedules execute

Because Run activates first, a manual test is not a private act. If the picker is on version 7 while version 5 was active, pressing Run makes version 7 active for everything — the next scheduled fire, the next webhook, every trigger on that workflow. Testing a newly published version and rolling production forward are the same gesture. Check the picker before you press it.

What genuinely differs between a manual run and an automatic one is much narrower than the version. A node can carry a pinned output — a design-time stub that makes the node emit a fixed payload instead of executing, so you can build downstream steps without re-running expensive upstream ones. Pins are honoured only when the trigger origin is manual. A scheduled, webhook or polled run ignores them completely, which is what stops a forgotten pin from shipping to production.

Where versions come from

OriginCreated by
PublishedPublishing the current draft.
RestoredRestoring an earlier version, which copies it forward as a new version rather than reviving the old one.
ImportedImporting an external definition. Imported versions arrive inactive.

Restoring never mutates history. Version 3 restored from version 1 becomes version 4, and versions 1 through 3 remain exactly as they were. Deleting a workflow is likewise a soft delete: archiving removes the editable draft but keeps the version history and the activation log intact, because the ability to explain a past run outlives the workflow itself.

Enabled, and armed

Two independent switches decide whether anything happens on its own. Both must be on, and they fail in the same silent way when they are not.

Enabled — per workflow

The enabled flag gates automatic and external starts for one workflow: schedules, polling triggers, inbound webhook and external calls, and an AI Agent's ability to invoke it as a tool. Manual runs are not gated by it. That exemption is about being allowed to start, not about what gets executed — a manual run on a disabled workflow still runs the active published version, exactly like every other run.

Disabling is more forceful than it sounds. As well as stopping new runs, it cancels runs already in flight — every pending, running, suspended or retry-waiting execution is set to cancelled and their queued work is dropped. The currently executing node finishes; nothing further is scheduled.

Armed — per instance

Arming is a single global switch separating design time from run time. While disarmed, schedule evaluation and polling are skipped entirely, inbound device signals are dropped, and externally triggered runs are refused. Manual runs always execute.

A fresh install starts disarmed. Once an instance has run, the stored state wins over configuration.

The disk guard disarms and never re-arms

A background check samples free disk space. When it drops below the configured floor and the runtime is armed, the runtime disarms itself and logs a critical message. Freeing space does not bring it back — re-arming is a deliberate operator action, on purpose, so that a machine that filled up once does not silently resume half-finished work. Backup restore has the mirror-image rule: it refuses to run while armed.

Capabilities and the security posture

A node package declares the privileged things it touches as capability tags — reading files, writing files, executing code, querying a database, making network calls, resolving credentials, running an agent loop. Declaring a tag is metadata. Only some of them are enforced, and the distinction matters.

CapabilityEnforced howDefault
code.executeInstance-wide toggleOff
databaseInstance-wide toggleOff
aiAgentInstance-wide toggleOff
filesystem.readPer-directory file access policyDenied
filesystem.writePer-directory file access policyDenied
networkNot gated by this system — see below—
credentialsNot gated by this system—

Exactly three capabilities are switchable, from Settings › Capabilities. The stored policy is a list of what is enabled, so an absent, empty or unparseable policy means everything is off. That is a deliberate fail-closed design: corruption of the setting cannot accidentally grant code execution.

Filesystem access is excluded from those toggles because it has something better — a policy of specific directory grants, each marked readable, writable or both, with an optional free-space reserve on writes. The default policy grants nothing at all.

Declaring a capability is not the same as being gated by one

The network and credentials tags are descriptive: no capability check consults them. Outbound requests are policed by a separate egress layer instead, which validates the address, re-checks after DNS resolution, and pins the connection so a hostname cannot be rebound to an internal address mid-request. That is a stronger control than a toggle, but it is a different mechanism — do not expect the capabilities screen to govern it.

Five tags are classed as privileged: both filesystem tags, code execution, database and the agent loop. When you import a template or a bundle containing a node that declares any of them, the importer surfaces the fact and asks you to acknowledge it before installing. The reasoning is that an imported graph is somebody else's code, and code execution is the shortest path from "I installed a template" to "someone else runs commands on my machine".

Sub-flows

A sub-flow lets one workflow be used as a step inside another. The calling graph contains a Subflow node naming the workflow to include.

Sub-flows are inlined, not called

Despite the vocabulary, there is no runtime call and no child run. At compile time the referenced graph is spliced into the parent, producing one flat execution plan. There is one run, one timeline, and one set of node states covering both graphs. Recursion is not a stack overflow at runtime — it is a compile error.

Inlining renames the child's nodes with a prefix so that including the same sub-flow twice produces two independent copies rather than a collision. Edges into the Subflow node are rewired to the child's Start node, and edges out of it are re-sourced from the child's End node — which is why a sub-flow must contain both.

Data crosses the boundary through two explicit maps configured on the Subflow node. Inputs pair a child variable name with an expression evaluated in the caller's scope. Outputs pair a child variable name with a caller variable name to write it back to. Those maps are the only bridge: the child's variables are namespaced to its instance, so nothing leaks in either direction by accident.

The maps are name-and-expression pairs rather than a typed signature. Nothing checks that the value you pass matches what the child expects, so a rename inside the sub-flow silently breaks its callers. Treat the input and output names as an interface and change them deliberately.

Templates and bundles

Both are ways of moving work between instances, and they differ in scope.

A template is a single workflow with metadata, packaged as a zip with a .kgtpl extension containing exactly two entries: a manifest and the workflow document. It is a secret-free projection — credentials it needs are declared as named slots that the installer asks you to bind to real credentials on your instance. A template can also declare parameters, substituted into the graph at install time.

A bundle is bigger: several workflows plus the node packages they depend on, with a .kgbundle extension. It carries two files that mirror the split familiar from package managers — a manifest describing intent, and a lock file generated at export recording exactly which package versions were resolved and their hashes. The installer verifies against the lock.

The rule the trust model exists to enforce is that a package claiming a remote or official origin without a signature that verifies against a trusted key must not be trusted. Unknown values fail closed to untrusted rather than being treated optimistically. Templates carry no signature at all, which is part of why they are limited to a single workflow and no code.
