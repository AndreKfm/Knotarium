Importing configurations

The Import screen reads a configuration file exported from another vendor's system and translates it into Knotarium workflows. It is a migration tool: you hand it someone else's automation, it tells you honestly how much of that automation it could express, and it lands the result as inactive drafts you review before anything is allowed to run. Nothing about this screen is reversible-by-accident — there is a dry run, and there is an undo.

What this screen needs before it works

The importer is a generic shell around a plugin. Knotarium itself understands no vendor format whatsoever; a host plugin supplies a source-format provider that knows how to parse one. With no plugin installed, the screen shows a single message — that no import providers are registered and that you need to install a connection-manager plugin that ships one — and nothing else on this page applies.

Plugins are loaded at startup from the folder named by NodeRuntime__PluginsPath, which defaults to a plugins folder beside the application. Each plugin lives in its own subfolder. Adding one means restarting; a plugin that fails to load is logged and skipped rather than stopping startup, so a provider that never appears in the list is worth looking for in the startup log.

The vendor format never reaches Knotarium

The boundary is deliberate. The host passes the plugin raw bytes, a hint derived from the file extension, and your options; the plugin returns generic workflow definitions plus a coverage report. No vendor-specific type crosses that line, which is why the importer can describe results in the same vocabulary regardless of which system the file came from — and also why the accuracy of a translation is entirely the provider's business, not the host's.

The three steps

A stepper across the top tracks where you are: Upload file, Configure, then Review coverage. Uploading a file advances to Configure; previewing or importing advances to Review coverage. Removing the file returns you to the start and clears every choice you made.

Step 1 — choosing a source format and a file

When more than one provider is installed, a Source format dropdown appears above the drop zone listing each provider by its display name. With exactly one provider the dropdown is hidden and that provider is selected automatically. Changing the source format resets the whole form, because a file parsed by one provider means nothing to another.

The drop zone accepts a click or a drag-and-drop. The file picker is filtered to the extensions the selected provider declares, and those extensions are also printed on the chip below the drop zone next to the provider's name — so the screen tells you what it will accept rather than making you guess. Three explanatory cards under the drop zone restate the flow: upload and translate, review coverage, publish and arm.

Selecting a file parses it immediately. This first parse is a preview call — it is required to be free of side effects, and it is what discovers the servers the configuration references and produces the first coverage report. Once it finishes, a file chip shows the file's name, its size in kilobytes, the provider that read it, and how many constructs were detected, with a Parsed badge that reads Parsing… while the call is in flight.

A parse failure is reported, not explained

If the provider cannot read the file, the screen shows the provider's own error message prefixed with a generic import failure. There is no partial parse and no salvage mode: the file is either understood or it is not. The commonest cause is the wrong provider selected for the file, which looks like a corrupt file rather than a mismatch.

Step 2 — configuring the import

Granularity: one workflow or many

Under Create as, two cards decide how the flows in the file are distributed across workflows. The section only appears when the provider declares that it honours the choice.

OptionWhat you get
One combined workflow Every flow in the file lands in a single workflow as independent chains, side by side on one canvas.
Separate workflows One workflow per flow. Each is published, armed and managed on its own.

The provider chooses which one is preselected, and the preselection is re-applied whenever you change provider. Vendor configuration files typically default to the combined option, for a practical reason: a single exported configuration can hold well over a hundred flows, and importing them as a hundred separate workflows floods the dashboard with entries nobody named.

The trade-off is real in both directions. One combined workflow is a single thing to publish and a single thing to arm, which makes the migration manageable — but it is also a single failure domain and a canvas you will have to untangle later. Separate workflows give you per-flow control from the start at the cost of a large, unstructured list. If you are evaluating an import, combine; if you are committing to it, consider separating and expect to spend time naming things.

Granularity does not change what the parse finds, so switching between the two does not re-parse the file. Only the coverage report's workflow count changes.

Device connections

Vendor configurations usually address physical devices or servers. When the provider declares that it references external systems and the parse discovered at least one, a Device connections section appears, headed with the count and listing the discovered aliases. Three strategies are offered:

StrategyWhat it does
Create automatically Makes a connection target for each referenced server, reusing any existing target with the same name instead of duplicating it. This is the default.
Map to existing Binds each referenced server to a connection target you already have. One dropdown per alias, each showing the alias and its host.
Don't map Provisions nothing. The imported nodes address the default target.

Choosing Map to existing and leaving any alias unmapped disables the Import button, with a line beside it saying every server must be mapped. Preview stays available, so you can still inspect coverage with an incomplete mapping. If you have no connection targets at all, an amber line says so and points you at connection settings — targets are managed under Settings › External Systems.

Changing the strategy, or changing any individual mapping, re-parses the file. That is what keeps the plan below accurate rather than stale.

The provisioning plan

Whenever a strategy other than Don't map is selected and the provider returned a plan, a Plan: line lists what would happen to each referenced server. Each entry is an alias, an action, and where applicable the target it resolves to:

ActionMeaning
CreateA new connection target will be created for this alias.
ReuseAn existing target with a matching name will be used as-is.
BindThe alias will be bound to the target you selected.
SkipNothing will be provisioned for this alias.
Created targets arrive without passwords

The plan line says so, and so does the success banner afterwards. A connection target created by the import carries the host and user the configuration described, but no credential — the vendor file does not contain one, and the importer will not invent one. Until you open Settings › External Systems and set each new target's password, those targets are offline and any workflow addressing them fails at run time. This is the single most common reason a technically successful import does nothing useful.

The dry run

Preview re-parses the file with your current options and switches to the coverage view without writing anything. The banner reads Preview, states how many workflows would be produced and whether they would be combined or separate, and says explicitly that this is a dry run and nothing has been imported.

The dry run is genuinely side-effect free — provisioning is switched off for it at the contract level, so even the Create actions in the plan are hypothetical. From the preview you can go Back to change your options, or Import to commit without re-reading the report.

The coverage report

The report is the reason this screen exists. Every construct the provider encountered gets one row, including the ones it could not translate — the contract states that a construct with no analogue is surfaced here and never silently dropped. Four columns:

ColumnContents
Scope Where in the source file the construct came from, in monospace — the provider's own coordinate for it.
Construct What it was. Bare numbers in this text — device and sequence identifiers — are highlighted, and a plain -> is rendered as an arrow, so relationships are readable at a glance.
Outcome A colour-coded pill: Mapped, Partial or Flagged.
Note The provider's reason, where it supplied one; otherwise an em dash.

The three outcomes are graded by the provider, and mean exactly this:

OutcomeMeaningWhat to do
Mapped Translated cleanly to a Knotarium construct. Nothing. Spot-check a few.
Partial Translated approximately. Something about the original was not fully expressible. Review each one. The result will run, but it may not do precisely what the original did.
Flagged No analogue exists. The construct is emitted as a stub so it is visible on the canvas rather than absent. Rebuild it by hand, or accept that this behaviour did not come across.

Above the table, three count pills summarise the whole report — how many mapped, how many partial, how many flagged. A segmented control filters to All or to one outcome, and a search box filters rows by the text of their scope or construct; the two combine, so you can search within the flagged rows alone. The footer says how many rows are visible out of the total, which matters because a filtered table can otherwise look reassuringly short.

Read the flagged rows before you import, not after

The count pills are the honest summary of what a migration will cost you. Filter to Flagged first: if that list is long, the import is a starting point rather than a migration, and it is better to know before you have a hundred drafts on the dashboard. Then read Partial, which is the more dangerous of the two — a partial row produces something that runs, and therefore something that can be wrong quietly.

Importing

Import runs the same translation with provisioning switched on, creates the connection targets the plan described, and installs each generated workflow as an inactive Imported version. The success banner reports how many workflows were imported and whether they were combined or separate, repeats that they are inactive drafts that will not run until you publish and arm them, and lists any connection targets that were created along with the reminder to set their passwords.

The coverage report stays on screen after the import, now reflecting the committed run, with three actions in its footer: Undo import, Import another, and Go to dashboard.

Collision handling

Providers assign their own workflow ids, and those ids are not necessarily unique across imports — a provider that produces one workflow per file may well use the same fixed id every time. Left alone, importing a second configuration would file it as a hidden new version of the first rather than as its own workflow.

The importer prevents that. Before installing, it reads the ids and names already in the database and, for each workflow whose id collides, mints a fresh id and appends a numeric suffix to the name until it is free — so a second import of a configuration named Building A installs as Building A (2). The set of taken ids grows as the import proceeds, so several workflows inside a single upload cannot collide with each other either.

Re-importing does not update anything

Importing a corrected version of the same configuration file produces a new set of workflows beside the old ones, not an update to them. There is no merge, no diff, and no reconciliation. If you are iterating on an import, undo the previous attempt before running the next one — otherwise the dashboard accumulates near-identical drafts distinguished only by a numeric suffix.

Undoing an import

Undo import is offered in the report footer immediately after a successful import, labelled with the number of workflows it will remove. It archives every workflow the import created, in one call, and the banner then reads that the import was undone and how many workflows were removed. The button disappears once used.

"Archives" is the precise word. A workflow that has versions is marked archived and its draft removed, rather than being erased — archived workflows are hidden from the dashboard list but can be restored, which un-archives the header and rebuilds its draft from the latest version. A workflow with no versions at all is simply dropped.

Undo covers workflows only

It removes exactly the workflows listed in the import result, and nothing else. Connection targets the import created under Create automatically stay behind, along with any password you set on them. If you undo an import and re-run it, expect the second run to report Reuse where the first reported Create. Cleaning up orphaned targets is a manual job under Settings › External Systems.

Undo is also bounded in time by the screen itself: it is available while the result is on screen, and it is gone once you press Import another, navigate away, or reload. There is no undo history. If you leave the screen and want the same effect, archive the workflows individually from the dashboard.

After the import

Everything the importer creates is inert. In order for an imported workflow to do anything, three separate things have to happen, and the importer does none of them:

  1. Any connection target the import created needs its password set under Settings › External Systems.
  2. The workflow needs to be published — an imported version is created but not made active.
  3. The runtime needs to be armed, and the workflow enabled, before a trigger will fire.

That ordering is worth respecting. Publishing before the targets are online produces a workflow that publishes cleanly and fails on its first run, which is a more confusing failure than one that never starts.

Importing is an administrator action

Both the preview and the install endpoints require an administrator, because an import creates workflows and can act on connection targets. When sign-in is disabled the check is a no-op — which is one more reason an instance running without authentication should never be reachable beyond localhost. See the configuration reference.
