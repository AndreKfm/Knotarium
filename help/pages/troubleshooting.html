Troubleshooting

Organised by what you observe rather than by which component is at fault. Almost every entry here has the same shape: something is refusing to happen quietly, because a secure default is doing its job. The messages quoted are the exact strings the application produces, so you can search this page for the text in front of you.

Nothing runs automatically

A scheduled workflow never fires

Three separate switches all have to be in the right position before a schedule produces a run, and none of them announces itself when it is not. Check them in this order.

The runtime is disarmed. The switch in the header reads Disarmed. While it does, the scheduler and the pollers keep ticking but skip every evaluation, so there is no failed run to look at and nothing in the dead letter queue — the workflow simply does not appear to exist. A fresh instance starts disarmed on purpose, and so does one you have just been editing, because opening the canvas disarms it. Click the switch to arm it.

The workflow is deactivated. This is separate from arming and applies to one workflow rather than the instance. A deactivated workflow shows an Inactive badge on its card in the dashboard, and its power button reads Inactive — click to activate. Newly created workflows start deactivated, which is the single most common reason a first schedule never fires. Deactivating also cancels anything already in flight, so do not use it as a pause button on a busy workflow.

There is no active version. Triggers run the active published version, never your draft. A workflow you have drawn but never published has nothing to run. The scheduler marks the firing as failed, advances to the next occurrence and writes a warning naming the schedule and the workflow — Skipped schedule fire for schedule … because workflow … has no active version. A polling trigger logs the equivalent. Publish and activate the workflow, then wait for the next occurrence.

Manual runs bypass only the first of the three

Arming does not gate a manual run, so a workflow you can run by hand may still be deactivated or unpublished. If the manual run also fails, you are looking at the second or third cause, not the first.

A webhook call is rejected

Inbound triggers go to a single anonymous endpoint, POST /api/executions, which names the target workflow in the request body. It applies seven checks in a fixed order and returns a different status for each, so the response tells you exactly which gate closed:

StatusMessageWhat to do
401 Invalid or missing webhook secret. Send the secret in the X-Knotarium-Webhook-Secret header. This check is deliberately first so that an unauthorised caller cannot learn the instance's arming state.
409 Runtime is disarmed. Arm the runtime to allow external triggers. Arm the runtime from the header switch.
404 Workflow definition not found The identifier in the body does not match a workflow. Check for a stale id after a restore.
409 Workflow is deactivated and cannot be triggered externally. Activate the workflow from its dashboard card.
409 Workflow has no active version. Publish and activate a version before triggering execution. Publish, then set a version active.
429 Execution queue is at capacity (… pending runs). Retry later. See the section on runs being refused below.
400 Workflow failed compilation and cannot be triggered The response carries the compiler diagnostics. Open the workflow and fix what the Diagnostics panel reports.
202 — Accepted. The run identifier is in the Location header.

A workflow with no secret configured accepts unauthenticated calls, so the first check is skipped rather than failed. Request bodies larger than Security__WebhookMaxBodyBytes — one megabyte by default — are rejected before any of this.

Webhook calls are rejected with an empty 429

Two different limits return 429 and they are easy to confuse. The queue-capacity rejection carries a JSON message naming the limit. The rate limit returns a bare 429 with no body at all — there is no rejection handler, so nothing explains itself.

The anonymous machine-to-machine limit allows Security__RateLimit__AnonymousMachinePerMinute requests per minute, sixty by default, in a fixed one-minute window with no queueing, partitioned by the caller's IP address. It covers exactly two endpoints: the webhook trigger and run resumption. A burst of legitimate webhook traffic from one source address will hit it. Raise the setting and restart; see the configuration reference.

The runtime disarmed itself

There are two mechanisms, and they behave differently enough that telling them apart matters.

Opening the canvas editor disarms it. Every time you enter the editor from somewhere else, the runtime is disarmed. The reasoning is that design time should be safe time: a half-finished draft should not fire on a schedule while you are still moving nodes around. This writes the disarmed state to the database, so it survives a restart, and re-arming is always a deliberate click on the header switch. Nothing pops up to tell you it happened; the only hint in the interface is the tooltip on the toolbar's run-history button, which notes that editing auto-disarms.

The low-disk guard disarms it. When free space on the data drive falls below Storage__MinFreeSpaceMb — 256 MB by default — the guard disarms the runtime and logs at critical level: 

Free disk space 118 MB is below the 256 MB threshold — runtime DISARMED
to stop new runs. Free up space and re-arm manually.

It does not re-arm when space comes back. Recovery is logged, and the wording is explicit that the decision is yours: 

Free disk space recovered to 4096 MB. The runtime was disarmed by the
disk-space guard; re-arm it when ready.
A guard disarm is undone by a restart

Unlike the editor's auto-disarm, the disk guard changes only the in-memory state and does not write to the database — the reasoning is that a transient low-disk blip should not permanently disarm an instance. The consequence is that restarting the process re-reads the stored value and can silently arm the instance again while the disk is still nearly full. The guard will trip again within a minute, but runs can start in that window. Free the space before restarting.

The threshold and the check interval are edited at Settings › Retention, under Minimum free space (MB). Setting it to zero disables the guard entirely.

My error workflow never runs

The global error handler is configured at Settings › Notifications. It is enqueued by an internal producer, which means it is never refused for queue depth — but it is a silent no-op when the workflow you nominated has no active version. An error workflow you drew and saved but never published will never run and will never complain. Publish it and set a version active.

A change appears to be ignored

My edits to the workflow have no effect

Nothing in Knotarium ever executes an unsaved draft. Not a trigger, and not the Run button.

Pressing Run on the canvas activates whichever version is selected in the toolbar's version dropdown and then triggers the workflow. Your unsaved changes are not part of that version, so a run started immediately after an edit executes the code as it was when you last published. If the workflow has never been published at all, the run does not start and the toolbar reports Publish a version (Save & Publish) before running.

The fix is always the same: press Save & Publish, which saves the draft, snapshots it as a new version and makes that version active in one step. See Versions and publishing.

A configuration change has no effect

There are four distinct reasons a setting can be edited correctly and still do nothing.

The interface overrides the file. Several groups of settings are editable at runtime and are then stored in the database, where the stored value wins permanently over anything in appsettings.json or the environment. This applies to the sandbox (Settings › Sandbox), retention and the disk threshold (Settings › Retention), the capability policy (Settings › Capabilities), the file access policy (Settings › File Access), the AI provider (Settings › AI Provider) and the arming state. Change these in the interface, not in the file.

The environment variable is set for the wrong account. Under the Windows service manager the process runs as the service account, and reads that account's environment, not your interactive session's. Setting a variable in a PowerShell window and restarting the service changes nothing. Set it as a machine-level variable or in the service definition.

The setting is read once at startup. Everything not in the list above is read during startup only. Restart the process after editing it.

The Logging section is inert. appsettings.json contains one, but logging is configured in code and never consults it. Editing Logging__LogLevel__Default has no effect whatsoever.

KG_AUTH_ENABLED or KG_ENCRYPTION_KEY has no effect

These are not application settings. They are shell variables interpolated by docker-compose.yml before the container ever starts, and the translation into real setting names happens entirely inside that file. Setting KG_AUTH_ENABLED=false on a zip install, a Windows service, a systemd unit or a plain docker run does nothing at all — and it fails silently, which is worse, because you are left believing sign-in is disabled when it is not.

Outside Compose use the full names: Auth__Enabled, Security__Credentials__EncryptionKeyBase64 and Security__PackageSigning__HostPrivateKeyBase64.

A node is refused at run time

A File Read or File Write node is denied

File access is deny-by-default: a fresh instance permits nothing, and every path must be granted explicitly. The node fails with File read failed: or File write failed: followed by the specific reason, and carries the error code FileAccessDenied. The reasons distinguish four different situations:

ReasonMeaning
… is not permitted (nothing is granted yet). An administrator must grant it under Settings → File Access. The policy is empty. This is what a new instance says.
… is outside every permitted directory. Grants exist but none covers this path.
… is within a grant that does not permit writing. The directory is granted, but read-only. The same message appears with reading for the opposite case.
only absolute paths are allowed, got '…'. A relative path was passed. Resolve it in the workflow first.

Open the failed run and the sidebar will have recognised the denial and offered a remediation button reading Grant access in File Access settings →, with a heading naming the specific problem — Path is not permitted, Path is granted read-only and so on. Following it switches to Settings › File Access with the parent directory of the attempted path already filled in as a new rule, left unsaved so you can review it before committing.

The pre-filled grant is always write

The remediation adds the rule with the mode set to Write regardless of which operation failed. If a File Read node was denied, change the mode to Read before saving rather than granting write access you did not intend. Grants are recursive — they cover the named directory and everything beneath it.

A write can also be denied for a reason that has nothing to do with policy: if completing it would leave the target drive below the reserved free space, the node fails with a message naming how much would be left and what the reserve is.

An Inline Code or Database Query node refuses to run

Both are privileged capabilities and both are off by default. The messages name themselves precisely:

  • Inline Code is disabled: the 'code execution' capability is off. An administrator can enable it under Settings → Capabilities.
  • Database Query is disabled: the 'database' capability is off. An administrator can enable it under Settings → Capabilities.

A custom node package fails the same way, because running one is running compiled code: Custom node '…' runs compiled code, which is disabled: the 'code execution' capability is off. Testing a node from the node editor produces its own variant of the same refusal.

Enable them at Settings › Capabilities, where the toggles are labelled Inline code execution and Database access. The toggles save immediately; no restart is needed. Do this only on an instance whose workflows you trust, because inline code is real C# with the process's own reach.

An outbound HTTP request is refused

Every outbound request the engine makes passes through the egress policy, including the HTTP Request node, AI provider calls and OpenAPI operations. All refusals start with Outbound egress denied. The variants tell you which rule fired:

MessageRule
Outbound egress denied for local host '…'. localhost and any name ending in .local or .internal. This one is unconditional — turning off DenyPrivateNetworks does not lift it.
Outbound egress denied for private or loopback address '…'. A literal IP address in a private, loopback or link-local range.
Outbound egress denied: host '…' resolves to a private, loopback, or link-local address. A hostname that resolved to such an address. If any of the resolved addresses qualifies, the whole host is refused.
Outbound egress denied by blocklist for host '…'. The host matched Security__HttpEgress__BlockDomains.
Outbound egress denied because host '…' is not in the allowlist. An allow-list is configured and the host is not on it.
Outbound egress denied because host '…' did not resolve to any address. DNS returned nothing. Usually a genuine name or resolver problem rather than policy.

Two ordering details save time. The block-list is evaluated before the allow-list, so a host on both is refused. An empty allow-list means no allow-list — it permits everything rather than nothing.

The check runs on every physical connection, including each redirect hop, and the socket then connects to the addresses that were just validated. A hostname cannot be rebound to an internal address between the check and the connection. This is also why a host that resolves differently from inside your network may be refused here and reachable from a browser on the same machine.

If reaching internal hosts is the actual point of the instance, set Security__HttpEgress__DenyPrivateNetworks to false and restart — but note the .local and localhost refusals remain in force regardless.

Runs queue up or are refused

Four runs execute at once by default and the rest wait, so a backlog is normal rather than a fault. Refusal only starts when the queue reaches Execution__MaxQueueDepth, one thousand by default, at which point new starts get 429 with the message Execution queue is at capacity (1000 pending runs). Retry later.

Which starts are refused is not obvious and is worth knowing before you raise any limits:

  • Refused: manual runs, inbound webhook calls, and firing a schedule by hand from the editor.
  • Never refused: automatic schedule fires, polling triggers, external device signals, the error workflow, and runs re-queued by crash recovery. These are internal producers and bypass the cap by design, so an automatic workload can push the queue past its own ceiling while manual runs are being turned away.

The live counters — in-flight runs, queue depth, both limits and the number of rejected starts — are available from GET /api/runtime/execution. Both limits are read at startup only, so raising Execution__MaxConcurrentRuns (valid range 1–64) or Execution__MaxQueueDepth (1–100000) requires a restart.

AI nodes fail

The provider is not configured

Every AI node fails with the same sentence until a provider is set up: 

The AI provider is not configured. Choose a provider, model, and API-key
credential in Settings → AI Provider.

The configuration is only considered complete when all three are present: a recognised vendor, a non-blank model name, and a credential reference. Setting the vendor and leaving the model blank produces this same message, which reads as though nothing was configured at all. The supported vendors are Anthropic, OpenAI, Azure OpenAI and Gemini.

The API key itself is never stored with the provider settings — only a reference to a stored credential or an environment variable. If that reference cannot be resolved you get a different message naming it: The AI provider API key could not be resolved from '…'. Check the credential in Settings → AI Provider. The workflow generator has its own wording, AI workflow generation is not configured…, but the same fix applies.

Settings › AI Provider has a test button that reports the specific gap rather than a generic failure — A model (or Azure deployment name) is required., An API-key credential is required. and so on. Use it before debugging a workflow.

The AI Agent will not use tools

Three different causes produce this, and they are distinguishable by the message.

The capability is off. The node fails immediately with AI Agent is disabled: the 'aiAgent' capability is off. An administrator can enable it under Settings → Capabilities. Follow the message: the switch is the third row on Settings › Capabilities, labelled AI agent tool loop. It saves immediately and the check is read per execution, so re-running the workflow straight afterwards succeeds without a restart.

The vendor does not support it. The AI Agent node does not support Gemini in this version. Configure Anthropic or an OpenAI-compatible provider in Settings → AI Provider. Other AI nodes work with Gemini; only the agent's tool loop does not.

The model is an OpenAI reasoning model. Reasoning models reject function tools on the chat completions API. Knotarium adapts automatically — it retries once with the parameter those models require and remembers the model so later turns skip the wasted round trip — but when the retry also fails you get: 

the configured model does not support function tools on the OpenAI Chat
Completions API (it looks like a reasoning model, e.g. the gpt-5 family).
The AI Agent needs a tool-capable model — set a per-node model override
such as gpt-4o or gpt-4.1, or choose a non-reasoning model in
Settings → AI Provider.

The per-node override is the better fix, because it leaves the reasoning model in place for the prompt and routing nodes that benefit from it while giving the agent a tool-capable model.

Credentials, data and upgrades

Saved credentials cannot be decrypted after a move or restore

Knotarium.db stores credentials encrypted; .credential-key in the same data directory is what decrypts them. Copying the database without the key file is the single most damaging mistake available in this product, and the way it fails is what makes it dangerous.

It does not fail at startup. Finding no key file, the application generates a new random one and carries on. The instance starts cleanly, the credentials are all still listed by name, and everything looks intact. Only when a workflow actually resolves a credential does it fail, with an authentication-tag mismatch from the cryptography layer, surfaced as the failed node's error in the run. The same happens when a notification channel sends and when a new backup is created.

There is no recovery without the original key. Restore .credential-key from the source machine into the data directory and restart; if it is genuinely gone, every stored secret must be re-entered.

Restoring an instance backup produces a much clearer message, because that path checks explicitly. A server-key backup restored on the wrong host reports Couldn't decrypt with this server's key — a server-key backup only restores on the host that created it (its credential key must be unchanged). A passphrase backup with the wrong passphrase reports Incorrect passphrase, or the backup archive is corrupt. Both come from Settings › Backup & Restore. See Backup and restore.

Back the two up together, always

Knotarium.db and .credential-key are a pair. Back up the whole data directory as a unit rather than picking files out of it.

Upgrading left the workflows or the database behind

Older builds kept workflow drafts in the per-user %APPDATA%\Knotarium folder. On every non-development startup the application looks there and moves what it finds into the current data directory. What it moves is narrow:

  • Draft .json files from %APPDATA%\Knotarium\workflows\, not recursively.
  • groups.json.

It moves nothing else. Not the database, not the credential key, not the export folder. If your previous installation kept Knotarium.db next to the executable, the new version starts with an empty database and the old one sits where it always was. Copy it and its .credential-key into the data directory before first launch, or point Database__ConnectionString at the old file.

Two further traps are worth knowing. The source folder is the AppData of the account running the process, so a service running as a machine account will find nothing in your user profile and log nothing interesting — run the executable interactively once to migrate your own drafts. And a file whose name already exists at the destination is never overwritten: it is skipped with Skipping legacy workflow file …: a file with the same name already exists in … and left in %APPDATA%, where it remains recoverable by hand.

A migration that fails on permissions or a locked file logs Could not migrate the legacy workflow store from …; continuing with the shared data directory only and startup continues rather than aborting. A successful one logs how many files moved.

The application will not start

Startup fails because authentication is disabled

If Auth__Enabled is false while any configured binding is not a loopback address, startup aborts on purpose with: 

Authentication is disabled (Auth:Enabled=false) but the server is
configured to bind a non-loopback address (…). In no-auth mode every
endpoint is anonymous, so this would expose an unauthenticated
remote-code-execution surface. Bind loopback only (e.g.
http://127.0.0.1:PORT), enable authentication (Auth:Enabled=true), or set
Security:AllowUnauthenticatedNonLoopback=true to accept the risk (e.g.
behind a trusted reverse proxy).

The guard inspects both the aggregate URL setting — which covers ASPNETCORE_URLS, DOTNET_URLS and --urls — and any Kestrel endpoint URLs. Note that a DNS hostname counts as non-loopback even if it happens to resolve to the local machine; only localhost and literal loopback addresses pass. Wildcards such as *, +, 0.0.0.0 and :: obviously do not.

In a development environment the same condition is downgraded to a [WARN] line on standard error and startup continues, which is why this can appear only after a deployment. Take the first two remedies in the message before the third.

Startup fails on the audit chain

The audit log is hash-chained and the chain is verified during startup; a chain that does not verify aborts the launch rather than starting with a log that can no longer be trusted. This is normally a symptom of a partially restored or hand-edited database. Note that enabling audit retention deliberately rewrites the chain to re-anchor the surviving entries, so older entries can no longer be checked against the original chain — that is expected, not corruption.

Where to find the logs

Application logging is console-only, one line of compact JSON per event, written to standard output. There is no log file and no rolling policy — do not go looking for a logs folder, there is not one. The log level is fixed in code at information, with database logging held down to warnings, and cannot be changed through configuration.

How you run itWhere the log goes
From a folder or a shortcutThe console window it was started from.
systemd on LinuxThe journal: journalctl -u knotarium -f.
Dockerdocker logs on the container.
Windows serviceNowhere retrievable. See below.
A Windows service has no log destination

The service is registered without stdout redirection and nothing writes to the Windows event log, so console output from a service run is discarded. To diagnose a service-mode problem, stop the service and run the executable interactively from a console with the same configuration. This is a real gap, not an undocumented location.

Two things inside the interface look like logs and are not. The run timeline is the per-run journal — the record of what each node received and produced — and is the right place to debug a workflow. The Diagnostics panel in the editor shows compiler diagnostics for the graph you are drawing. Neither shows application log events, and there is no in-app viewer that does.
