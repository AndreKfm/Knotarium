Network nodes

The nodes that reach outside the process — HTTP, SQL, the local filesystem, mail, MQTT, notification channels, and the operations generated from an imported OpenAPI specification. These are the nodes that need a credential, a capability grant, or both, and they are the ones that fail for reasons outside your workflow. Each entry lists every parameter the executor actually reads, the default it falls back to, and what the node does when it goes wrong.

What every node on this page has in common

A node in this group has three things a Log or a Set Variable node does not: it may need a credential, it may need a capability switched on, and it can fail because of something on the other end of a socket. Understanding those three before reading the individual entries saves repeating them nine times.

Credentials are referenced, never stored

Any parameter whose type is credentialRef holds the identifier of a stored credential, not the secret itself. The executor resolves it at run time through the secret resolver, so the password, token or connection string never appears in the workflow definition, in an exported bundle, or in a version diff. A blank credentialRef is not an error at compile time — the node simply runs with no secret, which usually surfaces as an authentication failure from the remote server rather than as a Knotarium error.

Which nodes are gated, and by what

Two different mechanisms gate these nodes, and they live on different settings screens. The coarse on/off switches at Settings › Capabilities cover code execution, database access and the AI agent loop. File access is deliberately not one of those switches — it has its own finer-grained directory policy at Settings › File Access. Everything else on this page runs without a grant.

Only three capabilities are actually enforced

The capability list on a manifest is mostly descriptive metadata used to warn you before installing an imported workflow. Exactly three tags are enforced at run time as on/off switches: code.execute, database and aiAgent. The network and credentials tags are never checked — a node carrying network is not gated by anything, so do not read the absence of a capability warning as "this node cannot reach the network".

Outbound HTTP goes through the egress policy

Every named HTTP client that can reach a user-supplied URL is registered behind the egress guard, and the guard validates twice: once against the literal URI, and once again at the point the socket is opened, pinning the connection to an address it has already vetted. That second check is what stops a redirect hop or a DNS name that resolves to 169.254.169.254 from reaching a private or metadata address after the URL passed inspection.

SettingDefaultEffect on these nodes
Security__HttpEgress__DenyPrivateNetworks true Refuses any request that resolves to a private, loopback or link-local address. This is the setting that blocks an HTTP Request aimed at a machine on your own LAN.
Security__HttpEgress__AllowDomains empty When non-empty, only these domains may be reached. Empty means no allow-list is applied at all.
Security__HttpEgress__BlockDomains empty Always refused, checked after the allow-list.

The guarded clients cover the HTTP Request node, the OpenAPI caller, the polling trigger, AI provider calls, dynamic-options loaders, OAuth token fetches, the context.Http handed to inline and compiled scripts, and outbound notification webhooks. See the configuration reference for the full list of security settings.

SMTP, IMAP, MQTT and SQL bypass the egress guard

The egress policy is an HTTP-client concern. Email Send, Email Fetch, MQTT Publish and Database Query open their own TCP sockets through MailKit, MQTTnet and the database driver, so DenyPrivateNetworks and the domain lists have no effect on them. A mail or broker host on a private network is reachable even with the strictest egress configuration. If that matters to you, the boundary has to be enforced at the firewall.

How the ports behave

The ports listed in each entry are the handles you can draw an edge from. Only six node types pick a single branch to follow — Condition, For Loop, Parallel For-Each, AI Router, AI Verify and AI Semantic Diff. Nothing on this page is one of them. When a node here succeeds, the engine schedules every outgoing edge, whichever handle it left.

When the node fails, the engine looks for outgoing edges whose handle is named error or failure. If it finds any, it follows those and the run continues; if it finds none, the whole run is marked failed at that node.

An error edge also fires on success

Because these nodes do not select a branch, an edge you draw from the error handle is scheduled on a successful run as well as a failed one. The handle is a failure edge in the sense that the engine takes it when the node fails — not in the sense that it is skipped when the node succeeds. If your error branch must run only on failure, gate it with a Condition on the upstream node's output rather than relying on the handle alone.

Automatic retry is narrower than the manifest suggests

Several manifests here declare a recovery mode of "retry automatically", but the retry scheduler also requires the node to be marked as an idempotent side effect. A node that changes something on the far end is never retried automatically, no matter what its recovery mode says — re-sending an email or re-running an INSERT because a socket hiccuped is worse than failing. In practice that leaves three nodes on this page with automatic retry.

Where retry does apply, the default policy is three attempts with a two-second initial delay, doubling with jitter up to thirty seconds. A timeoutSeconds (or timeout) property set on the node overrides the manifest default, clamped to 1–3600 seconds.

Web and API nodes

HTTP Request

The general-purpose way to call something that speaks HTTP. Reach for it when there is no imported OpenAPI specification to generate a typed node from, when you are calling a webhook or a one-off endpoint, or when you need control over the exact headers and body. If you are calling many operations of the same documented API, importing its specification is less work and gives you an operation picker instead of hand-written URLs.

Authentication is applied before your custom headers, deliberately: an explicit Authorization header in the headers field overrides whatever the auth block produced, so an API with a non-standard scheme is still reachable.

On a successful call the node emits three values downstream: statusCode (a number), body (the raw response text) and isSuccess (a boolean, always true here, since a non-2xx fails the node instead).

Content-Type is handled specially

A Content-Type entry in the headers field is pulled out and applied to the request body rather than added as a request header. With no body it therefore has no effect at all, and with a body but no explicit Content-Type the node sends application/json. This is the usual explanation for an API rejecting a form-encoded body you thought you had labelled correctly on a GET.

A 4xx or 5xx fails the node, it does not branch

Any non-2xx status makes the node fail with a message containing the status code and the response body. Because HTTP Request is a non-idempotent side effect, it is not retried automatically even though its manifest declares "retry automatically". Handle expected error statuses with an error edge, or with a workflow-level error handler.

Imported OpenAPI operations (openapi.<slug>)

Importing an OpenAPI specification does not generate one node per endpoint. It generates one node package for the whole specification, whose operationId parameter is a picker over every operation the document declares. Reach for these instead of HTTP Request whenever the API you are calling publishes a specification: you get an operation list, a reusable server configuration holding the base URL and credential, and a version pin.

The package id is openapi. followed by the specification's own id lowercased with every character outside a–z, 0–9 and - removed; an id that reduces to nothing becomes openapi.spec. The node's display name is the specification's title, and it is filed under the Integrations category in the palette.

ParameterTypeRequired{{ }}Effect
operationIdstringyesnoWhich operation to invoke. The generated manifest lists every operation id found in the specification as a selectable value, so this renders as a dropdown rather than free text.
serverConfigIdstringyesnoThe saved server configuration supplying the base URL, the credential and the certificate policy. Without it the node has no idea which host to call.
specVersionstringnonoPins the call to a specific stored version of the specification. Left blank, the active version is used — which means re-importing a changed specification can change what this node does.
argumentsstringnoyesThe path, query, header and body arguments for the chosen operation. This is the field that carries your {{ }} references to upstream data.
PortWhen it fires
successThe operation returned a successful response.
errorThe node failed. Also scheduled on success, as with every non-branching node.
No code is generated or compiled

Every openapi.* node runs through a single pre-compiled interpreter rather than per-specification C#. Importing a specification therefore does not invoke the compiler, cannot fail with a compilation error, and does not depend on the sandbox settings. It is a manifest and nothing more.

The capability tags differ from the built-ins

Generated OpenAPI manifests carry the tags http and credentials, where the built-in nodes use network. Neither tag is enforced, so this is cosmetic — but it does mean a search for nodes tagged network will not find your imported API operations.

Data store and file nodes

Database Query

Runs one parameterized SQL statement against PostgreSQL or SQLite and hands the rows back as data. Use it for the cases an HTTP API cannot cover: reading a table your organisation already maintains, or writing a row as the last step of a workflow. Anything more elaborate than a single statement belongs in a stored procedure or a view that this node then calls.

Values are always bound as database parameters and never concatenated into the statement text, which is what makes the node injection-safe. Write @name in the query and supply name under Parameters; the key may be written with or without a leading @, : or $ and is normalised to @name, a form both drivers accept.

Off until an administrator turns it on

The node checks the database capability before it does anything else. On a fresh instance nothing is enabled, so the node fails immediately with "Database Query is disabled: the 'database' capability is off." Enable it at Settings › Capabilities. This is a privileged capability: a workflow that can run arbitrary SQL against a connection string you supplied can do anything that connection string permits.

The node has no error port of its own: a failure is an ordinary node failure, so an edge named error or failure drawn from it is still followed. For a SELECT, rowCount is the number of rows returned; for a write it is the number of rows affected as reported by the driver. Byte-array columns are base64-encoded and GUIDs are stringified so the result survives the JSON journal.

File Read

Reads one local file and emits its contents. Use utf8 when the file is text you want to parse or match on, and base64 when it is binary — an image, a PDF, a zip — that you intend to pass through to an attachment or an upload without interpreting it.

Deny by default, and it is not the Capabilities screen

A fresh instance grants no directories at all, so every read is denied until an administrator adds one at Settings › File Access. The check happens before any I/O: the requested path is made absolute, every symlink and junction along it is resolved to its real target, and the result must sit inside a granted subtree. Textual .., a different drive, and a junction pointing out of an allowed root are all rejected, and a path whose real location cannot be determined is denied rather than trusted.

ParameterTypeRequired{{ }}DefaultEffect
pathstringyesyesnoneAbsolute path to the file. A relative path is rejected outright under an enforced policy, because it cannot be safely bounded against absolute grants.
encodingenumnonoutf8utf8 returns text; base64 returns the raw bytes base64-encoded. Any other value is treated as utf8.
PortDeclared typeFields
resultobjectcontent (string), encoding (string), size (number, bytes) and path (string — the canonical, boundary-checked path actually read, not what you typed)

A policy refusal and a missing file are different failures. A refusal carries the error code FileAccessDenied, which is what lets the run view offer a one-click "grant this path" action; the message always names the resolved path in single quotes. A file that is permitted but absent fails with "file not found" and no error code.

File Write

Writes text or decoded bytes to a local file, creating any missing parent directories along the way. Use append for a running log; leave it off to replace the file wholesale.

ParameterTypeRequired{{ }}DefaultEffect
pathstringyesyesnoneAbsolute destination path. Missing parent folders are created after the policy check passes.
contentstringnoyesemptyWhat to write. An unset content writes a zero-byte file rather than failing.
encodingenumnonoutf8base64 decodes the content to raw bytes first. Content that is not valid base64 fails with a clear message before any file is touched.
appendbooleannonofalseAppends instead of overwriting. Also changes the free-space arithmetic: an overwrite only needs headroom for its net growth, an append needs headroom for the whole payload.
PortDeclared typeFields
resultobjectpath (the canonical path written) and bytesWritten (number)

Writes are checked against the same directory policy as reads, plus a free-space reserve: if the write would leave the target drive below the configured reserve, it is refused with a message naming both the remaining space and the required reserve. Two folder-shaped mistakes are caught with their own messages rather than a raw operating-system permission error — a path ending in a directory separator, and a path that resolves to an existing directory.

A known, accepted race

The guard validates a path and returns it as a string; the node opens the file afterwards. An actor able to swap a validated directory component for a junction between the check and the open could redirect the write. This is accepted under the assumption that operating-system ACLs on a granted root prevent untrusted content from creating reparse points inside it. If you grant a writable root to workflows you did not author, set its ACLs accordingly.

Messaging nodes

Email Send (SMTP)

Composes and sends a message through an SMTP server. Reach for it when the recipient is a person who expects mail; for operational alerts that should follow the same routing as automatic failure notifications, Send Notification is the better choice because the server details and secret live on the channel rather than on every node.

The node also journals an explicit "attempting external effect" entry before it connects, which is what lets the run history distinguish "never sent" from "possibly sent".

Email Fetch (IMAP)

Pulls recent messages from a mailbox and emits them as data. It pairs with the polling trigger for the common "watch an inbox" shape: poll on a schedule, fetch the unseen messages, mark them seen so the next run does not see them again.

Each message in the array is flattened to uid, from, to, subject, date (UTC, ISO 8601 round-trip format) and body. The body is the plain-text part when the message has one and the HTML part otherwise — there is no separate HTML field, and attachments are not extracted.

Without markSeen you will reprocess the same mail

Fetching is idempotent, which is why this node is retried automatically on failure. The flip side is that a polling workflow which does not set markSeen — or which fails after fetching but before acting — sees the same messages on the next poll. Set unseenOnly together with markSeen for at-most-once-ish behaviour, and accept that a crash between the flag and your side effect can still lose a message.

MQTT Publish

Publishes one message to a topic on an MQTT broker. Use it to push a workflow's result onto a bus that devices or other services already listen to. This node only publishes; consuming a topic is a separate long-lived subsystem, not a node you drop on the canvas.

Send Notification

Sends a message through a notification channel you configured once at Settings › Notifications. This is the right node for "tell someone this happened": the channel owns the transport, the endpoint and the secret, so the workflow carries only a channel reference and the text. It reuses exactly the same channel storage and sender layer as the automatic failure alerts, which means a channel you have already tested for alerts is already proven for this node.

The node declares no capabilities and needs no grant, because it cannot be pointed at an arbitrary destination — it can only use a channel an administrator already created. Delivery failures are reported with the channel name in the message, so a broken webhook is identifiable without opening the settings screen. Webhook-based channels do go through the egress guard.
