Bundles

A bundle is an integration shipped as one file: several workflows, the custom node packages they depend on, a lock recording exactly which package bytes were meant, and a declaration of the credentials the recipient must supply. Where a template is a convenience, a bundle is a supply chain — which is why installing one runs a verification gate that can refuse the whole thing. Bundles has two tabs, Install and Export.

Bundle or template?

Both formats carry workflows and both use the same slot: credential placeholders, so the choice comes down to what else needs to travel:

Template (.kgtpl)Bundle (.kgbundle)
WorkflowsExactly oneAny number
Node packagesNoneEvery non-built-in package the workflows use
Dependency lockNonebundle.lock, with a hash per package
SignaturesNonePer package, verified on install
Credential handlingCredentials are stripped into slots automatically on exportSlots are declared by hand; export does not rewrite credential ids
Install parametersTyped {{param:…}} valuesNone
Failure modeImports as a draft even when not runnableAll-or-nothing; a rejected install writes nothing

If you are sharing one workflow built from stock nodes, reach for a template. If your workflow depends on a custom node package you wrote in the node editor, only a bundle can carry that package with it.

What is inside a .kgbundle

A .kgbundle is a zip written deterministically — entries in a stable order with a fixed timestamp — so identical contents always produce identical bytes and therefore an identical hash. Its layout is:

EntryContents
bundle.jsonThe manifest: authoring intent. Bundle id, version, name, publisher, tags, category, schema version, minimum engine version, the package references, the declared credential slots, the workflow references, and the claimed provenance. Deliberately carries no hashes.
bundle.lockThe resolved record: for every package, its resolved version, its SHA-256, the source it resolved from, and its trust level, plus the resolution timestamp and resolver version. This is what the installer verifies against.
packages/<id>.jsonOne file per package — the signed payload (id, version, display name, category, manifest, source and capabilities) plus its detached signature, if it has one.
workflows/<key>.jsonOne exported workflow document per bundled workflow.

The split between manifest and lock mirrors package.json and package-lock.json. The manifest is what a human wrote; the lock is what the machine resolved, and it is the only half the installer trusts. Anything verifiable — hashes, resolved source, trust level — lives in the lock and never in the manifest.

Entry names are checked when the archive is read: an entry that is neither bundle.json, bundle.lock, nor a direct child of packages/ or workflows/ is rejected rather than ignored, as is a nested path or a name containing a path separator. A bundle may hold up to 1024 entries.

The upload hint overstates the size limit

The Install tab describes the drop zone as accepting an archive "up to 200 MB". The limit the reader actually enforces is much smaller: 5 MB for the compressed archive, 25 MB total uncompressed, 10 MB for any single entry, and a 100:1 compression ratio. A larger file is refused with an archive error rather than being accepted and truncated, so the failure is loud — but it will not be the failure the interface led you to expect. Bundles carry JSON, not binaries, so a real bundle is far below either number.

Export — assembling a bundle

The Export tab builds the manifest from four sections, then asks the server to resolve and pack it.

Metadata

FieldNotes
Bundle idRequired; the export is refused without one. A reverse-domain name such as com.example.integration is the convention the placeholder suggests. It also becomes the file name stem.
VersionDefaults to 1.0.0; an empty value is packed as 0.0.0.
NameFalls back to the bundle id when left blank.
PublisherFree text. Recorded in the manifest and in the claimed provenance.
CategoryFree text.
TagsComma-separated.

The download is named from the id and the version, so com.example.integration at 2.1.0 arrives as com.example.integration-2.1.0.kgbundle.

Publisher and provenance are claims, not evidence

Both the publisher field and the manifest's provenance block record what the exporter typed. Nothing verifies them, and the manifest is not covered by any signature. The only statement in a bundle that carries cryptographic weight is a package's own signature, checked against your trusted keys — everything in bundle.json is a label.

Workflows

A checklist of every workflow on the instance, with Select all and Clear all. At least one must be selected or the export is refused. Each selected workflow becomes a manifest entry with the role primary, and its exported document is written into the archive under its own id.

Packages — derived, not chosen

There is no package picker. Every node's type is a package id, so the bundle's package set is computed from the node types used by the workflows you selected, and the panel updates as you tick workflows on and off. Two filters apply:

  • Built-in node types drop out. They ship with the engine, carry no installable registry version, and cannot be bundled — if your workflows use only built-in nodes, the panel says so and the bundle contains no packages at all.
  • Each remaining package is pinned to an installed version whose source is not a built-in one — the panel describes this as its latest installed version.

A bundle with no packages is perfectly valid: it is a multi-workflow archive, and its verification gate has nothing to gate, so it passes trivially.

Credential slots

Add credential slot appends a row with two fields: the slot key — the slot:<name> placeholder the bundled workflows are expected to use — and a human-readable label shown to whoever installs the bundle. A row with an empty key is dropped when the manifest is built, and the label defaults to the key when left blank.

Bundle export does not remove your credentials

This is the single most important difference from a template. Template export walks every node property and rewrites credential references into slots automatically. Bundle export does not. Workflows are packed exactly as they are, so a workflow referencing a real credential id ships that id inside the bundle, and declaring a slot here does not cause any rewriting to happen. For a portable bundle, the workflows themselves must already reference credentials as slot:<name> placeholders matching the slots you declare. The only thing stopping you from shipping host-specific credential references is remembering to.

A practical route to a portable bundle is to prepare the workflow first — export it as a template and reinstall it with the slots deliberately left unbound, which leaves the placeholders in place — and only then bundle it. The alternative is to edit the credential fields to slot: values by hand before exporting.

A sticky action bar at the bottom summarises the selection as a count of workflows, packages and slots, next to the Export .kgbundle button. Export fails loudly rather than producing a partial archive: a package reference that cannot be resolved against the installed registry, or a selected workflow with nothing to export, aborts the whole operation with a message naming the package or workflow at fault.

Signing

Bundle trust rests entirely on the signatures carried by the individual node packages inside it. Two configuration settings govern the two directions.

SettingDirectionEffect
Security__PackageSigning__HostPrivateKeyBase64 Outbound The Ed25519 private key this host signs node packages with. It must be valid base64 decoding to exactly 32 bytes; a key that is missing, not base64, or the wrong length makes publishing fail with a server error naming which of the three it was.
Security__PackageSigning__TrustedPublicKeys Inbound The list of public keys whose signatures this host accepts. Empty by default, which means no signature can verify and every signed package is treated as untrusted.
The signature is applied when a package is published, not when a bundle is exported

Exporting a bundle never invokes the private key. A package is signed at the moment it is published to this instance's registry, and the signature is stored with it; bundle export copies that stored signature into the archive and records the resulting trust verdict in the lock. So the host private key affects what your bundles contain, but only indirectly — via the packages you published with it. A package installed rather than published arrives with a signature someone else produced, which must already verify against your trusted keys or the install is refused.

Signing covers a canonical serialization of the package's identity and content — id, version, display name, category, manifest JSON, source and capabilities — hashed with SHA-256 and signed with Ed25519. Because the serialization sorts keys recursively, two logically identical manifests that differ only in key order produce the same digest.

Verification asks one question: does this signature verify against any key in TrustedPublicKeys? A consequence worth knowing is that a cryptographically broken signature and a perfectly valid signature from a publisher you have not trusted are currently indistinguishable in the report — both appear as Untrusted signature. Telling them apart would require the package to carry its signer's public key, which the format does not yet do.

Install — the verification gate

The Install tab takes a .kgbundle by click or drag-and-drop, offers an Allow provisional installs toggle, and installs on the button. What happens next is a sequence of gates, each of which must pass before the next runs, with every database write held until the end:

What verification actually re-derives

The installer does not take the lock's word for anything. For each package listed in the lock it finds the matching file under packages/, recomputes the hash from the carried payload, compares it against the lock, re-checks the signature against your trusted keys — which may differ entirely from the exporter's — and re-derives the trust level from that result. The lock is a claim to be checked, not a verdict to be accepted.

Trust is derived from two inputs, the signature verdict and the package's resolved source:

Trust levelHow a package earns itInstallable?
Verified Its signature verified against one of your trusted public keys. The source is irrelevant. Always.
Provisional No verified signature, but the package's source is local — it was authored on a Knotarium instance rather than claiming a remote origin. Only with Allow provisional installs ticked.
Untrusted No verified signature and a non-local source. This is a package claiming an origin it cannot prove. Never — there is no override.

The verification report

Whatever the outcome, a table appears listing every locked package with six columns — Package, Trust, Signature, Hash, Status and Installable — and the rows that blocked the install are highlighted. Signature and Status are kept as separate axes on purpose, because they answer different questions:

Signature columnMeaning
No signatureThe package file carries no signature at all.
Untrusted signatureA signature is present but did not verify against any of your trusted keys. As noted above, this covers both an invalid signature and a valid one from an untrusted signer.
Verified signatureThe signature verified against a trusted key.
Status columnMeaning
MissingThe lock names a package with no matching file under packages/. A file that fails to parse is also reported this way rather than crashing the gate.
Tampered (hash mismatch)The file is present but its recomputed hash does not match the lock. The bytes changed after the bundle was locked.
UntrustedIntact bytes, but this host will not trust their origin.
ProvisionalIntact bytes, locally authored, unsigned.
VerifiedIntact bytes with a signature verified against a trusted key.

A hash mismatch always wins over the trust verdict: if the bytes changed, the lock no longer describes what would be installed, so re-derived trust is beside the point. This is why a tampered package and a merely untrusted one are never conflated — collapsing them would let tampering hide behind a trust note.

Unsigned, or signed by a key you do not trust

These are the two cases you will actually meet, and they behave differently:

  • Unsigned and locally authored. Trust is Provisional. The install is rejected with 422 and nothing is written until you tick Allow provisional installs and install again. This is the normal path for a package a colleague built in their own node editor.
  • Unsigned but claiming a non-local source. Trust is Untrusted, and the provisional toggle does not help — there is no configuration that makes it installable. To install it you must obtain a properly signed build, or add the publisher's public key to TrustedPublicKeys and use a copy that is actually signed.
  • Signed by an untrusted key. Also Untrusted, for the same reason and with the same absence of an override. The fix is to add that publisher's public key to TrustedPublicKeys and restart, which turns the same file into a Verified install — a signature is re-evaluated on every install attempt, so nothing about the bundle needs to change.
Provisional installs bypass signature verification by design

The toggle's own description says so. A compiled node package runs code inside the engine, so allowing provisional installs is a decision about whether you trust the person who handed you the file — the software cannot help you there. Enable it deliberately, for one install, rather than leaving it on.

The privileged-node acknowledgement

Once verification passes, every node across every bundled workflow is resolved against its package manifest and any privileged capability — filesystem, code execution, database — is collected. If anything is found and you have not acknowledged it, the install stops there and writes nothing.

Because the scan happens server-side, the warning appears after your first install attempt rather than on upload: an amber panel lists each privileged node with its capabilities and offers I understand and want to install this bundle, and the primary button changes to Re-install. Tick the box and press it again. Nothing was installed by the first attempt.

Version conflicts

The last check before any write compares each locked package against what is already in the registry. If a package at that exact version is installed but its bytes hash differently from the lock, the whole install is rejected with a conflict banner naming the packages, and nothing is written.

This refusal is the point. Skipping such a package as "already installed" would quietly bind the bundle's workflows to a different build of the same version number, which is the sort of failure that surfaces weeks later as behaviour nobody can reproduce. A package version that is already installed with identical bytes is skipped, and the success banner lists it under "Skipped (already present)" — that skip is genuine idempotence, since the pre-flight has just proved the bytes match.

Credential slots

Slot binding for bundles happens after an install attempt rather than before it. The result carries the slots the manifest declares, and a Credential slots card appears with one dropdown per slot, defaulting to leave unbound. Choose credentials and install again.

Leaving a slot unbound is allowed. The imported workflows keep the literal slot:<name> placeholder, the success banner lists the unbound slots in amber, and you can either re-install with bindings or set the credentials on the workflows directly. Rebinding walks node properties at any depth, so a placeholder nested inside an object or an array is rewritten along with the top-level ones.

What a successful install did

The success banner enumerates exactly what changed:

  • Installed packages — added to the registry at their locked versions.
  • Skipped (already present) — that version was already installed with identical bytes.
  • Imported workflows — each with the version number that was created for it.
  • Bound credential slots, and separately any left unbound.

Workflows are imported as new inactive versions. As with templates, installing a bundle never causes anything to run: publishing, enabling and arming remain your decisions.

One known gap in the all-or-nothing guarantee

Package rows, package versions and workflow versions are written inside a single database transaction, so a failure part-way through rolls all of them back. The workflow draft file that importing writes is not covered by that transaction, because it goes through the file-based workflow store rather than the database. A failure at exactly the wrong moment can therefore leave a draft file behind while the database rolls back. The residue is a stray draft you can delete — no package is half-installed — but the guarantee is not quite absolute.

Configuring the two keys

Both settings follow the usual configuration precedence, and both are read at startup, so changing either means restarting. The private key is a secret and belongs in a secret store or an environment variable, never in a checked-in appsettings.json. 

# Accept packages signed by two publishers (PowerShell)
$env:Security__PackageSigning__TrustedPublicKeys__0 = '<base64 public key>'
$env:Security__PackageSigning__TrustedPublicKeys__1 = '<base64 public key>'

# Sign the packages this host publishes — 32 raw bytes, base64-encoded
$env:Security__PackageSigning__HostPrivateKeyBase64 = '<base64 private key>'

Under Docker Compose the shorthand KG_SIGNING_KEY maps to the host private key. That translation lives in the Compose file, not in the application, so the shorthand does nothing on a zip install, a Windows service or a plain docker run — see the configuration reference.

An empty trusted-key list is the default

Out of the box, TrustedPublicKeys is empty, which means no signature can verify. Every signed package is then Untrusted and blocked, and only locally sourced packages get as far as Provisional. That is the correct fail-closed behaviour, but it does mean the first signed bundle you are given will be refused until you have added the publisher's key — and the report will say "Untrusted signature", which reads like an accusation when the real answer is that you have not told the instance whom to trust.
