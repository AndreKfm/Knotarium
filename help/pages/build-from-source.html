Building from source

Knotarium builds with two toolchains and no other infrastructure: a .NET SDK for the backend and Node for the user interface. There is no database to provision, no code generation step and no container required. This page covers running it from a clone, producing a shippable build, and the three test suites — plus the parts of the build that behave differently from what the README implies.

Prerequisites

ToolVersionNeeded for
.NET SDK 10.0 Everything backend. Every project targets net10.0, and the solution is an .slnx file, so an older SDK cannot even restore it.
Node.js 22 or newer The interface. Node is a build-time dependency only — the shipped product contains no JavaScript runtime.
PowerShell 7 7.0+ Only for publish.ps1, which declares that requirement explicitly. run.ps1 is Windows-oriented and uses Windows-only cmdlets.
Inno Setup 6 optional Only for publish.ps1 -Installer.
Python 3 optional Only for the mock REST API that run.ps1 -MockApi launches.
Warnings are errors

Backend/Directory.Build.props sets TreatWarningsAsErrors for every backend project, so a build that compiles on your machine and fails on someone else's is usually an analyzer difference, not flaky tooling. Package-vulnerability warnings (NU1901 through NU1904) are deliberately exempted, because upstream advisories appear without anyone touching the code and are fixed by dependency bumps rather than by breaking every local build.

The nodes/ folder is a stale copy

The manifests under nodes/ look authoritative and are not. The node catalog the running product uses is Backend/Knotarium.Features.Compiler/InMemoryNodePackageManifestProvider.cs. Read that file when you need to know what a built-in node actually declares. The nodes/ folder also shares its name with the default binary-package watch folder at run time, which is a separate thing entirely — see Custom node packages.

Running from a clone

The backend and the interface run as two processes during development. The backend serves the API on 43120; Vite serves the interface on 5273 and proxies /api through to the backend, so the browser only ever talks to one origin and the session cookie behaves exactly as it does in production. 

# Terminal 1 — backend, http://localhost:43120
dotnet run --project Backend/Knotarium.Api

# Terminal 2 — interface, http://localhost:5273
cd Frontend
npm install
npm run dev

Open http://localhost:5273, not 43120 — in development there is no bundled wwwroot, so the backend serves the API and nothing else. The Vite port honours a PORT environment variable if you need a second instance side by side; the proxy target stays 43120 either way. vite preview, which serves a production build locally, mirrors the same proxy on port 4173.

Development mode is load-bearing

Running through dotnet run puts the host in the Development environment, and that changes far more than logging: it moves where data is stored, relaxes the HTTPS-only session cookie, refuses to auto-generate a credential encryption key, skips the legacy draft migration, and turns node-package hot-reload on. A development instance is not a small production instance. The full list is in the Configuration reference.

run.ps1

On Windows, ./run.ps1 does the two-terminal dance for you. It is a developer convenience with some opinions:

  • It kills whatever is listening on 43120 and 5273 before starting, walking up the process tree through cmd, powershell and pwsh parents to catch a shell wrapper. If a process refuses to die for want of privileges, the script relaunches itself elevated.
  • It opens two new PowerShell windows, one per service, and starts the backend with the http launch profile, waiting three seconds before starting Vite.
  • -Clean deletes every bin and obj folder under Backend/ first, forcing a full rebuild.
  • -MockApi also starts the Python mock REST server from dev/mock-api on port 8787, serving a spec at /openapi.json. If Python is not on the path the script says so and continues without it.

Stopping the environment means closing the two console windows. There is no stop switch.

The productive single-folder build

./publish.ps1 produces a copy-and-run build: a self-contained .NET publish with the whole runtime bundled, plus the built interface in wwwroot beside the executable so the backend serves both from one origin. The output lands in publish/app. 

./publish.ps1                              # win-x64 Release folder build
./publish.ps1 -Runtime linux-x64
./publish.ps1 -SkipFrontend                 # reuse an existing Frontend/dist
./publish.ps1 -Version 1.0.0-rc.1 -Zip -Installer
ParameterDefaultEffect
-Runtimewin-x64The .NET runtime identifier to publish for. linux-x64 is what the release workflow uses for the tarball.
-ConfigurationReleaseBuild configuration.
-OutputDir./publishWiped and recreated on every run.
-Port43120Baked into the generated Start.bat and passed to the installer script.
-SkipFrontendoffSkips the Vite build and reuses Frontend/dist. The script still fails if that folder has no index.html.
-SingleFileoffOne self-extracting executable instead of a folder.
-Versionfrom the csprojStamped into the assembly and used in artifact names. Falls back to the <Version> element in Knotarium.Api.csproj.
-ZipoffAlso compresses publish/app into a versioned zip with a .sha256 beside it.
-InstalleroffAlso compiles installer/Knotarium.iss with Inno Setup's ISCC, auto-detected in the usual locations or given via -InnoSetupExe.
-SignCertBase64from SIGN_CERT_BASE64Enables Authenticode signing of the executables and the installer. With no certificate the step is a complete no-op and the output is an ordinary unsigned build.

Three choices in that script are deliberate and worth not "fixing":

  • Not NativeAOT, not trimmed. The engine compiles inline code and custom nodes with Roslyn at run time, which needs the JIT and reflection metadata. Ahead-of-time compilation or trimming removes the feature.
  • A folder, not a single file, by default. A self-extracting build unpacks to a temporary directory at launch, which antivirus routinely flags, and it leaves Assembly.Location empty — which the Roslyn compiler needs. The single-file switch compensates with IncludeAllContentForSelfExtract, but the folder build avoids the problem rather than working around it.
  • No debug symbols. DebugType=none keeps .pdb files out of the shipped folder.
The closing message about the database is wrong

publish.ps1 finishes by printing that "the SQLite database (Knotarium.db) is created next to the exe on first run". It is not. The database and the credential key are created under the machine-wide data directory — %ProgramData%\Knotarium on Windows — unless Storage__DataDirectory says otherwise. Back up that directory, not the application folder.

The Docker build

The Dockerfile is a three-stage build: Node 22 builds the interface, the .NET 10 SDK image publishes the backend framework-dependent (the ASP.NET runtime image supplies the runtime), and the runtime stage copies both together. 

docker build -t knotarium:dev --build-arg VERSION=1.0.0-rc.1 .
docker run -d -p 43120:43120 -v knotarium-data:/data knotarium:dev

# or, from the compose file in the repository root
docker compose up --build

Details that matter when you change it: the image sets Storage__DataDirectory=/data explicitly, because the cross-platform default resolves to /usr/share inside a container and is not persisted; it binds http://+:43120 so traffic from outside the container is accepted; and it runs as the non-root app user, with /data created and chowned in the image so a named volume inherits that ownership on first use. A bind mount does not — chown the host directory to UID 1654, or pass --user.

The backend copy step takes only Backend/, so a change under Frontend/ does not invalidate the backend layer and vice versa. help/ is copied straight into ./wwwroot/help/ in the runtime stage.

Running the tests

Backend

cd Backend
dotnet test

That runs all four test projects. The architecture project is worth running on its own while you work, because it is fast and it is the one that fails when a feature slice reaches across a module boundary it should not: 

dotnet test Backend/Knotarium.Architecture.Tests/Knotarium.Architecture.Tests.csproj
Why CI serializes the backend suite

The sandbox tests spawn real worker processes. Running four test assemblies in parallel, each with xUnit's own parallelism, exhausts memory on a 7 GB runner, and a test then blocks forever waiting on a worker that never started. CI therefore runs everything single-threaded with a five-minute hang timeout. If you see the suite hang locally on a small machine, the same switches fix it.

Frontend

cd Frontend
npm install
npm test          # vitest run, jsdom environment
npm run build     # tsc -b && vite build — the type check lives here
npm run lint      # eslint

npm test runs once and exits; npm run test:watch is the interactive form. The type check is part of npm run build, not of npm test, so a type error passes the unit tests and fails the build — run both before pushing.

End-to-end

cd Frontend
npx playwright install chromium   # once
npm run test:e2e

Playwright starts both servers itself: the backend with the http launch profile, waiting on /api/workflows, and the Vite dev server. It reuses an already-running backend outside CI but always starts its own dev server, so shut down a stray Vite on 5273 first. The specs run in Chromium only, one worker, not in parallel.

The backend it launches gets Security__HttpEgress__DenyPrivateNetworks=false, because the OpenAPI importer spec drives a generated node against a mock server on loopback and the egress policy blocks that by default. That relaxation applies to the test backend and nothing else.

The e2e suite is not part of CI. It is yours to run when you touch the canvas or the importer.

What CI checks

One workflow gates a pull request against main, with four jobs that must all pass.

JobWhat it does
SPDX license headers Fails if any .cs, .ts or .tsx file outside node_modules, obj, bin and dist lacks an SPDX-License-Identifier in its first 400 bytes. Add the two-line copyright and SPDX header to every new source file.
Architecture / drift guard Runs Knotarium.Architecture.Tests alone, so module-boundary drift is caught in review rather than months later.
Frontend build + tests npm ci, then npm test, then npm run build. npm ci means package-lock.json must be committed and in sync.
Backend tests Restore, build the solution once, then run the whole suite serialized with a five-minute hang timeout and a thirty-minute job cap.

A second workflow builds releases on a tag: Windows artifacts through publish.ps1 -Zip -Installer, a Linux tarball through publish.ps1 -Runtime linux-x64, an optional VirusTotal scan whose links are appended to the release notes, and a multi-architecture container image pushed to the GitHub container registry. It is not part of the pull-request gate.

Editing the offline help

This documentation lives in help/ as plain HTML with no build step. Both publish.ps1 and the Dockerfile copy the folder verbatim into wwwroot/help, where the existing static-file middleware serves it at /help with no backend route involved. The one exception is the directory form /help/, which needs a literal route so it is not swallowed by the interface's catch-all fallback.

Two scripts belong to it, and both should be run after any edit: 

node scripts/build-help-index.mjs   # regenerates help/assets/search-index.json
node scripts/check-help-links.mjs   # verifies every link, asset and anchor resolves

The index generator reads the site map from help/assets/nav.js and re-derives the search index from the pages, so a page added without dropping its pending flag is reported rather than silently omitted. The link checker resolves every internal reference, including in-page anchors — which it computes the same way the runtime does, from the heading text — and it also validates the committed search index, because an index pointing at a renamed heading is a broken link by another name.

The authoring rules for a page — the markup vocabulary, the tone, and the requirement that every fact come from the source rather than the README — are in help/AUTHORING.md.

Neither script is wired into CI

Nothing fails a pull request when the help index is stale or a link is dead. Offline documentation has no server to report a 404, so a broken link stays broken and silent. Running both scripts is a manual discipline, and it takes under a second.
