Custom node packages

A node package is a manifest plus, optionally, an executor. The manifest declares what the node is called, which parameters it exposes, which sockets it has and which capabilities it needs; the executor is the C# that runs. This page is the reference for that format and for the three different routes a package can take into a running instance — the in-app editor, a signed install, and a compiled assembly dropped into a watched folder.

The three kinds of package

Everything in the palette comes from one of three sources, and knowing which one you are looking at explains most surprises:

  • Built-in. Compiled into the product and served from an in-memory provider. The authoritative list lives in Backend/Knotarium.Features.Compiler/InMemoryNodePackageManifestProvider.cs — the manifests under the repository's nodes/ folder are a stale second copy and should not be trusted as documentation.
  • Binary. A .dll plus a companion manifest.json, loaded from disk at startup into an in-memory executor registry.
  • Custom. A manifest, and for the compiled tier a block of C# source, stored as rows in the database. This is what the node editor and the install endpoint write.

Tiers

The manifest's tier decides how the node executes. Three values exist:

TierWhat runs
Declarative A shared built-in executor interprets the manifest. No compilation, no privileged capability required. This is the tier the built-in nodes use.
Compiled The package's C# source is compiled with Roslyn on first use and cached. Gated on the code execution capability, and routed through the process sandbox when one is configured.
Interpreted Reserved for the OpenAPI importer's generated openapi.* nodes, which all route to one pre-compiled interpreter. You do not author this tier by hand.

A tier the runtime does not recognise is refused rather than treated as compiled C#, so a typo here fails loudly.

The manifest schema

Manifests are deserialized case-insensitively with camel-cased property names and string enum values, so displayName and DisplayName both bind, and tier: Compiled and tier: compiled are both accepted by the backend. The in-app editor is stricter — see the note at the end of this section.

FieldTypeDefaultMeaning
idstringrequired The node type. Dotted lower-case by convention. This is the identity the palette, the compiler and the catalog merge all key on.
versionstringrequired Free-form version string. Ordered semantically when it parses as a .NET version, ordinally otherwise — which means a pre-release suffix such as 1.0.0-rc.1 sorts as text.
displayNamestringrequired The palette and canvas label.
categorystringrequired The palette section. The canvas palette has sections for Trigger, Logic, Data, Network, Ai and Utility; a category outside that set still stores fine but has no section of its own.
tierenumrequired Declarative, Compiled or Interpreted.
sideEffectKindenumNonIdempotentSideEffect IdempotentSideEffect or NonIdempotentSideEffect. Declares whether running the node twice is harmless — the honest answer here is what makes replay and automatic retry safe.
recoveryModeenumfrom the document RetryAutomatically or FailImmediately.
defaultTimeoutSecondsinteger0 Per-execution timeout handed to the sandbox runner for compiled nodes.
capabilitiesstring arrayempty The privileges the node claims. See the capability table below.
parametersarrayempty Configuration fields shown in the properties panel. Detailed below.
outputsarrayempty The node's output sockets. An empty list means the node has nowhere to connect onward.
inputsarrayempty Typed data inputs consumed from upstream, distinct from configuration parameters. Declaring required fields opts the node into compile-time field checking against the producing output's schema.
retryPolicyobjecta default policy Omitted means the default policy is applied, not that retries are disabled. Fields below.
triggerOnlybooleanfalse The node can only start a workflow; it is not placeable mid-graph.
secondarybooleanfalse Editor hint: an escape-hatch node. See below.
descriptionstringnull A one-line summary. Surfaced to AI workflow generation so a model can map an intent onto the right node — display name and category alone are ambiguous across vendor packs.

Parameters

A parameter is a configuration field, not a data socket. The properties panel renders one editor per parameter, in manifest order.

FieldTypeMeaning
namestringThe key the executor reads out of NodeInput.Parameters, and the label shown above the field.
typestringWhich editor to render. See the type list below.
requiredbooleanRenders a red asterisk beside the label.
expressionbooleanAdvertises that the field accepts {{ … }} expressions, and shows the hint under it.
valuesstring arrayThe options, for enum.
descriptionstringA hint line rendered under the field.
optionsLoaderstringFor dynamicOptions and resourceLocator: the server-side loader to call. Loaders are allow-listed by name.
integrationTypestringThe endpoint namespace the loader lives under.
dependsOnstring arraySibling parameter names whose current values are passed to the loader.
loaderConfigstring mapStatic loader configuration, for example a path or a label field. connectionParam names the sibling holding the connection id.
allowManualEntrybooleanPermits free text when the remote system is unreachable at design time.
multiplebooleanStores an order-preserving array of keys instead of a single value.

The property form renders these types: string, number, boolean, enum, credentialRef, notificationChannelRef, code, keyValue, dynamicOptions, resourceLocator, dynamicFields, agentTools and aiModel. An unrecognised type falls back to the string editor rather than failing.

Outputs, inputs and field schemas

An output has a name, an optional type defaulting to any, and an optional fields list. An input has the same three. A field schema entry has name, type (default any) and required (default false).

Leaving type as any is the compatible choice: untyped sockets never trigger type-mismatch warnings. Declaring concrete types and required fields is opting in to compile-time checking, where the compiler verifies that a downstream node's required fields are actually delivered by whatever is wired into it.

Capabilities

Capability strings are both documentation and enforcement. The draft test runner fails a case that invokes a capability the manifest did not declare, and the import flow warns before installing a workflow containing a node that claims a security-sensitive one.

CapabilityMeaning
filesystem.readReads local files, enforced against the file-access policy.
filesystem.writeWrites local files, enforced against the same policy.
code.executeExecutes arbitrary code on the host. The highest privilege, and off by default.
databaseRuns arbitrary database queries. Off by default.
aiAgentRuns an LLM tool-use loop that can invoke other workflows. Off by default.
networkMakes outbound network calls. An informal tag rather than a hard gate.
credentialsResolves stored secrets. Also an informal tag.

The draft sandbox records three names when it observes them — logging, http and credentials — so a package whose executor logs must declare logging, and one that sends a request must declare http, even though neither string appears in the table above. Declare both the runtime capability and the tag the sandbox records.

The secondary flag

secondary: true marks a node as a de-emphasized escape hatch. The palette pulls every such node out of its normal category and into a single Advanced section, which is collapsed by default and rendered last. Use it when your package offers both a friendly block and a raw one and you want the friendly one to be the obvious choice; a user who wants the raw block can still find it, but will not trip over it.

The in-app editor reads a smaller schema

The node editor's sandbox parser ignores properties it does not recognise, and it spells two of them differently: it reads sideEffectKindName and recoveryModeName, not sideEffectKind and recoveryMode. The scaffolded templates use the short spellings, so those two lines are silently discarded during a draft test run and the defaults apply instead. Separately, the editor's own YAML reader drops every field except id, version, displayName, category, tier and parameters when it publishes. Both behaviours are covered in detail on The node editor; the practical consequence is that a manifest which must be complete should not be authored there.

A complete manifest

The following is a full manifest for a compiled package with two parameters, two outputs, a typed input, an explicit retry policy, and the palette flags set. As JSON this is exactly what goes in a binary package's manifest.json or in the manifestJson field of an install request: 

{
  "id": "acme.invoice.submit",
  "version": "1.2.0",
  "displayName": "Submit Invoice",
  "category": "Network",
  "tier": "Compiled",
  "description": "Posts an invoice to the Acme billing API and returns the receipt id.",
  "sideEffectKind": "NonIdempotentSideEffect",
  "recoveryMode": "FailImmediately",
  "defaultTimeoutSeconds": 60,
  "secondary": false,
  "triggerOnly": false,
  "capabilities": ["logging", "http", "network", "credentials"],
  "parameters": [
    {
      "name": "endpoint",
      "type": "string",
      "required": true,
      "expression": true,
      "description": "Absolute URL of the billing endpoint."
    },
    {
      "name": "apiKey",
      "type": "credentialRef",
      "required": true,
      "expression": false
    }
  ],
  "inputs": [
    {
      "name": "invoice",
      "type": "object",
      "fields": [
        { "name": "customerId", "type": "string", "required": true },
        { "name": "amount",     "type": "number", "required": true }
      ]
    }
  ],
  "outputs": [
    {
      "name": "success",
      "type": "object",
      "fields": [
        { "name": "receiptId", "type": "string", "required": true }
      ]
    },
    { "name": "error", "type": "object" }
  ],
  "retryPolicy": {
    "maxAttempts": 2,
    "initialDelaySeconds": 5,
    "backoffRate": 2.0,
    "jitter": true,
    "maxDelaySeconds": 60
  }
}

Writing the executor

A compiled package's source must contain a concrete, non-abstract class implementing INodeExecutor. The loader takes the first such type it finds in the assembly, so ship one executor per package. 

using System;
using System.Text.Json;
using System.Threading;
using System.Threading.Tasks;
using Microsoft.Extensions.Logging;
using Knotarium.Core.Contracts;
using Knotarium.Core.Domain;

namespace Knotarium.Nodes;

public class SubmitInvoiceExecutor : INodeExecutor
{
    public async ValueTask<NodeResult> ExecuteAsync(
        NodeInput input, INodeContext context, CancellationToken cancellationToken)
    {
        context.Logger.LogInformation("Submitting invoice…");

        if (!input.Parameters.TryGetValue("endpoint", out var endpointElement))
        {
            return new NodeResult("error",
                JsonSerializer.SerializeToElement(new { error = "endpoint is required" }),
                NodeExecutionStatus.Failed);
        }

        var payload = JsonSerializer.SerializeToElement(new
        {
            receiptId = Guid.NewGuid().ToString("N"),
            submittedAt = DateTimeOffset.UtcNow
        });

        return new NodeResult("success", payload, NodeExecutionStatus.Succeeded);
    }
}

The pieces worth knowing:

  • input.Parameters is a dictionary of JsonElement keyed by the parameter names from your manifest. Expressions have already been evaluated by the time you see them.
  • context gives you Logger, State for workflow variables and upstream node outputs, and the nullable Http and Credentials accessors. Every one of them is recorded against your declared capabilities during a draft test run.
  • The first argument to NodeResult is the output socket name, and it must match one of your declared outputs or the graph has nowhere to send the result.
  • Honour cancellationToken. Both the 15-second draft test limit and the runtime timeout are cooperative: code that never observes the token cannot be stopped.

The draft compiler also accepts a bare script body — source that does not look like a class implementing the interface is wrapped into a generated executor with an Input.Get<T>(name) helper. That is convenient for experiments and is not a good shape for something you intend to install.

Banned namespaces

The analyzer that runs before compilation rejects System.IO, System.Diagnostics, System.Reflection.Emit, System.Net.Sockets, System.Runtime.InteropServices, System.Runtime.Loader and Microsoft.Win32, resolving symbols rather than matching text so aliases and casing tricks do not help. It also flags mutable static state. Treat it as a linter, not a jail: a binary package you drop into the watch folder is never analyzed at all, and even the analyzed path executes in-process.

How the catalog merges

The catalog endpoint concatenates built-ins, then binary packages, then database packages into a dictionary keyed by id, so the later source wins: custom beats binary beats built-in. Ids are compared ignoring case. The intent is that a deployed package can override a placeholder built-in of the same id and the palette shows one authoritative entry rather than a shadowing pair.

Within one package, the versions are ordered newest-first by creation time, and the manifest lookup uses the newest. A package whose manifest JSON is malformed is skipped rather than breaking the whole catalog — it simply disappears from the palette, which is worth remembering when a node you know you installed is not there.

Resolution at run time is a different order

Executing a node does not go through the catalog merge. The task registry resolves a node type in this order:

  1. A built-in task type, matched by name.
  2. The binary executor registry — the highest loaded version for that id.
  3. The database, via the dynamic custom-node task.

So a built-in task still wins at execution time even where a database package of the same id won the catalog merge and is what the palette showed you. Overriding a built-in id is therefore only partially effective, and that inconsistency is a good reason to choose a fresh, vendor-prefixed id.

For a database package the tier decides what happens next. Declarative runs the shared interpreter. Compiled first checks the code execution capability and fails with an explicit message if it is off, then compiles the stored source with Roslyn — cached on a key of node type, version and creation timestamp, so a republished version recompiles and an unchanged one does not — and hands it to the sandbox runner if one is configured, which is what makes Security__Sandbox__Mode effective for custom nodes.

Installing and publishing

Two endpoints write a package into the database. They share their implementation and differ only in how trust is established.

RouteTrust model
POST /api/node-packages/install The caller supplies a signature. It is verified against Security__PackageSigning__TrustedPublicKeys; an unsigned or unverifiable package is rejected with a 400. Use this to install someone else's package.
POST /api/node-packages/publish No signature is accepted from the caller. The server requires a passing sandbox test for this exact package id and version, then signs the package itself with Security__PackageSigning__HostPrivateKeyBase64. Use this from the node editor.

Both are administrator-only and both take multipart/form-data with a package file part plus these text parts: packageId, version, displayName, category, manifestJson, sourceCode, and for install signature. Missing values are filled in: the package id falls back to the uploaded file's base name lower-cased, the version to 1.0.0, the display name to the package id, the category to Utility, the manifest to {} and the source to the literal placeholder ZIP Extracted Binary.

Two things the write path does not do

The stored version's capability list is hard-coded to ["logging"] on both routes, whatever your manifest declares — the manifest's own capabilities array is what the runtime reads, but the package row does not reflect it. And the uploaded package file is only used for its name: nothing unzips it, and nothing extracts an assembly from it. The executor that runs is the sourceCode text. A genuinely pre-compiled package belongs in the watch folder, not in an install request.

Signing

Signatures are Ed25519 over a SHA-256 digest of a canonical serialization of the package id, version, display name, category, manifest JSON, source and capability list. Both keys are base64 and the private key must decode to exactly 32 bytes; anything else fails the publish with a 500 naming the setting. Verification tries every key in Security__PackageSigning__TrustedPublicKeys in turn, so distributing a package to colleagues means giving them your public key to add to that list.

Because the digest covers the manifest and the source, re-signing is required after any edit — a signature does not survive a "small fix" to the YAML.

Binary packages and the watch folder

The third route into the catalog needs no API call at all. A hosted watcher scans a folder for assemblies and registers what it finds.

SettingDefaultWhat lives there
NodeRuntime__WatchPath <app folder>/nodes Binary node packages. Scanned recursively for *.dll. Created if missing.
NodeRuntime__PluginsPath <app folder>/plugins Host service plugins — a different mechanism entirely. These contribute an external-signal provider, editor option loaders, workflow import providers and background loops. They are loaded once at startup into real dependency injection and are never hot-reloaded.
NodeRuntime__DevMode on in Development Whether the watch folder is watched after the initial scan.

Each assembly needs a companion manifest.json in the same folder. Without one the DLL is skipped with a warning and the node never appears — the most common reason a binary package seems to be ignored. One folder per package, holding the assembly and its manifest, is the layout that works.

Loading reads both files with a short retry loop, because a build system may still hold the file open, then deserializes the manifest and registers the executor under its id and version in a collectible load context. A malformed manifest, an assembly with no INodeExecutor, or a type that cannot be instantiated is logged as an error and skipped; nothing fails the startup.

The initial scan always runs

Loading packages that are present at boot is not a development feature and is not gated by NodeRuntime__DevMode. The setting controls only whether a file-system watcher keeps running afterwards. A production instance therefore picks up everything in the watch folder at startup with hot-reload off, which is the intended arrangement.

Leave hot-reload off in production

With NodeRuntime__DevMode on, any write under the watch folder re-registers the package and unloads the previous assembly context — while runs may be executing code from it. It is also an unauthenticated code-loading path: anyone who can write a file into that folder gets their code executed in the Knotarium process, with no signature check anywhere in this route. Set it explicitly to false rather than relying on the environment being Production, and treat write access to the watch folder as equivalent to administrator access.

Versions on disk

The registry keys on id and version, so two versions of the same package can be loaded at once. Execution picks the highest, ordered as a .NET version when both parse and ordinally when they do not. Since a version such as 1.2.0-rc.1 does not parse, mixing plain and pre-release versions in the same folder gives you text ordering — where 1.2.0-rc.1 sorts after 1.2.0. Keep one version per folder unless you have a reason not to.
