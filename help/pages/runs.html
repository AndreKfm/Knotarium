Runs and the inspector

The Execution Visualizer is where a run stops being an abstraction. It shows the same graph you drew, coloured by what actually happened, beside a timeline of every journal entry the run produced — and it lets you step backwards through the run, re-run it from any node, and act on nodes that stopped and asked for a decision. It is the debugger, not just a log viewer.

Opening a run

The visualizer opens from several places: the Execution Visualizer entry in the header once a run is selected, a run in the dashboard history, the Dead Letter list, or automatically when you fire a device signal from the editor. The screen is split: the graph fills the left, and a resizable sidebar on the right carries the run's state and timeline. Drag the divider to widen the sidebar; the width is remembered.

The header above the graph shows the workflow name, a shortened run identifier, the run's status, and — when this run is a replay — a pill naming the source run and the node it resumed from, which navigates back to that run when clicked.

The graph shown is the version that ran

The visualizer loads the exact published version the run executed, not the current draft. A run from three versions ago renders with the nodes and wiring it actually had. This is why the graph in a run sometimes does not match what you see in the editor — and why that difference is information rather than a bug.

The live graph

Each node carries the status it reached: pending, running, completed, failed, waiting or skipped. A running node pulses. The canvas is pan-and-zoom with the usual controls in the bottom-right, and it frames the whole graph once the nodes have been measured, so a run opens showing everything rather than a corner of it.

Nodes can be dragged out of the way for legibility, but nothing here edits the workflow: wiring is disabled, and position changes are not saved. Status only ever moves forwards — a late-arriving event cannot pull a node that already completed back to running — so the picture does not flicker while updates stream in.

On a device-event run, the block that produced the signal is painted as Triggered rather than executed, and once the run is finished the branches this particular signal did not fire are painted Skipped instead of leaving a misleading trail of pending nodes.

Live updates

The run streams over server-sent events. The visualizer subscribes to the run's event stream and reacts to workflow start, node start, node completion, node failure, node resumption, suspension, and workflow completion or failure. Each event appends its journal entry to the timeline and advances the corresponding node's colour; the full run state is then refetched so the variables panel and per-node inputs and outputs stay in step.

The stream is not a poll. Catch-up entries are read from the stored journal when you connect — including resuming from a last-seen event — and the live tail is pushed as it is written, with duplicates removed across the join. Opening a run that finished last week therefore shows the complete history immediately, and opening one that is still going shows it filling in.

There is a global cap on live subscribers. When it is reached the stream is refused with HTTP 503 rather than accepting an unbounded connection; retrying shortly afterwards is the correct response. The Replay Logs button in the header re-reads the journal and the run state on demand, which is the manual fallback when a stream was interrupted.

The visualizer also follows automatic runs. While you have a run open, it watches for a newer scheduled or device-event run of the same workflow and moves you to it when one appears. Manual and webhook runs are deliberately not followed — you started those, so you decide where to look.

The sidebar

Evaluated Globals

The top panel lists the run's global variables and their current values, or reports that no state variables have been mutated yet. Values that look like secrets are masked before the run is handed to the browser; the full value stays in the database for replay and debugging, but a runtime-fetched token is never rendered here.

Schedule Controls

Below that, every scheduler node in the workflow appears as a card with its identifier, an Active or Inactive badge, the next fire time in local format, and its cron expression and time zone. Each card has a Fire now button that starts a run immediately without disturbing the schedule's own next occurrence. A workflow with no scheduler nodes says so.

Manual Actions

When a node is stopped awaiting a decision, a red-tinted panel appears above the timeline listing each such node with the reason. See Manual decisions below.

Execution Timeline

The timeline is the heart of the sidebar. Its header counts the nodes and the total elapsed time and carries the run's overall status. Directly beneath it, a coloured banner names the trigger: cyan AUTO for a schedule, with the cron expression and next fire time; emerald EVENT or ACTION for a device signal; violet MANUAL otherwise.

Each executed node is one group in the timeline, connected by a vertical rail whose colour follows the status of the steps on either side. A collapsed group shows its title, its status chip, the wall-clock time it started, the offset from the start of the run, and a one-line summary of its result. Nodes inlined from a sub-flow are tagged SUBFLOW, and a scheduler node carries the same trigger pill as the banner.

Clicking a group expands it. Inside are the individual journal entries with their own timestamps and a short event tag — STARTED, DONE, FAILED, WAITING, RETRY or MANUAL — followed by the message. Long failure messages are clamped to two lines in the entry list, because a compiler dump otherwise turns the row into a wall of text; the complete text is always available in the box below.

That box is the node's payload. A simple result is titled Output and rendered field by field. A failure whose payload is nothing but an error is titled Error and tinted red instead, so the eye lands on the cause rather than hunting for it among labels. Entries carrying a larger payload get their own collapsible View payload disclosure.

Failed groups are expanded automatically. Collapsing one is remembered for as long as you stay on that run, and opening a different run starts from a clean slate.

Child runs

Some nodes start runs of their own, and the timeline links to them rather than inlining them. An AI Agent group renders its per-iteration tool-call trail — each turn, each call, whether it succeeded, and the short identifier of the child run it produced. A failed run that was caught by the global error workflow gains a link to the handler run, both inside the failed group and as a button under the timeline.

Hiding skipped branches

A device-event run fans out across every wired pin, but only one of them fires; the rest appear as skipped noise. On those runs the timeline hides skipped groups by default and offers a Show N skipped branches toggle at the bottom of the list. The filter is scoped to device-event runs on purpose — a meaningful skip elsewhere, such as an operator's Skip decision or a condition's untaken branch, always stays visible.

The Time Travel inspector

Step Through in the header opens a panel across the bottom of the graph that walks the run one node at a time, in execution order. A run that is already finished when you open it starts in step mode automatically, positioned on the first failed step when there is one; a run that is still in progress stays in the live view, and once you toggle the mode by hand your choice sticks for that run.

The panel header carries previous and next buttons with a Step n / total counter, the node's title and status, the time it started, how long it ran, and its offset from the start of the run. Below that is a scrubber with one dot per node, coloured by status and dimmed for steps you have not reached yet — click any dot to jump straight there. The arrow keys step backwards and forwards and Esc closes the panel.

Three columns fill the body of the panel for the selected step:

ColumnShowsWhen empty
InputsThe values this node received."No inputs"
Variables at this stepThe global-variable snapshot taken immediately before this node ran."No variables set", or "Not captured" for a run whose snapshot predates this feature.
OutputsThe values this node produced."No outputs"

If the step failed, its error message runs along the bottom of the panel.

Stepping drives all three surfaces at once. The current node gets a light-blue ring on the canvas, every node reached only after it fades back to roughly a third opacity so the graph shows where you are in time rather than merely that everything ran, and the matching timeline row is highlighted. Clicking a timeline row moves the step, and clicking a scrubber dot moves the highlight — the three views never disagree.

The variables column is what makes this a debugger

"Variables at this step" is not the run's final state; it is the snapshot captured the instant the node started. Stepping backwards through it answers the question a log cannot: not what the value was at the end, but which node changed it and what it had been before.

Replaying from a node

Right-click any node on the graph to open the Re-run from here dialog. A replay creates a brand-new run that inherits the source run's upstream node states — their historical inputs and outputs are reused as-is — and re-executes the node you picked together with everything downstream of it. The variables it starts from are the exact snapshot taken when that node originally began. The source run is never modified.

The dialog offers two choices:

  • Target version. Defaults to This run's version (original), so a replay reproduces the original conditions. Any published version can be selected instead, which is how you check whether a fix actually fixes the failure — replay the failed run against the new version and see if it gets past the same node.
  • Mock side effects. When ticked, non-idempotent nodes replay their original recorded output instead of firing for real. Leave it off to genuinely re-execute; tick it when the downstream path sends mail, posts payments or otherwise cannot be repeated safely.

If the replay would re-execute non-idempotent nodes for real, the dialog does not jump straight to the new run: it stops on a confirmation listing exactly which nodes will fire again, with Open replay run and Close. When there is nothing to warn about, it navigates to the new run immediately.

A replay is refused with an explanatory error when the chosen node does not exist in the target version, when the target version fails to compile, or when the source run has no version recorded to replay against. The new run is stamped with the origin replay and keeps a link back to the source run and the node it started from — that is the pill in the run header.

Manual decisions

A node can end up in a state where the engine refuses to guess. The usual cause is a crash or restart in the middle of a non-idempotent side effect: the journal records that the effect was attempted but never records its completion, so on recovery the engine cannot know whether the payment went out. Rather than risk a duplicate, it parks the node with the message "Execution interrupted during a non-idempotent side effect. Manual decision required." and suspends the run.

Those nodes appear in the Manual Actions panel with three buttons:

DecisionEffectChoose it when
Retry Node Clears the node's error and outputs, closes the interrupted attempt in the journal, and executes the node again. The run continues from there. You have confirmed the effect did not happen, or repeating it is harmless.
Skip Node Marks the node completed with a manualDecision of Skip, and schedules everything downstream of it. You have confirmed the effect did happen and the run should carry on as though the node succeeded.
Fail Run Marks the node failed, recording your reason as the error message. The run should not continue and you want the failure recorded, alerted on and routed to the error workflow.

Each decision is journaled with the reason and the identifier of the attempt it resolves. That attempt identifier is also sent with the request, so a decision made against a stale view of the run is ignored rather than applied to a different attempt. A node that has already completed or failed accepts no decision at all, and a node that is not actually awaiting one is refused.

The file-access remediation card

File nodes run against a path allow-list, so the most common first failure of a file-touching workflow is a policy denial rather than a missing file. When the visualizer recognises one — the error says the file access was denied and names the attempted path — it renders an amber How to fix card immediately after the failure, so the reading order is cause then cure.

The card's title names the specific problem rather than repeating the generic message:

TitleMeaning
Path is outside permitted directoriesNothing in the policy covers this location.
Path is granted read-onlyThe location is granted, but not for writing.
Path is not granted for readingThe location is granted, but not for reading.
No paths are permitted yetThe policy is empty, so everything is denied by default.
Path is not permittedThe fallback when the denial does not match any of the above.

Below the title the card shows the exact directory that needs granting — the parent of the attempted path, with drive roots handled correctly — and adapts its wording to the node that failed, saying "read it here" for a file read, "write here" for a file write and "reach it here" otherwise. Two actions follow. Grant access in File Access settings → stores the path and navigates to Settings › File Access with it already filled in, so you do not retype it. Copy path puts it on the clipboard and confirms with "Copied" — useful when the grant belongs on a different machine, or when you would rather adjust the workflow than widen the policy.
