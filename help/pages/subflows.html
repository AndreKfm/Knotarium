Sub-flows and grouping

A sub-flow is an ordinary workflow called as a single step from another one. It is how a chain of nodes that appears in four places becomes one node in four places. This page covers the Sub-flow node, the typed interface a child declares, how data crosses the boundary, the "Extract selection" command and the fairly strict rules it enforces, and why grouping is a different thing entirely.

What a sub-flow actually is

This is worth understanding before anything else, because it explains most of the behaviour that follows. A sub-flow is not a separate run. When the workflow is compiled, the child's nodes are copied into the parent's execution plan, the Sub-flow node itself disappears, and the wires that led into it are redirected to the child's Start node while the wires that led out of it come from the child's End node.

The consequences are concrete. There is no child execution to inspect separately — the child's steps appear in the parent's run, with ids like my-subflow-node/step-2. There is no "run asynchronously" or "wait for completion" option, because there is nothing to wait for. A failing step inside a sub-flow is simply a failing step in the parent's run, handled by that node's own retry and recovery settings; there is no "continue on child error" switch.

The child is read fresh, not pinned

The compiler resolves a Sub-flow node against the child workflow's current saved definition. There is no version pinning, and a published parent version stores its own nodes and edges rather than a frozen copy of the child. Because the plan is compiled when a run starts, editing a child changes the behaviour of every workflow that calls it, immediately, without republishing any of them. That is often what you want from a shared building block — but it means a change to a shared sub-flow is a change to every caller.

Adding a Sub-flow node

Drop a Subflow node (category Control) onto the canvas. It has one input and a single result output. Its property panel offers a searchable list of every other workflow — the workflow you are editing is excluded, since a node cannot call its own graph — and a Create new subflow button.

Creating one mints a workflow named Subflow followed by a short identifier, containing a Start node wired to an End node, saves it, publishes it and links it to the node in one step. That is the quickest way to start, because a child that has never been saved cannot be resolved and produces a not-found error.

If a node references a workflow that no longer exists, the panel says so and asks you to pick an existing one. Publishing in that state fails with a compilation error naming the missing workflow.

Declaring the interface

A sub-flow's inputs and outputs are declared inside the child, on its Start and End nodes:

  • Select the child's Start node to edit Subflow inputs (from caller) — the local variables this sub-flow expects to be given.
  • Select its End node to edit Subflow outputs (to caller) — the local variables it produces and hands back.

Each row is a name and a type, chosen from string, number, boolean and object. While you edit the child, its declared locals appear in the Workflow variables panel so they can be referenced and dragged like any other variable.

Until a child declares something, its caller has nothing to bind. The Sub-flow node's property panel says exactly that: This subflow has no declared inputs or outputs yet. Double-click the node to open it, then declare them on its Start (inputs) and End (outputs) nodes.

Binding on the caller

The Sub-flow node card shows two folders, Inputs (global → local) and Outputs (local → global), with one slot per declared local of the child. Each slot can be filled in two ways: drag a variable pill from the Workflow variables panel onto it, or type directly into the inline field.

An input slot accepts either a bound variable or a literal value or expression. An output slot takes the name of a caller variable to write the result into; when that name is not one the caller already knows, the slot is tagged NEW so it is obvious you are creating a variable rather than filling an existing one.

The property inspector mirrors the same bindings as a read-only summary, one line per row, so the mapping is legible without zooming into the node. Bindings that no longer correspond to a declared local are pruned automatically once the child declares an interface, which keeps a node from carrying stale rows after the child's contract changes.

How data crosses the boundary

Data does not travel through the ports. It travels through variables, and the two maps you fill in are the only bridge.

Every call site gets its own prefix, so calling the same sub-flow twice in one workflow — or nesting it — cannot make the two invocations trample each other's variables. Any Set Variable or Set Variables node inside the child has its target name rewritten with that prefix at compile time.

The two sides of the map are not symmetric, and it catches people out:

  • An input's value is an expression evaluated in the caller's scope, so {{ $variables.orderId }}, a literal, or anything else valid works.
  • An output's target is a plain caller variable name, not an expression. Typing {{ $variables.verdict }} there creates a caller variable whose name is that whole string.

Rows with an empty name on either side are skipped silently rather than reported, so a half-filled slot simply does nothing.

Drilling into a sub-flow

Double-clicking a Sub-flow node — or clicking the open icon on its card — opens the child on its own canvas. Before navigating, the parent draft is saved, so unsaved edits including the Sub-flow node's own binding are not lost. If the node has no target chosen yet, the status bar says Pick a workflow for this subflow before opening it.

While you are inside a child, a breadcrumb pill floats at the top of the canvas reading Back to parent and · inside subflow (depth N). Nesting is allowed, and the depth counts how many levels down you are.

Leaving a sub-flow saves and publishes it

Both the breadcrumb and the editor's own Back button run the same action while a sub-flow is open: Save & Publish the child, then return to the parent. You do not get the usual unsaved-changes dialog, because leaving a child without persisting it would leave the caller bound to an interface that does not exist. If publishing the child fails — an incomplete condition, a compilation error — the failure surfaces the same way as any other publish failure.

The breadcrumb trail is kept in memory only. Reloading the browser lands you on the child workflow with no trail back to the parent, so use the dashboard to return.

The constraints on a sub-flow target

Two structural rules are enforced at compile time, and both block publishing:

CodeCause
ERR_MISSING_SUBFLOW_IDThe node has no target workflow chosen.
ERR_SUBFLOW_NOT_FOUNDThe referenced workflow does not exist.
ERR_SUBFLOW_MISSING_STARTThe child contains no node of type start.
ERR_SUBFLOW_MISSING_ENDThe child contains no node of type end.
ERR_RECURSIVE_SUBFLOWThe call chain returns to a workflow already on the path. The message prints the whole path.

The rule is contains a Start node and contains an End node — not "begins with one". Node type matching is case-insensitive, and if the child happens to have more than one Start node, the compiler picks the first it finds and attaches the input map to that one, which is a good reason to keep exactly one.

A child containing a trigger is not rejected

Nothing stops you pointing a Sub-flow node at a workflow that also has a webhook, schedule or poller on it. Those trigger nodes are inlined along with everything else and exempted from the usual "a trigger cannot have incoming connections" check. The result compiles, but what it does at run time is rarely what anyone intended. Keep a workflow that is used as a sub-flow to a plain Start-to-End shape.

The stricter rule you may have seen — that a workflow must begin with a plain Start node, and webhook, schedule, poll or error-triggered workflows cannot be used — applies to AI Agent tool workflows, not to sub-flows. The two features look similar and are validated in completely different places.

Nesting has no depth limit. The only structural guard is the recursion check, and it uses the call path rather than a counter, so two different branches calling the same shared sub-flow are fine — only a genuine cycle is an error.

Extract selection to a sub-flow

Extract appears in the canvas layout toolbar as soon as at least one node is selected. It lifts the selection into a brand-new sub-flow, creates and publishes that workflow, and replaces the selection with a single call node wired so the parent behaves exactly as before. You are prompted for a name; the default is Extracted subflow.

It refuses far more often than it succeeds, and the refusals are the useful part. The selection must be a region with one way in and one way out, because that is all a single call node can represent. The exact messages are:

RefusalWhat to do
A trigger node can't move into a subflow Leave the trigger where it is and select the nodes after it. A sub-flow is invoked, not triggered.
The selection has more than one entry point External steps must enter the region at a single node.
The selection has more than one exit point The region must leave to external steps from a single node.
The selected nodes aren't all connected Each region must be one connected chunk.
A selected node reads another step's output from outside the selection Include that step, or replace the $node reference with a variable.
A kept node reads a selected step's output Same problem in reverse. Sub-flow outputs travel by variable, not by node output.

Those last two exist because $node references are tied to node identity, and moving a node into a child changes its identity. Rather than silently breaking the reference, the extraction refuses.

When it succeeds, the variable interface is worked out for you. Any variable read inside the region but not written inside it becomes a declared input — this is also how the ambient signal context survives the move. Any variable written inside and read by a node left behind becomes a declared output. Variables written inside and used nowhere outside are simply left inside.

Two node types count as writers, and both are detected: Set Variable, which contributes its single target name, and Set Variables, which contributes the name from every row. A keyed write contributes its head container rather than the full path, so a region writing order.id declares order as the output. Nothing else in the selection is treated as writing a variable, which is why a value produced by a node but never stored in one has to leave the region as a node output — and that, in turn, is what the last two refusals above are about.

Extracting several identical chains at once

Selecting more than one region at a time does something more interesting. If the regions are structurally identical — the same sequence of node types, each a simple chain with no internal branching — their properties are compared leaf by leaf, and every value that differs between them is promoted to a sub-flow parameter. One parametrised sub-flow is created, and each region is replaced by its own call node binding that region's own values.

Parameter names are inferred from the property they came from, falling back to param1, param2 and so on for generic keys. The status bar reports what happened, for example Extracted into subflow "Notify contact" with 2 parameters and replaced 3 chains. The refusals for this mode are that each region must be a simple chain, and that the chains must share the same node type sequence.

The child is published; the parent is not

Extraction saves and publishes the new child workflow immediately, but the parent is only changed on your canvas. The status message ends with Save & Publish to keep the change. Leaving without saving discards the parent's rewrite and leaves the new child workflow behind as an orphan.

Grouping is not a sub-flow

The Group button next to Extract does something entirely different. A group is a coloured frame drawn around two or more selected nodes: an editor-only annotation that can be labelled, tinted, collapsed to a chip and moved as a unit. It changes nothing about execution — the nodes inside it run exactly as they did before, keep their own wires, and are compiled individually.

Use a group when a stretch of a large graph needs a name so it can be read. Use a sub-flow when the same steps are needed in more than one place, or when the graph is genuinely too big for one canvas. Group membership and the group's own label, colour and collapsed state are saved with the workflow, so a collapsed group stays collapsed for the next person who opens it. Full behaviour is in The canvas editor.
