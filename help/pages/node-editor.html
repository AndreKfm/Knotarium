The node editor

Knotarium ships a small authoring IDE for node packages, reached from Node Editor in the top navigation. It gives you a YAML manifest editor, a C# executor editor, a live rendering of the property form your manifest generates, and a sandboxed test runner whose result is a hard precondition for publishing. This page describes what each surface actually does — including several places where the editor is narrower than the manifest format it edits.

Read the package format alongside this page

The node editor writes a subset of the node package manifest. The full schema — outputs, typed inputs, capabilities, retry policy, the secondary palette flag — is on Custom node packages, and several fields you can legitimately write in a manifest do not survive a round trip through this editor. The limitation is spelled out under What Publish actually sends below.

Opening it

The editor is a full-screen view, not a modal: choosing Node Editor replaces the canvas, and the Back button in its header returns you to whatever view you came from. There is no address you can bookmark — the view lives in React state like every other screen.

Testing and publishing are administrator-only actions. Both POST /api/node-editor/test and POST /api/node-packages/publish check the caller's admin role before doing anything, because both end in compiling and running C# on the host. When sign-in is disabled entirely the check is a no-op, which is one more reason an instance without authentication belongs on loopback only.

The package list

The left rail lists everything GET /api/node-packages returns, which is the whole merged catalog rather than just your own work: the built-in nodes compiled into the product, any binary packages loaded from the watch folder on disk, and the custom packages stored in the database. Where two of those share an id you see one row — the merge resolves duplicates with custom beating binary beating built-in.

Each row carries four facts: the display name, the version of the newest version record, the package id in small type, and a tier pill reading declarative or compiled. Clicking a row loads its newest version into the three editors.

The list does not mark built-ins as locked

Nothing in the list is read-only, and there is no "Locked" badge on a package row — the only Locked marker in the editor sits on the Executor.cs tab, and it means "this manifest is declarative", not "this package is a built-in". You can select a built-in node, edit its manifest and publish it. That does not modify the built-in: it writes a database package with the same id, and because custom packages win the catalog merge, your copy shadows the original everywhere — palette, compiler and runtime. Use a fresh id unless shadowing is exactly what you intend.

The tier pill is computed with a case-sensitive comparison against the literal string compiled. The catalog serializes a built-in or binary package's tier from the C# enum, which produces "Compiled" with a capital C, so a compiled built-in shows as declarative in this list and its Executor.cs tab stays locked. The same rule applies to your own drafts: write tier: compiled in lower case or the editor will treat the package as declarative even though the backend, which parses the tier case-insensitively, will happily compile it.

Creating a package

The + button beside the Node Packages heading opens the Create Node Package dialog. It is a scaffolder: it produces a draft from one of the built-in templates and nothing else.

FieldRequiredEffect
Package id yes Lower-cased and with runs of whitespace replaced by dots, so System Alert becomes system.alert. Rejected with a browser alert if a package with the resulting id is already in the list.
Display name yes The palette label. Substituted into the template's displayName.
Category defaults to Utility One of Utility, Network, Data, Logic, Trigger — the five palette sections the dialog offers. The manifest format itself accepts any string; the dialog just does not let you type one.
Tier level defaults to Declarative Declarative (Tier 1) scaffolds a manifest only. Compiled C# (Tier 2) scaffolds a manifest plus a working INodeExecutor implementation and unlocks the executor editor.

Pressing Create package inserts the draft at the top of the list with the placeholder version 1.0.0-draft and selects it. Nothing has been sent to the server at this point — the draft exists only in the browser tab. Reloading the page before you publish loses it, and so does navigating away and back, because the list is re-fetched from the API on mount.

The three editors

The centre pane is a Monaco editor with three tabs. All three share the same configuration: the dark theme, no minimap, and a monospaced face at 13 px.

  • manifest.yaml — YAML mode. The package definition. This is the tab that drives everything else on screen.
  • Executor.cs — C# mode. Enabled only while the parsed manifest's tier is compiled; otherwise it is disabled, tagged Locked, and its tooltip reads "Only enabled for Compiled (Tier 2) packages".
  • tests/cases.yaml — YAML mode. The cases the sandbox runs.

There is no file system behind these names. The three buffers are held in component state and submitted together as three strings when you press Run Tests.

What the templates start you with

A declarative draft opens with a manifest declaring one string parameter named inputMessage, the logging capability, and success and error outputs. A compiled draft adds the http capability, renames the parameter to targetUrl, and fills Executor.cs with a complete INodeExecutor that reads the parameter, logs, and returns a NodeResult on the success output. Both templates set defaultTimeoutSeconds: 30.

How parse errors surface

The manifest is re-parsed on every keystroke, and the result is not shown in the editor gutter. Monaco here has no schema and no diagnostics — the error appears in the Live UI Preview panel on the right, which replaces the preview with a red YAML Parse Error box containing the parser's own message, including the line and column. If the document parses but is not a mapping — a bare list, or a single scalar — the message is instead "Parsed content is not a valid YAML object".

A broken manifest also locks the executor tab

While the manifest fails to parse there is no parsed tier, so the tier test falls through to "not compiled" and the Executor.cs tab greys out mid-edit. It is disconcerting the first time; it is not data loss. The executor buffer is untouched and the tab returns the moment the manifest parses again with tier: compiled.

The Live UI Preview

The right-hand panel answers the question a manifest author actually has: what will someone configuring this node see? It renders two things.

At the top, a small card imitating the canvas node: the display name, the category, and a dot coloured by tier. Below it, the real property form — the same ManifestForm component the canvas properties panel uses, given your parsed parameters. It is not a mock-up of the form; a field that renders wrongly here renders wrongly on the canvas too.

Because the preview passes only id, displayName and parameters into the form, it shows the field list and nothing else: no output sockets, no input sockets, no capability summary. Parameter types the form knows how to render include string (an expression-aware field that becomes multi-line for long or multi-line values), number, boolean (a toggle), enum (a select populated from values), credentialRef and notificationChannelRef (selects populated by live API calls), code (an embedded Monaco with an expand-and-test button), keyValue, and the dynamic loader types. The editor's own manifest parser, however, only recognises five of those — see the next section.

Values you type into the preview form are kept, and the same store backs the Mock Inputs tab of the test runner, so filling in the form is a reasonable way to set up a test case's inputs by hand.

The preview understands five parameter types

The editor's YAML reader keeps a parameter only if its type is one of string, number, boolean, enum or credentialRef. A parameter of any other type — including perfectly valid ones such as code or keyValue — is silently dropped from the parsed manifest. It vanishes from the preview form and from the mock-input grid, with no error anywhere. The manifest text is unaffected, but everything the editor derives from it is now incomplete.

The sandboxed test runner

The bottom panel is the test runner. It has two tabs and one button.

Mock inputs lists one text box per parameter the editor parsed, labelled with the parameter name and type, seeded from the parameter's default. With no parsed parameters it says so. Run console shows the last result: a pass/fail banner, one line per case, and the sandbox log journal, colour-coded on the [ERROR], [RUNNER] and [EXECUTOR] prefixes.

Run Tests switches to the console, waits about 1.2 seconds — a deliberate pause in the interface, not work being done — and then posts the package id and all three buffers to POST /api/node-editor/test. The package id sent is the selected package's id, not the id: in your manifest, so renaming a package by editing the manifest does not rename what is tested.

What the sandbox does with them

  1. Rejects the request outright if the package id or the manifest is empty.
  2. Parses the manifest with a YAML deserializer that ignores unmatched properties. A key it does not recognise is discarded without comment.
  3. If the tier is anything other than declarative, checks the code execution capability. It is off by default; the failure message points at Settings › Capabilities. The check is on "not declarative" rather than "is compiled", so an unknown future tier fails closed.
  4. Parses the test cases. Both a { cases: [...] } document and a bare list of cases are accepted. An empty file produces one default case rather than nothing to run.
  5. For a compiled draft, runs the banned-API analyzer, then compiles with Roslyn into memory, loads the assembly into a throwaway collectible context, and finds the first concrete type implementing INodeExecutor. A missing implementation is reported as an "Executor Discovery" failure.
  6. Runs every case against a recording context whose logger, HTTP client, credential accessor and workflow state are inert fakes. The whole run is bounded at 15 seconds; exceeding it aborts with a "Timeout" case.
  7. Unloads the assembly context.

A case fails for four distinct reasons, and the message tells you which: the executor returned null; it invoked a capability the manifest never declared; the result came out on a different output than expectedOutput named; or it threw, in which case the exception message is the case message.

Undeclared capability use is the interesting failure

The recording context notes every capability the draft actually touches — writing a log line records logging, sending a request records http, resolving a secret records credentials — and compares that set case-insensitively against your manifest's capabilities list. Code that reaches for something it did not declare fails the case with the exact capability named. This is the mechanism that keeps a package's declared privileges honest, and it is worth running even for a declarative package.

Which C# the analyzer refuses

Before compilation, a semantic analyzer rejects any use of these namespaces: System.IO, System.Diagnostics, System.Reflection.Emit, System.Net.Sockets, System.Runtime.InteropServices, System.Runtime.Loader and Microsoft.Win32. It resolves symbols rather than matching text, so aliasing a namespace or changing its casing does not slip past it. It also flags mutable static state. Sources over 500,000 characters are refused unread.

The compilation itself references a deliberately small set of assemblies: the core library, the Knotarium contracts, the collectible load context, HttpClient, the logging abstractions, System.Text.Json, collections, tasks and URIs. Anything outside that set is a compile error rather than a runtime surprise. If your source does not look like a class implementing INodeExecutor, the compiler wraps it as a bare script body inside a generated executor with an Input.Get<T>(name) helper.

This runs in the main process

The banned-API analyzer is authoring assistance, not a containment boundary, and the draft test path compiles and executes your C# in the Knotarium process — not in the worker-process sandbox that Security__Sandbox__Mode governs at run time. Cancellation is cooperative, so a CPU-bound loop that never observes the cancellation token will run past the 15-second limit and can only be stopped by restarting the application. Do not paste untrusted code into this editor to "see what it does".

Publishing

Publish Node refuses before it sends anything if the current session has no passing test result, with the message "Mandatory Gate Violated". That client-side check is courtesy; the server enforces the same rule independently. On a successful test run the backend records a pass keyed by package id and version, and the publish endpoint refuses with a 400 unless a matching pass exists.

The version half of that key is read out of your manifest text by the server, which scans for the first line whose trimmed text begins with version: and takes the rest of it. Keep version at the top level of the document and near the top of the file; a version: nested inside another block earlier in the file would be picked up instead.

The gate is in memory and is not persisted

Passing results live in a dictionary in the running process. Restarting Knotarium clears them, and you must re-run the tests before you can publish again. Changing the manifest's version also invalidates the gate, because the key includes the version — bump the version and press Publish without re-testing and you get the gate error, which reads like a bug and is not one.

Signing is mandatory on publish

Publishing signs the package with the host's private key, so Security__PackageSigning__HostPrivateKeyBase64 must be configured and must decode to exactly 32 bytes. If it is missing, not valid base64, or the wrong length, the endpoint answers 500 with a message naming the setting. This is the single most common reason a first publish fails on a fresh instance — the key is optional for everything else, but not for this. See the Configuration reference.

What Publish actually sends

This is the sharpest edge in the editor, and it is worth stating plainly. The manifest that gets stored is not your YAML. It is a JSON rebuild of the parsed manifest, and the parser keeps only six things:

  • id, displayName, category, version
  • tier, normalised to compiled or declarative
  • parameters, reduced to name, type and default per entry
Outputs and capabilities do not survive the round trip

outputs, inputs, capabilities, sideEffectKind, recoveryMode, defaultTimeoutSeconds, retryPolicy, secondary, description, and the required / expression / values flags on each parameter are all dropped before the manifest is stored. A node published from this editor therefore reaches the palette with no declared output sockets and no declared capabilities, whatever your YAML said — and the stored version row is always tagged with the single capability logging regardless. Selecting the package again re-serializes that reduced manifest back into the YAML editor, so the detail is gone from your buffer too.

For anything beyond a quick declarative experiment, author the manifest as JSON and install it through POST /api/node-packages/install, or ship it as a binary package in the watch folder. Both paths store the manifest verbatim.

On success the status line in the runner header confirms the package and version, and the package list is re-fetched so the newly stored version appears. On failure the same line shows the backend's message.

A workable order of operations

  1. Create the package with a fresh, dotted, lower-case id.
  2. Write the manifest. Watch the preview panel — it is your only syntax check.
  3. For a compiled package, enable code execution under Settings › Capabilities first, or the test run fails before it compiles anything.
  4. Write cases that assert an expectedOutput, not just that nothing threw.
  5. Run the tests. Read the log journal even when everything is green — it lists the capabilities the sandbox saw you declare.
  6. Publish, then confirm the node appears in the canvas palette under the category you named.
