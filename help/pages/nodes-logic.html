Logic nodes

The seven nodes that decide what runs, when, and how many times. They share a manifest category — Control — which the palette shows as Logic. Two of them are containers that hold a body subgraph rather than passing work along a wire, and that distinction changes how you draw the graph.

Branch ports and container ports

Most nodes hand the run to whatever is wired downstream. A branch node instead picks exactly one of its ports and suppresses every edge leaving the others. Only seven node types route this way, and four of them are on this page: Condition, Switch, For Loop and Parallel For-Each. That restriction is deliberate — a node such as HTTP Request has several data sockets that must all deliver, so routing has to be opt-in rather than triggered by any node that happens to name a port.

Because the chosen port wins outright, a branch node's explicit choice is not second-guessed by the failure-edge rule that applies elsewhere. An ordinary node skips its error and failure handles when it succeeds, but a branch node that selects a port spelled error — an AI Router carrying a category by that name, say — follows it exactly as it would any other label.

Container nodes — For Loop and Parallel For-Each — are drawn as a resizable box you drop other nodes into, and they have three wiring points rather than two:

  • start is an output. It fires once per iteration and must be wired to the first node of the body.
  • end is an input, and the loop-back. The last node of the body wires into it, which both closes the iteration and supplies that iteration's result. It appears in the manifest as a parameter, but the properties panel always hides it, because it is wired with an edge and never typed in.
  • success is the exit. It fires once, after the last iteration, and is where the rest of the workflow continues.

Wiring the body to success instead of start is the classic mistake: the loop completes immediately having done nothing, and the "body" runs exactly once afterwards.

Condition

condition · Control · timeout 10 · branch node

The workhorse of branching: evaluate a test and send the run down true or false. Reach for it for anything that is genuinely a yes-or-no question — an HTTP status worth continuing on, a field that must be present, a threshold being crossed.

Its properties panel is not a generic form. Selecting a Condition node replaces the parameter fields with a compact summary and an Edit logic launcher that opens a full-screen editor for building the test out of comparators, groups and negations. The four parameters below are what that editor persists; you do not normally type into them directly.

The logic parameter

logic holds the whole test as a JSON tree — the modern form, and the one the editor writes. It is versioned: a flat version 1 document is accepted and normalised into a version 2 tree in memory, so older workflows keep working without being rewritten on disk.

Comparators are named by short operator ids grouped into five families:

FamilyOperatorsArity
Comparisoneq, ne, gt, gte, lt, lteBinary
Textcontains, ncontains, starts, ends, regexBinary
Membershipin, ninBinary
Existenceempty, nempty, exists, nexistsUnary
Booleantrue, falseUnary

The tree is bounded, and the bounds are enforced when it is parsed rather than when it is drawn: at most 50 comparators, 50 children per group, 20 levels of depth and 200 nodes in total, with a literal capped at 10,000 characters, a reference at 2,000 and a regular expression at 512. Every violation is reported as invalid logic.

logic is deliberately not expression-enabled. The engine hands the tree over untouched so the node can resolve each operand itself and distinguish a reference that was not found from one that resolved to null. That distinction is the point: a missing reference is a configuration error and fails the node, rather than quietly evaluating false and sending the run down a path you did not intend.

The legacy operands

left, operator and right are the original single-comparison form, retained so a workflow authored before the logic editor still runs untouched. Precedence is strict: a usable logic value always wins; the legacy operands are consulted only when logic is absent, empty or whitespace. Opening the node in the logic editor and saving migrates it.

The legacy vocabulary is seven names — Equal, NotEqual, GreaterThan, LessThan, GreaterThanOrEqual, LessThanOrEqual, Contains — each mapped onto a modern operator id. A name outside that list is treated as corrupt data and fails the node rather than defaulting to equality. Unlike logic, left and right are expression-enabled, so they are resolved before the node sees them and their types are inferred from the resulting values.

A Condition with neither form configured routes false. That is the only remaining silent fallback, and the publish gate is what stops such a node from shipping.

ParameterTypeRequiredExprNotes
logicjson No— The comparator tree. Written by the logic editor. Takes precedence over the legacy operands.
leftstring No Yes Legacy left operand. Resolved before evaluation.
operatorstring No— Legacy operator name. An unknown name fails the node.
rightstring No Yes Legacy right operand. Ignored by unary operators.
PortTypeFires when
trueanyThe test evaluated true.
falseanyThe test evaluated false, or the node is entirely unconfigured.
An error is not a false

An unresolvable reference, an unknown operator or a malformed tree makes the node fail, carrying a bracketed error code plus the comparator and operand that caused it. Nothing ambiguous is routed to false. If you want "missing counts as false", say so explicitly with an exists or empty comparator.

Delay

delay · Control · timeout 60

Waits, then continues. Reach for it to pace a loop against a rate-limited API, to leave a remote system time to settle before polling it back, or to stagger a fan-out.

Two parameters express the same thing and only one is read. delayMs wins if it is present at all; duration is consulted only when it is absent, and is parsed as a time span such as 00:05:00. Neither has a default — an empty node waits zero milliseconds and continues immediately.

The threshold worth knowing is one second. A wait of 1000 milliseconds or more suspends the run: the engine schedules a timed resume and releases the worker, so a ten-minute delay in one workflow does not hold up every other workflow on the instance. Shorter waits simply block inline, because a suspend-and-resume round trip to the database costs more than the wait itself.

The manifest's 60-second timeout would otherwise cap the wait, so the engine raises the timeout for a Delay node to the configured duration plus two seconds. A deliberate wait can never trip a limit whose job is to catch a hung node.

ParameterTypeRequiredExprNotes
delayMsnumber No Yes Milliseconds to wait. Checked first; if present, duration is ignored entirely.
durationstring No Yes A time span, for example 00:00:30. Read only when delayMs is absent; an unparsable value silently becomes no wait at all.
PortTypeCarries
resultanyNothing of its own; the run simply continues.

Switch

switch · Control · timeout 10

A multi-way branch: compare one value against a list of case labels and take the matching branch, or default when nothing matches. The catalog registers it, the palette offers it and the compiler recognises it.

The branches come from the cases you type

Switch declares no fixed output ports. Each label in cases becomes its own output handle on the canvas, with default always present and always last — the same arrangement the AI Router uses for its categories. Add a case and a new handle appears to wire.

Matching is case-insensitive, so a value of PAID takes a branch labelled Paid. The branch is exclusive: only the matching edge continues, unlike most nodes, where every outgoing edge fires. Two labels differing only in capitalisation collapse into one branch, because only the first could ever be selected.

ParameterTypeRequiredExprNotes
valuestring Yes Yes The value to match.
casesstring Yes— Case labels, separated by commas, semicolons or newlines.
PortTypeFires when
defaultanyThe only declared port. No per-case ports exist.

For Loop

forLoop · Control · timeout 60 · container · branch node

Runs a body repeatedly, one pass at a time, in the order the items arrive. Reach for it when the iterations must not overlap — writing rows to a file, calling an API that will not tolerate concurrency, or accumulating into a variable where order matters. When the iterations are independent, Parallel For-Each is faster.

Loop state lives in the run's global variables under keys derived from the node's id, and the presence of the count key is what tells the loop it is on a later pass. That is why the end loop-back is a port and not a value you set: a stray value in an end field would once have made the very first pass look like a loop-back, skip initialisation and exit with zero iterations.

Each iteration emits its index and the current item on the start port, so the body can reference them. When the collection is exhausted the loop clears its own state and fires success once.

Modes

mode drives which other fields the properties panel shows, so the form changes as you change it. The manifest declares four values:

  • count — repeat a fixed number of times, taken from count. The body's item is the index.
  • foreach — iterate a collection from collection. A JSON array is parsed as one; a value that will not parse is split on commas and each piece trimmed, which makes a plain comma-separated string work without ceremony.
  • while — advertised as repeating while condition holds.
  • batch — advertised as iterating collection in chunks of batchSize.
Only count and foreach are implemented

The executor branches on count and treats every other value — including while and batch — as foreach. The condition and batchSize parameters are never read by anything. Selecting while therefore does not loop on a condition; it iterates whatever is in collection, which is usually empty, so the body never runs and the loop exits at once. It fails silently. Build a conditional loop as a foreach over a pre-computed collection, or as a Condition node wired back into the graph.

collectionstring No Yes What to iterate. Shown in foreach and batch modes.
countnumber No Yes How many passes. Shown in count mode. Absent means zero passes.
conditionstring No Yes Shown in while mode. Not read by the executor.

Parallel For-Each

parallelForEach · Control · timeout 300 · container · branch node

Runs the same body once per collection item, concurrently. Reach for it when the items are independent and the work is dominated by waiting — enriching a hundred records from an API, fetching a batch of documents, sending a set of notifications. On latency-bound work the difference against For Loop is not marginal.

Each item runs in its own in-memory mini-executor with a private copy of the global variables and its own node-state map, so iterations cannot interfere with one another. The consequence is that a body node writing a workflow variable writes it into that item's private copy, which is discarded when the item finishes. Accumulate through the results array instead. Only after every item has finished does the node commit its aggregate.

The per-item result is whatever the body sends back into the end input, exactly as with For Loop. The node then reports results (in item order), count and failedCount, and continues through success.

Bounds and failure

maxParallelism defaults to 8 and is clamped to between 1 and 64. continueOnError defaults to false. With it off, one failed item fails the whole node, reporting how many items failed and quoting the first error. With it on, every item is attempted and a failed one contributes an object carrying its error in place of a result — so a partial success is distinguishable from a clean one by inspecting failedCount.

Body nodes are timed individually: each body node's manifest timeout is clamped to between 1 and 600 seconds, and a body node declaring no timeout gets 30 seconds rather than the usual 5-second fallback.

What the body may not contain

The body must be wired to start and must not be empty; either mistake fails the node before any item runs, with a message saying which. It also may not contain a nested For Loop, Parallel For-Each or Join — wrap that logic in a subflow instead. A body node that asks to wait for an external event fails its item, because a single parallel branch cannot suspend the whole run. Inside the body, only Condition performs port selection.

ParameterTypeRequiredExprNotes
collectionstring No Yes The items to map over. An empty collection completes immediately with an empty results array.
maxParallelismnumber No Yes Concurrent items. Defaults to 8; clamped to 1–64. The form shows it blank.
continueOnErrorboolean No Yes Defaults to false. When true, failed items become error objects in results and the node still succeeds.
endstring No Yes The per-item loop-back input port. Always hidden from the form.
PortTypeFires when
startanyOnce per item, in its own isolated body run. Wire the body here.
successarrayOnce, after every item has finished. Carries results, count and failedCount.
errorstringDeclared, but the node does not route here — a failure goes through the normal node-failure path instead.
The inspector shows one iteration, not all of them

Persisting a node state per item would explode the state table on a large collection, so the body nodes are recorded once, holding the last iteration's outputs and an execution count equal to the number of items. Treat the body's entry in the inspector as a sample.

Join

join · Control · timeout 10

Fan-in. It waits until every branch wired into it has completed, then emits their outputs as a single ordered array. Reach for it after a deliberate fan-out where all branches are guaranteed to run — several independent calls made in parallel, or the branches downstream of a Parallel For-Each.

The waiting is done by the engine, not the node: a Join is simply not scheduled until each of its incoming-edge predecessors has completed. By the time the node itself runs, the branch values have already been collected in incoming-edge order, and the node is a thin pass-through that exposes them. It has no parameters, because there is nothing to configure.

Both of its ports carry the same array. results is the descriptive name; result mirrors it so a downstream node that just wants "the joined value" can wire to the generic port like any other node.

Never join mutually exclusive branches

Do not place a Join after a Condition — or any other branch node — whose branches are alternatives. The branch that was not taken never completes, the Join's precondition is never satisfied, and it waits forever. The run does not fail with a useful message; it simply stops making progress. A Join belongs only where every incoming branch is certain to run.

ParameterTypeRequiredExpr
None.
PortTypeCarries
resultarrayThe collected branch outputs. Mirrors results.
resultsarrayThe collected branch outputs, in incoming-edge order.

Subflow

subflow · Control · timeout 300

Calls another workflow as a step. Reach for it to factor out something you repeat — a notification format, an authentication dance, a validation routine — and to get around the Parallel For-Each restriction on nested control flow, which a subflow satisfies by definition.

A subflow is inlined at compile time, not invoked as a separate run. The compiler splices the referenced workflow's nodes and edges into one flat execution plan, prefixing every inlined id with the subflow node's own id — a node called inline-1 inside a subflow node called subflow-a becomes subflow-a/inline-1 — so names stay unique at any nesting depth. The consequence is that a subflow shares the caller's run, its journal and its variable scope, and appears in the inspector as ordinary nodes with compound ids. There is no child run to look up.

This is worth holding on to, because a neighbouring feature works the opposite way: the workflows an AI Agent calls as tools really do execute as separate, separately journaled child runs. Same intuition, different mechanics — if you are looking for a child run in the run list, a subflow will never produce one and an agent tool always will.

Because inlining happens at compile time, three failures are compile errors rather than run-time ones, each naming the offending node: a missing subflowId (ERR_MISSING_SUBFLOW_ID), a referenced workflow that does not exist (ERR_SUBFLOW_NOT_FOUND), and a recursive reference — a subflow that reaches itself, directly or through a chain — reported as ERR_RECURSIVE_SUBFLOW. The recursion diagnostic prints the whole path, which is usually enough to spot the cycle. None of these can become a run-time stack overflow, because the plan is finite before anything executes.

The manifest declares one parameter, but the properties panel writes several. Selecting the node gives you a searchable list of the other workflows, a button that creates and links a new one, and — once a workflow is chosen — slots for binding a variable to each of its declared inputs and outputs. Those bindings are stored alongside subflowId and are applied by the subflow's own Start node (inputs) and End node (outputs). A subflow that declares neither is flagged in the panel, because it can neither receive nor return anything.

Double-clicking the node opens the referenced workflow. A reference to a workflow that has since been deleted is called out as dangling in the panel before it ever reaches the compiler.

subflowIdstring No— The workflow to inline. Not required by the manifest, but missing it is a compile error — chosen from the picker rather than typed.
PortTypeCarries
resultanyContinues after the inlined body. Values come back through the declared output bindings, not through this port.
