File access

Settings › File Access decides which directories the File Read and File Write nodes may touch. On a fresh instance the answer is none — every file operation is denied until an administrator grants a path. This page covers granting subtrees, the free-space reserve that stops a workflow filling a drive, the escape hatch you should think twice about, and the one-click remediation offered when a run fails on a denial.

Deny by default

The policy is instance-global and consulted before any input or output. With no grants and total access off, the card shows a grey advisory reading No paths granted and total access off — every File Read / File Write will fail until you allow a path, and that is exactly what happens. A run reaching a file node gets a denial naming the path it attempted.

This is not the same kind of control as the switches on Capabilities. There is no coarse "filesystem on/off" toggle, precisely because granting one directory at a time is a better control than granting all of them at once. The two filesystem capability tags a node declares are enforced here rather than there.

Granting a path

Under Permitted paths, press Add path to create a row. Each row is an absolute directory path and a mode chosen from a dropdown: Read, Write, or Read & write. A grant covers the directory and everything beneath it, recursively — you do not enumerate subfolders. A trash-can button on the right removes a row.

Rows are edited freely and nothing is enforced until you press Save policy. The button stays disabled while the form matches what is stored, and the card says No changes beside it; after a successful save it says Saved. Rows whose path is blank are dropped on save rather than stored as empty grants.

ModeSatisfies
ReadFile Read only.
WriteFile Write only.
Read & writeBoth.

A request is always exactly one of read or write, and a grant carrying both modes satisfies either. Grants are evaluated as a set: if any rule's root contains the target with the right mode, the operation proceeds. There is no ordering and no deny rule — you cannot carve an exception out of a granted subtree.

Grant the narrowest directory that works

Because a grant is recursive and there is no way to exclude a subfolder, the directory you name is the whole of what you have given away. Granting C:\jobs\inbox is a very different decision from granting C:\, and the interface will happily accept either.

What the server enforces

The card's own description is accurate: path traversal and symlink escapes are blocked server-side, so a workflow can never reach outside a granted directory by manipulating its path. The specifics are worth knowing because they explain denials that can otherwise look wrong:

  • Relative paths are refused outright in enforced mode, with a message naming the path. They are not resolved against the working directory, because that directory is not something a grant can be reasoned about against.
  • Textual .. is collapsed before any comparison, so a path that climbs out of a granted root is measured where it actually lands.
  • Symlinks and junctions are resolved along the whole existing prefix of the path — not just its last component — so a reparse point buried in the middle with real directories below it is still followed to its true target.
  • A write target that does not exist yet is still checked, by walking up to the nearest existing ancestor, resolving that ancestor completely, then re-appending the missing tail.
  • Resolution is fail-closed. A path whose real location cannot be determined — an unresolvable reparse point, a link cycle, an I/O error — is denied rather than trusted as written.
  • The boundary test is exact. A sibling directory such as C:\data-evil never matches a grant on C:\data, and a path on a different volume is rejected.

A grant whose own path is malformed simply grants nothing, rather than failing the save or widening the policy.

The deny messages

Denials are specific about which of the checks refused, which is the fastest way to tell a misconfiguration from a genuine block:

SituationWhat the run reports
Nothing granted yet The path is not permitted (nothing is granted yet), and an administrator must grant it under Settings › File Access.
Outside every grant The path is outside every permitted directory.
Inside a grant, wrong mode The path is within a grant that does not permit reading — or writing.
Relative path supplied Only absolute paths are allowed, quoting what was given.
Free-space reserve would be breached The write would leave a stated amount free on the drive, below the required reserve.

The distinction between "outside every permitted directory" and "within a grant that does not permit writing" is the useful one. The second means your path is right and only the mode is wrong, which is usually a one-dropdown fix.

The free-space reserve

Under Free-space reserve (writes) there are two fields, Minimum free (MB) and Minimum free (%). A write is blocked if it would drop the target drive below the reserve. Leave a field blank for no reserve on that dimension; leave both blank and no capacity check runs at all.

When both are set, both apply and the stricter wins — the effective reserve is the larger of the absolute figure and the percentage of the drive's total size. This matters when the same policy covers drives of very different sizes: a percentage scales, a fixed figure does not, and taking the larger means neither can be used to sneak past the other.

The arithmetic accounts for overwrites. On an append, the full number of bytes is charged against free space. On an overwrite, the existing file's bytes are reclaimed, so only the net growth needs headroom — writing a 10 MB file over an existing 9 MB one needs 1 MB, not 10. If the existing file's size cannot be read, the write is treated as fresh, which is the conservative direction.

The percentage field is bounded to 0–100 in the interface and the megabyte field to non-negative values. Both are stored in the same policy record as the grants, so a single save writes them together.

This is not the disk-space guard

The reserve here stops one node's write. It is a different mechanism from the free-space floor on Settings › Retention, which watches the volume holding the database and disarms the whole runtime when it runs low. Both are useful and they protect different things — see Retention and disk space.

Total access

At the top of the card is a checkbox labelled Total access (unrestricted), described as letting file nodes read and write anywhere on the host and overriding the path grants below. Switching it on is gated: a modal appears headed Grant total file access?, explaining that every workflow — including imported and generated ones — will be able to read and write any file the host can reach, and offering Cancel or Enable total access. Switching it off again is immediate and needs no confirmation.

While it is on, the path-grant list is hidden entirely, because it no longer has any effect, and an amber banner sits in its place restating what is in force.

Why this is a bad idea

Total access removes the only per-path control the product has. Every workflow on the instance can then read anything the host account can read — including the SQLite database itself, the .credential-key file that decrypts every stored secret, and the configuration files — and write anywhere it can write, including over the application's own binaries. Combined with code execution being enabled, it is a complete loss of the file boundary. The confirmation text is honest when it says to only leave this on for a trusted single-operator instance.

Two things survive total access, and they are worth knowing so you do not mistake them for the boundary still holding. Relative paths become allowed again, resolved against the working directory. And the free-space reserve is still enforced on writes, so a runaway workflow still cannot fill the disk. Everything else is open.

If you turned it on to get past a denial, the better fix is almost always a narrow grant. The remediation flow below exists to make that the path of least resistance.

Fixing a denial from the run that hit it

When a run fails on a file-access denial, the run inspector shows a remediation card underneath the failure — placed after it deliberately, so the panel reads cause then fix. The card is headed How to fix, explains that file access is sandboxed and that this location must be added to File Access to let the node read or write there, and shows the exact path in a code chip.

Two actions sit below it:

  • Grant access in File Access settings queues the path and switches straight to Settings › File Access. The screen opens on that section rather than its usual landing section, and the path is already added as a new row with the mode preset to Write. It is appended after the form takes its baseline snapshot, so the form reads as changed and Save policy is enabled with the suggestion sitting there for you to review.
  • Copy path puts the same path on the clipboard and briefly changes its own label to Copied. Useful when you want to grant a parent directory instead, or check the path against what you expected before granting anything.
The pre-filled row is a suggestion, not a decision

Nothing is granted until you press Save. Read the row before you do. The suggested path is the exact file or directory the node attempted, and the suggested mode is Write regardless of which node failed — so a File Read denial arrives pre-filled with a write grant you almost certainly want to change to Read. Editing the path to a sensible parent directory before saving is normal and expected.

The queued path is consumed once. Arriving at the screen clears it, so navigating away and back does not re-add the row, and it will not silently reappear in a later session. If a row with that exact path already exists in the policy, nothing is added.

Where the policy lives

The policy is stored in the database as a single application setting containing the total-access flag, the list of rules and the two reserve figures. Like the capability policy, it has no appsettings.json counterpart — you cannot pre-seed it for an unattended install, and there is no configuration key to inspect when diagnosing a denial. An unset or unparseable value is treated as the secure default: nothing permitted, no reserve.

The guard fetches the live policy on every check, so a saved change applies to the next file operation with no restart and no cache to wait out. Revoking a grant stops the next write just as promptly as adding one enables it.

Because the policy is stored as an application setting, it travels in a backup along with everything else in that table — restoring an instance restores its file grants. See Backup and restore.
