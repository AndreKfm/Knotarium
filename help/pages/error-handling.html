Error handling and alerts

A failure can be handled at three levels, and they compose rather than compete: the node itself can retry, the graph can route the failure down an error port, and the instance can start a dedicated error workflow and notify you. This page covers what happens at each level, in the order the engine tries them.

What happens when a node fails

When a node throws, the engine works through a fixed sequence:

  1. Automatic retry, if the node opts in. A node whose catalog entry declares the retry recovery mode and an idempotent side-effect kind is retried according to its retry policy. The run parks in a waiting-for-retry state and a delayed work item is enqueued per the backoff. Both conditions are required — a node that causes a non-idempotent side effect is never retried automatically, because repeating it is not safe.
  2. An error port, if one is wired. Once retries are exhausted or not applicable, the engine looks for outgoing edges from the failed node named error or failure. Every such edge is followed and the run continues. The run does not fail.
  3. Otherwise the run fails. With no error path, the run is marked failed and a workflow-failed entry is journaled naming the node.
A caught failure is a successful run

Because an error edge lets the run continue, a workflow that catches everything never reports a failure — which also means it never triggers the global error workflow and never sends a failure alert, since both hang off the run-failed event. If you want a caught branch to still be visible as a problem, end it in something that surfaces it: a notification, a record written somewhere, or a node that deliberately fails after doing the cleanup.

Per-node error ports

An error port is just an output socket named error or failure, and the engine treats both names identically and case-insensitively. Nodes that expose one — the Inline Code node, for example, carries result and error — let you wire the failure path on the canvas exactly like the success path. Everything downstream of that edge runs with the failure already in hand.

A failure edge is exclusive to the failure path. Only the failure handler schedules it, and the success path skips any edge carrying either name, so an error branch drawn from an HTTP Request, a Transform, a Merge or a custom package runs when that node fails and not otherwise. The one exception is a node that routes by choosing a port — Condition, Switch, For Loop, Parallel For-Each, AI Router, AI Verify and AI Semantic Diff. Their explicit choice wins, so a branch label that happens to be spelled error is followed like any other.

Loop and iteration nodes reserve their own port names, so success, failure and error are all recognised as exit paths out of a loop rather than as part of the loop body. A parallel iteration collects a per-item error into that item's result instead of failing the whole batch.

The global error workflow

One workflow per instance can be nominated as the error handler. It is chosen from the Error Workflow card at Settings › Notifications, a single dropdown listing every workflow with — None (disabled) — as the default. The choice saves immediately and confirms with "Saved." or "Cleared."

Whenever any run fails, the failed run's identifier is handed off — as a non-blocking in-memory hand-off, so it can never slow down or break the run that failed — to a background worker that starts the error workflow. Every path that marks a run failed flows through the same chokepoint, so there is no category of failure that quietly bypasses this.

Loop prevention

Two guards stop an error handler from triggering itself, and both must pass before a handler run is started:

  • The failed workflow is not itself the configured error workflow.
  • The failed run was not itself started as an error handler — that is, its origin is not error.

The second guard is the one that matters in practice: it means a handler that fails while handling someone else's failure does not spawn another handler. When either guard blocks the dispatch it is logged at debug level and nothing else happens — so a broken error workflow fails silently as far as the interface is concerned, which is worth knowing when yours seems not to run.

What the handler receives

The handler is started with the origin error and a link back to the run it is handling. The failure context arrives twice, in two shapes, so you can use whichever suits the node you are wiring.

As a bundled object on the Error Trigger node's result port:

FieldContains
workflowIdIdentifier of the workflow that failed.
workflowNameIts display name.
executionIdIdentifier of the failed run.
failedNodeIdThe node that failed.
failedNodeTypeThat node's type, resolved from the failed workflow's definition.
errorMessageThe failure message.
triggerOriginHow the failed run had been started.
timestampUtcWhen the failure occurred.

And flattened into individual global variables, each prefixed so it cannot collide with the handler's own state: errorWorkflowId, errorWorkflowName, errorExecutionId, errorFailedNodeId, errorFailedNodeType, errorMessage, errorTriggerOrigin and errorTimestampUtc. The flattened form exists so simple handlers need no unpacking — a Log node message such as "{errorMessage} in {errorFailedNodeType}" substitutes them directly, and an Inline Code node can read them straight off the run state.

The error workflow must be published and activated

Like every other trigger path, the handler runs its active version. A nominated error workflow that has never been published, or has versions but none activated, starts no run at all; the only trace is a warning in the log saying the error workflow is not published or active. Since this only surfaces the first time something actually fails — usually at the worst possible moment — publish, activate and test the handler deliberately rather than assuming it works.

Failure-alert channels

Alerts are separate from the error workflow and fire from the same run-failed event. Destinations are managed as Notification Channels at Settings › Notifications. Each channel has a name, a type, and type-specific configuration.

TypeConfiguration
Webhook (generic JSON POST) A single Webhook URL. The failure message is posted to it as JSON.
Slack (incoming webhook) A Slack Incoming Webhook URL of the usual hooks.slack.com/services/… form.
E-Mail (SMTP) SMTP Host, Port (default 587), a Use SSL/TLS switch (on by default), Username and Password, a From Address — which falls back to the username when blank — and comma- or semicolon-separated Recipients.

A channel's type is fixed once created: the type selector is disabled when editing, so changing from Slack to email means creating a new channel. Secrets are never returned by the API, so the configuration fields open blank when editing, with a note explaining that leaving them empty keeps the stored value and filling them in replaces it.

Test send

Every channel card has a Test button that sends a message through the real sender with the real stored configuration. The result appears on the card itself: Sending…, then ✓ Test sent or ✗ followed by the actual error. This is the only way to find out that an SMTP password is wrong or a Slack webhook has been revoked before a genuine failure needs it, and it costs nothing — use it after every edit.

Which channels a workflow alerts

Routing is per workflow, chosen from the alerts chip on the workflow's card in the dashboard. There are three modes, and the resolution is deliberately simple:

ModeChip readsResolves to
Default channels (Inherit) Alerts: Default, green Every channel marked as a default failure-alert channel. This is the mode a workflow has until you change it.
Off Alerts: Off, red No channels. This workflow never alerts.
Custom channels Alerts: Custom, violet Exactly the channels you tick, ignoring the default flag entirely.

A channel is marked as a default with the Use as default failure-alert channel checkbox in its form, and shows a star badge on its card. If no channel is marked as default and the workflow inherits, the resolved set is empty and nothing is sent — which is the usual explanation for a failure that produced no alert.

Delivery and its failures

Alerting can never affect a workflow run. Dispatch happens on a background worker, and every send is wrapped so a delivery failure is recorded but never propagates back into execution.

Each channel's outcome is journaled onto the failed run itself, with the channel's identifier, name and type attached — so the run timeline of a failure also tells you whether the alert about it went out, and to where. A send that throws is journaled as a notification failure with the exception message. That is where to look first when someone says the alert never arrived: if there is no notification entry at all, the channel was never resolved; if there is a failed one, the message is the reason.

Beneath that, the worker retries a transient dispatch failure — a momentary database read error, say — up to three total attempts with a backoff of five seconds times the attempt number, capped at thirty seconds. After three attempts it logs that it is giving up, so a poison item cannot loop forever.

Navigating between a failure and its handler

A failed run and the handler run it spawned are linked in both directions, and the visualizer makes both directions one click.

A pill floats at the top-centre of the run canvas. On a failed run it is a solid amber Error handler ran → button that opens the handler. On the handler run it is a coral-outlined Triggered by failed run → button that navigates back to the failure. When a run is both — a handler that itself failed and was handled — both pills appear side by side.

There are three further entry points to the same handler run, so it is discoverable wherever you happen to be reading:

  • A synthetic amber card is drawn on the canvas below the failed node, connected to it by a dashed amber edge, so the cause-to-handler relationship is visible on the graph itself. Clicking the card opens the handler run.
  • Inside the expanded failed group in the timeline, a button reading ⚡ Error handler caught this — view run →.
  • Under the timeline, ⚡ An error handler caught it and ran — view handler run →.
Give the handler a moment to appear

The handler run is created asynchronously after the failure, so it does not exist at the instant the failure is rendered. The visualizer polls for it roughly every one and a half seconds for about fifteen seconds, then stops. If no pill has appeared after that, no handler run was created — check that an error workflow is configured, that it is published and activated, and that neither loop guard blocked it.

The links are also written into the journals themselves, so they survive independently of the interface. The failed run gains an ErrorWorkflowStarted entry naming the handler workflow and the new run identifier, and the handler run opens with an ErrorWorkflowLink entry reading "Handling failure of run …".

Putting the layers together

A sensible default arrangement for a production instance is all four layers at once. Let idempotent nodes retry themselves. Wire an error port only where the graph genuinely has a fallback, and deliberately leave it unwired where it does not, so the run fails and the rest of the machinery engages. Configure one default notification channel and test it, so a human hears about it. Nominate one error workflow — published, activated and tested — so the failure gets recorded or escalated consistently regardless of which workflow produced it. What is left over lands in the dead letter queue for triage.
