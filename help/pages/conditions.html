Conditions and branching

Branching is what turns a sequence of steps into a workflow. Knotarium's main branch node is Condition, which has a dedicated full-screen editor for building nested AND/OR/NOT logic and previewing the result against real data before you ever run anything. This page covers that editor in detail, and then the two other nodes that route a run — Switch and AI Router — including a limitation of Switch that is worth knowing before you build on it.

The Condition node

The Condition node has two output ports, true and false, and the run follows exactly one of them. It is one of a small, explicit set of node types the engine treats as branch routers: when such a node reports which port it chose, every outgoing edge on a different port is suppressed.

Configuration is stored in a single logic property. A much older format kept three separate fields — left, operator and right — and nodes still carrying it continue to run. Precedence at run time is strict: valid logic wins; otherwise the legacy fields are used; a node with neither is a configuration error.

The logic editor

The property inspector shows a one-line summary of the current logic and an Edit logic button. Double-clicking the Condition node on the canvas opens the same editor. It fills the screen, because a condition of any real complexity does not fit in a side panel.

The editor draws the logic as a left-to-right dataflow graph rather than as nested boxes: operand cards on the left feed comparator cards, comparators feed AND/OR group cards and NOT cards, and the final result arrives at a TRUE/FALSE output card on the right. The layout is computed for you — nodes cannot be dragged — and it is recomputed on every edit, so the picture always matches the logic.

Save & Publish in the editor's top bar is disabled until every operand is complete; its tooltip reads Complete every operand to save. Leaving with unsaved changes asks Discard unsaved changes to this condition?; Esc is the same as Back.

Building one comparison

Clicking an operand card opens a small editor with two tabs.

  • Reference lists the workflow's variables and, on signal-driven graphs, the fields of the inbound signal, each with its type. Picking one stores an expression that is resolved at run time. Beneath the list is a Sample value field used only by the live preview.
  • Literal offers a string / number / boolean selector. Boolean literals are a true/false toggle rather than free text; the other two are a text field, and the value is converted to its declared type when you save.

For the two membership operators the right-hand operand is a list instead of a single value: the type picker disappears and you type comma-separated values, for example 3, 5, 4. Each element is typed against the left operand when the comparison is evaluated.

The operator catalogue

The catalogue is shared between the editor and the runtime and is kept in sync by a drift test, so what the menu offers is exactly what will execute. Unary operators ignore the right-hand operand entirely.

Type filtering and the ordering guardrails

When the left operand's type is known, the operator menu only offers operators that accept it. A number hides the text operators, a boolean hides the ordering operators, and so on. Exists and Does not exist are genuinely type-agnostic and are always offered. When the type is not known — a dynamic reference — everything is offered and the runtime is the backstop.

Ordering comparisons are constrained further. If both operand types are known and they differ, or they match but are not orderable, the editor blocks the combination so it can never be saved, with a reason such as Ordering needs matching types; got string and number.

Ordering on strings compares letter by letter

The four ordering operators also accept strings, and the editor shows a hint when you use them that way: Strings compare lexically (ordinal): "9" > "10" is true, "Z" < "a" is true. If you are comparing version numbers, quantities or anything else that only looks numeric, set the operand's type to number rather than relying on the string comparison to do what you meant.

Grouping and negation

Add condition in the toolbar adds a comparator, wrapping the existing logic in an AND group if it was a bare comparison. Every card carries three small tools: wrap in a group, wrap in NOT, and remove. A group card switches between AND and OR, and groups nest freely, so (A AND B) OR NOT C is built by wrapping, not by typing.

The structure has bounds, mirrored from the parser that validates it on the backend: nesting at most 20 deep, at most 200 nodes in the whole tree, and at most 50 children in any one group. A literal may be up to 10,000 characters, a reference 2,000, and a regular expression 512.

The live preview

Everything in the editor is evaluated as you type. Each comparator card shows its own result, the wires are coloured by what they carry, and an output pill in the toolbar gives the overall verdict.

StateMeans
TRUE / FALSEThe comparison resolved with the values currently in play.
runtimeValid, but referencing something that has no design-time value. It will resolve when the workflow runs. This is a healthy state, not a problem.
incompleteAn operand or operator is still missing. Save is blocked.
errorThe comparison cannot be evaluated as written — for example a type mismatch or a malformed regular expression.

Above the graph, a Conditions strip labels each comparator A, B, C… in the order they appear on screen, with its expression and a pass/fail marker, followed by the top-level combinator. It is the fastest way to see which half of a long condition is the one failing.

Where the preview gets its values

This is the part that makes the preview trustworthy. When the workflow has already run, the editor asks the backend to resolve each of the condition's references against the last real run, and a Last run / Manual selector appears in the toolbar. Last run is chosen by default. The selector shows when that run happened, and marks it stale when the run came from a different published version than the one you are editing — the values are still shown, but the graph they came from is not this graph.

Switching to Manual uses the per-operand Sample value fields instead. If the workflow has never run, Manual is the only option and the selector is not shown at all.

Test mode

The ▶ Test button turns every reference operand into an editable field so you can type the values an incoming signal would carry and watch the condition resolve. A row of presets fills them for you: make everything match, make one named comparator fail, make everything fail, or clear. The bar states plainly that values are temporary and the configuration is unchanged, and ✕ Exit test discards them.

Migrating a legacy condition

A node still using the old three-field form is summarised in the property inspector as Legacy condition — open to migrate. Opening the editor seeds a single comparator from those fields as a best effort, and saving writes the new format and deletes the old left, operator and right properties. The migration is one-way and happens on save, not on open, so opening a legacy condition to look at it changes nothing.

The editor also opens conditions already stored in the earlier flat format — a list of comparators joined by one combinator — and saves them as a tree. The property inspector renders that flat format as a row per comparison, and the tree format as a single parenthesised expression, which is a quick way to tell which one a node is on.

What blocks publishing

A Condition node is publishable when it can produce a definite branch: it has either a logic blob that parses, or a legacy operator. A node with neither, or whose logic no longer parses, is incomplete and publishing is refused with a message naming the offending node ids and telling you to open and complete them in the editor.

Saving a draft is deliberately not gated, so an unfinished condition never stops you from saving work in progress. Only publishing and activating are checked.

What happens at run time

References inside the logic are resolved by the node itself rather than by the generic expression pass, which lets it distinguish "resolved to null" from "could not be found". The outcome maps onto three behaviours:

  • True or False — the run continues down that port.
  • Error — the node fails, carrying a code and the comparator and operand that caused it. The codes are INVALID_LOGIC, RESOLUTION_FAILED, COERCION_FAILED, TYPE_MISMATCH and an internal-invariant backstop.
  • A node with no configuration at all takes the false port. That is the only silent fallback, and the publish gate is what stops it from reaching a live instance.
A missing reference fails the node rather than reading as false

This is a deliberate difference from ordinary expression fields, where an unresolved reference quietly becomes nothing. A branch taken because a value could not be found is a bug that hides for months, so a Condition treats it as RESOLUTION_FAILED and stops. Recovery for the node is fail immediately — it is not retried.

The Switch node

Switch (category Control) takes a value and a cases list. The list is split on commas, semicolons and line breaks; entries are trimmed and empties dropped. At run time the value is compared against each case in order, ignoring case, and the node reports the first case that matched — or default when none did.

Switch does not currently branch

Two things stop it. Its manifest declares a single output socket, default, so an edge drawn from any other port is rejected at compile time with an invalid-socket-mapping error and publishing fails. And the engine's list of branch-routing node types — the types for which a reported port suppresses the other outgoing edges — contains Condition, For Loop, Parallel For Each, AI Router, AI Verify and AI Semantic Diff, but not Switch. So even where an edge exists, every outgoing edge from a Switch node is followed regardless of which case matched.

In practice a Switch node evaluates its cases and records the match, but the run continues down all of its connections. Use chained Condition nodes, or an AI Router when the input is natural language, for multi-way branching that actually routes.

The AI Router and its dynamic ports

AI Router (category AI) classifies its input using the configured language model and routes the run down one of its category branches. Unlike Switch, it is a real branch router: the port it selects is the only one followed.

Its branches are not fixed. The categories field takes labels separated by commas, semicolons or line breaks, and each label becomes an output port on the node card as you type, followed always by an otherwise fallback. Labels are trimmed, empties dropped, and duplicates removed case-insensitively keeping the first spelling. The same parsing runs on the backend, so the handles you see are the ports the runtime can select.

Because the ports are derived from configuration rather than declared in the manifest, the node declares no outputs at all — which is precisely what tells the compiler to skip socket validation for it. That escape hatch is why AI Router's dynamic branches work where Switch's do not.

Renaming a category orphans its branch

The port id is the label text. Editing a category label changes the handle, and any edge attached to the old handle no longer has a port to hang from. Re-wire branches after renaming a category, and prefer short stable labels over sentences.

Two further AI nodes route by verdict with fixed ports, so they need no such escape hatch: AI Verify emits verified, unsupported, contradicted and uncertain, and AI Semantic Diff emits its material, cosmetic and none branches. In both cases the verdict is computed by ordinary deterministic code over the model's structured output, not by asking the model to judge itself.
