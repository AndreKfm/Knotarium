Dead letter queue

The dead letter queue is the instance's inbox of failed runs. It is not a separate store and nothing is moved into it — it is a filtered view of the runs whose status is Failed, kept as a distinct screen so that "things that broke and nobody has looked at yet" is a list you can drive to zero rather than a status you have to remember to filter for.

Where it is

Dead Letter is a top-level entry in the header navigation. The screen is a single column: a heading, a Refresh button, one row per failed run, and a line of explanatory text. When there is nothing to triage it says "No failed runs. 🎉" — which is the state you are aiming for.

The list does not update by itself. It loads when you open the screen and reloads when you press Refresh, so a run that fails while you are looking at the list will not appear until you ask for it.

What lands here

Exactly the runs whose status is Failed. In practice that means a node failed and nothing in the graph caught it: automatic retries were exhausted or did not apply, and no outgoing edge named error or failure was wired from the failed node. It also includes runs an operator failed deliberately with the Fail Run decision on a node awaiting a manual decision.

Just as important is what does not land here:

Not listedWhy
Runs that caught their own failure on an error port Following an error edge lets the run continue, so it never reaches Failed status.
Cancelled runs Cancelled is its own status — usually the result of deactivating a workflow, which cancels its in-flight runs.
Runs waiting for a retry or a manual decision Still in progress. They appear here only if they eventually fail.
Runs you have already discarded Discarding moves them to a separate status, off this list.
Starts that were refused outright A start rejected because the version fails to compile, or because the execution queue is at capacity, persists no run at all — the caller gets the diagnostics or a 429 and there is nothing to fail.

Reading a row

Each row shows the workflow's name — falling back to its identifier when the name is unavailable — and, underneath, the run's trigger origin and the time it last changed, formatted for your locale. The origin is the useful half: a wall of schedule rows says something systemic broke, whereas a single webhook row among them points at one caller.

The row itself carries no error message. That is deliberate — a failure message is frequently a multi-line dump, and the list is a triage queue, not a log. The message lives one click away.

Triage: open or discard

Every row has exactly two actions, which is the whole workflow of the screen.

Open

Open loads the run in the Execution Visualizer, which is where all the actual diagnosis happens: the failed node highlighted on the graph it ran against, the expanded failure group in the timeline with the full error, the Time Travel inspector for the inputs and variables as they stood at each step, and right-click replay to re-run from any node — optionally against a newer version, which is how you verify a fix against the exact run that exposed the bug.

A replay creates a new run and never modifies the source. The original therefore stays in the dead letter list until you discard it, which is correct: the failure happened, and a successful replay does not un-happen it. Discard it once you are satisfied the replay resolved the situation.

Discard

Discard marks the run as Discarded so it drops off the list, and writes an ExecutionDiscarded journal entry recording that it was discarded from the dead-letter view. Only a failed run can be discarded — anything else is refused with the message "Only failed executions can be discarded."

Discarding is not a delete and not a retry. It changes a status and nothing else:

  • The run, its journal, its per-node states and its inputs and outputs all remain in the database and remain openable if you have the run's identifier.
  • Nothing is re-executed and nothing is compensated. Whatever the run did before it failed stays done.
  • The version the run executed remains protected from the version-retention cap, because that cap preserves any version a retained run used.

Read it as "acknowledged": the human decision that this failure has been understood and needs no further action.

There is no undiscard

The screen offers no way back. A discarded run is not deleted, but it will not reappear in this list, so if you discard something you have not actually investigated, you will need its run identifier — from a notification, a log line or the error-handler run's link back — to find it again. Open before you discard.

How it relates to the error workflow

The dead letter queue and the global error workflow react to the same event — a run reaching Failed status — but they are complementary rather than alternatives, and neither suppresses the other.

Error workflowFailure alertsDead letter queue
WhenImmediately, in the backgroundImmediately, in the backgroundWhen you next open the screen
Who actsA workflow you wroteA channel you configuredA person
Good forAutomatic compensation, escalation, ticket creationTelling somebodyDeciding what actually happened
Clears itselfn/an/aOnly when you discard

A failed run therefore does three things at once: it starts the error workflow if one is configured and neither loop guard blocks it, it queues a failure alert to whichever channels the workflow resolves to, and it appears in this list. The first two are automatic responses; this list is the record that a human still owes it a decision.

A handler run that fails appears here too

Error-handler runs are ordinary runs, so one that fails while handling somebody else's failure lands in this list alongside the original. It will not have spawned a handler of its own — the loop guard on the error origin prevents that — so the dead letter queue is where a broken error workflow becomes visible. Two rows appearing together at the same timestamp is usually that pattern, and the lineage pills in the visualizer will confirm it.

The list empties itself eventually

Retention prunes terminal runs older than Retention__RunHistoryDays, which defaults to 30 days, and deleting a run cascades to its journal and node states. Failed runs are terminal, so an untriaged failure disappears from this list once it ages out — along with the evidence needed to diagnose it.

That is the argument for keeping the queue near zero rather than treating it as an archive. If you need failures to persist longer than they are being investigated, raise the retention window at Settings › Retention; note that a stored value there overrides the configuration file, and that keeping everything forever grows the database without bound.
