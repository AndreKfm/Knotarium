Triggers

A run begins in exactly one of six ways: you press Run, an HTTP caller posts to the webhook endpoint, a cron schedule comes due, a polling trigger sees something new, another workflow fails and hands off to the error workflow, or an external device raises a signal. This page covers each of them — what configures it, what it produces, and how it fails.

The trigger nodes

Trigger nodes are marked trigger-only in the node catalog, which means they may start a graph and cannot be wired into the middle of one. They all sit in the Triggers palette category.

External Device blocks are not trigger nodes and live in the External category, but a graph built around them is started by inbound signals rather than by anything on this list. They are covered in their own section below.

Triggers run the active version, not your draft

This is the single most important thing to understand about starting a run, and it applies to every start path without exception. A run always executes an immutable published version — specifically the one currently marked active — never the working draft in your editor. The webhook, scheduler, polling and simulate-signal endpoints all resolve the active version and refuse with HTTP 409 and the message "Workflow has no active version. Publish and activate a version before triggering execution." when there is not one.

The editor's Run button is not an exception; it is the mechanism that makes this invisible. Run first activates the version selected in the toolbar dropdown and then triggers the workflow. Activation happens on every press, so the dropdown selection is always what executes and no separate activate step is needed. The practical rule is: save and publish, then run. Editing the canvas and pressing Run without publishing re-runs the previously published version, and the change you just made is not in it.

Pinned test outputs behave differently per origin

A node with a pinned output emits its pinned sample instead of executing — but only on a run whose origin is manual. Automatic runs from a webhook, a schedule, a poll or a device signal ignore pins entirely and execute the node for real. Publishing a version that still contains pins succeeds, with a warning naming the pinned nodes. That combination is a real trap: the workflow can look correct every time you test it by hand and behave completely differently the moment a schedule fires it.

Manual runs

A graph starting with a Start or Manual Trigger node is run from the canvas toolbar's green Run button. The button is disabled until at least one version has been published — its tooltip then reads "Publish a version (Save & Publish) before running." Running while previewing an older version is allowed: the preview closes and the previewed version is what runs.

The run's origin is recorded as manual. Starting a run does not navigate away from the editor; a non-disruptive toast reports that the run started, and the graph's variable pins and per-node status colours fill in live while you keep working. Manual runs are never gated by the arming switch.

A start can still be refused. If the execution queue is at capacity the response is HTTP 429 naming the pending-run limit, and if the version fails to compile the response is HTTP 400 carrying the compiler diagnostics, which the editor surfaces in its diagnostics panel rather than as a bare error.

Webhook triggers

The inbound trigger is a single machine-facing endpoint, POST /api/executions, whose JSON body names the workflow to start and supplies its input variables: 

# Start a workflow from outside
curl -X POST http://localhost:43120/api/executions \
  -H 'Content-Type: application/json' \
  -H 'X-Knotarium-Webhook-Secret: <secret>' \
  -d '{"workflowDefinitionId":"<id>","inputVariables":{"customer":"acme"}}'

The endpoint is deliberately anonymous — it is called by other systems, not by a signed-in browser — so it is protected by four separate gates instead of a user session, checked in this order:

  1. The per-workflow webhook secret, when one is configured. The caller presents the raw secret in the X-Knotarium-Webhook-Secret header and it is compared in constant time. A wrong or missing secret is 401. A workflow with no secret configured stays open, preserving the original machine-facing contract.
  2. The arming switch. A disarmed runtime answers 409.
  3. The workflow's enabled flag. A deactivated workflow answers 409 with "Workflow is deactivated and cannot be triggered externally."
  4. An active version must exist, or 409 again.

Two limits bound what an anonymous caller can do to the instance. Requests are rate-limited by Security__RateLimit__AnonymousMachinePerMinute, which defaults to 60 requests per minute and is shared with the run-resumption endpoint; raise it if legitimate webhook traffic is being rejected. The request body is capped by Security__WebhookMaxBodyBytes, default 1048576 bytes. The body limit is enforced by the web server during the read, so an oversized payload is never fully buffered or parsed.

A successful call returns HTTP 202 with the new run's identifier, so the caller can follow the run without waiting for it. A full queue returns 429; a version that fails to compile returns 400 with diagnostics. The run's origin is recorded as webhook.

A workflow without a webhook secret is open to anyone who can reach the port

The absence of a secret is not an oversight in the design, it is backwards compatibility — but it means any process that can open a socket to the instance can start that workflow with input variables of its choosing. Configure a secret for every workflow you expose, and treat the combination of a network-reachable bind address and an armed runtime as the moment that becomes mandatory.

Cron schedules

A Cron Scheduler node carries a five-field cron expression and an IANA time-zone identifier. The property form offers two modes. Simple builds the expression from a frequency (every N minutes, hourly, daily, weekdays, weekly, monthly) plus the day and time controls that frequency needs, and shows the generated expression underneath so you can see what it produced. Advanced (cron) exposes the raw expression: five fields in the order minute hour day-of-month month day-of-week, with Sunday as 0, * for any, */5 for steps and 1-5 for ranges. An expression the simple builder cannot represent opens the form in advanced mode and warns rather than silently rewriting it.

The time zone is a combobox: pick a suggestion or type any IANA identifier such as Europe/Berlin. It is required, and occurrences are computed in that zone, so a daily 08:00 schedule stays at local 08:00 across a daylight-saving transition.

The scheduling worker wakes every ten seconds and evaluates whatever is due. Schedules belonging to an explicitly deactivated workflow are skipped, and a schedule whose workflow has no active version is skipped with a log entry rather than an error. Claiming a due occurrence is atomic, so a duplicate claim simply advances the schedule instead of firing twice. Runs started this way carry the origin schedule.

Missed occurrences catch up, but only ten of them

When an instance was stopped over several scheduled occurrences, evaluation walks forward through the missed windows to find where it should resume — up to ten occurrences, after which it logs that the catch-up cap was reached and continues from there. A minutely schedule that was down for a day therefore fires once on return, not fourteen hundred times.

Polling triggers

A polling trigger asks a source whether anything has changed and starts a run only when the answer is yes. Three fields are always present.

FieldValuesMeaning
Interval (seconds) integer, minimum 1; the form starts at 60 How long after each poll the next one becomes due. Required.
Source Kind http · openapi Whether to call a URL directly or an operation from an imported OpenAPI specification. Required.
Change Detection etag · last-modified · hash · json-cursor · always How "something is new" is decided. Required; an unrecognised value falls back to hash.

The change-detection strategies differ in what they need from the server. etag and last-modified compare the corresponding response header against the stored cursor; if the server does not send that header at all, the poll is treated as new so a run is never silently skipped — which on a badly-behaved server means a run every interval. hash hashes the response body, needs no server cooperation, and is the safe default precisely because it cannot flood you with runs. json-cursor reads a value out of the response using the JSONPath in the JSON Cursor Path field, which appears only when this strategy is selected — for example $.data.cursor. always starts a run on every poll with no comparison at all.

An http source adds a URL (required, and it accepts expressions such as {{ $variables.myVar }}), a Method chosen from GET, POST, PUT, PATCH, DELETE and HEAD, an optional Headers (JSON) object, and an optional API Key Secret picked from your stored credentials, whose value is injected as the Authorization header. An openapi source instead asks for a Server Config, an API Spec and an Operation; the spec selector is only there to narrow the operation list and is not itself saved with the node.

The polling worker also ticks every ten seconds and processes whatever is due. The cursor advances only when a run was actually created, so a poll that finds new data but cannot start a run — no active version, for instance — will find the same data new again on the next pass rather than losing it. When a poll throws, the failure is recorded on the trigger and the next poll is scheduled one interval later, so a broken endpoint is retried at the configured rate instead of being hammered. One failing trigger never stalls the others.

The Error Trigger

An Error Trigger node marks a workflow as the entry point of an error handler. It takes no configuration: which workflow plays that role is a single global choice made in Settings › Notifications. When any other workflow fails, the chosen workflow is started with the origin error, and the failure context — the failed workflow, run, node, node type, message, original trigger origin and timestamp — is emitted on the node's result port and also flattened into individual global variables. The handler is never re-triggered by its own failures. This is covered in full on the error-handling page.

External device signals

A graph containing External Device blocks reacts to signals from a connected system: device events the device raises, and incoming actions it sends. Each wired output pin becomes an entry point, and when a matching signal arrives the engine starts an ordinary run seeded at that pin's downstream nodes.

Inbound signals are gated by the arming switch. While disarmed the subscription stays connected and the signal is simply dropped, so nothing has to be re-registered when you arm the instance again. Duplicate deliveries of the same signal instance — a provider re-sending a still-active event after a reconnect, for example — are de-duplicated, and a pin targeting a specific lifecycle phase only fires on the matching transition. Runs started this way carry the origin deviceEvent; the run inspector labels them EVENT or ACTION depending on the signal.

Manual Run is disabled for these graphs

When a graph contains an External Device block and has no Start or Manual Trigger node, the toolbar hides the Run button. In its place sits a non-interactive emerald status badge reading Event-driven · runs on device events. It is a status, not a disabled button: there is nothing for a manual run to start, because the device block itself is inert and a generic run would execute it as a disconnected no-op and never flow out of the pin.

Two real actions sit next to that badge. Watch live runs → opens the run inspector on this workflow's most recent run and then follows new device-event runs as they arrive. Simulate signal is the manual test path that replaces Run.

The Simulate signal dialog

The dialog fires one wired pin as if the device had sent it. Its Pin dropdown lists every simulatable pin, marked as an action or an event. Choosing an action reveals a Sample fields section with one input per statically known field of that action; blank fields are omitted from the payload, and an action with no static fields says so and sends an empty payload. Choosing an event says instead that it fires the event as "started" with an empty payload. Fire signal starts the run and opens it in the run inspector immediately — unlike a background Run, a simulation is an explicit test, so it takes you to the result.

A simulated run is a real run: it uses the active version, and the graph reads the synthetic envelope through signal.params.* exactly as it would a live one. Simulation is not gated by the arming switch, which is what makes it the way to test a device-driven workflow while the instance is safely disarmed. It does still require an active version, and it refuses with an explanatory error when no wired pin matches the chosen signal — "No wired device pin found … Wire the pin to a node first."

Firing a schedule by hand

The run inspector's Schedule Controls panel lists every scheduler node in the workflow with its next fire time, its cron expression and time zone, and a Fire now button. Firing by hand starts a run immediately without disturbing the schedule's own next occurrence. It requires the workflow to be enabled and to have an active version, and it refuses with 400 if the node named is not a scheduler node. The resulting run is recorded with the origin schedule, so it appears alongside genuinely scheduled runs in the history.

Which origin produced a run

Every run records the origin it was started with, and the run inspector shows it as a coloured pill above the timeline. The vocabulary is small and worth knowing, because several features branch on it.

OriginStarted byInspector pill
manualThe editor's Run button, or firing a schedule by hand.MANUAL, violet
webhookAn inbound HTTP call.MANUAL, violet
scheduleA due cron occurrence, or Fire now.AUTO, cyan
deviceEventAn inbound device signal, live or simulated.EVENT or ACTION, emerald
errorThe global error workflow reacting to a failure.—
replayRe-running an earlier run from a chosen node.—

Polling runs are enqueued directly rather than through the trigger endpoint. The inspector only distinguishes the three pill styles above, so anything that is neither a schedule nor a device event reads as MANUAL there even when it came in over HTTP — the recorded origin on the run is still the precise one.
