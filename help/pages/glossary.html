Glossary

Every term this manual uses with a meaning specific to Knotarium, defined in one or two sentences and linked to the page that covers it properly. Where the interface and the code disagree about a word — and in a few places they do — both are given, because you will meet both.

Five words carry most of the weight

If you read only part of this page, read workflow, node, edge, trigger and run. Nearly every other entry is defined in terms of those five. Core concepts explains how they fit together.

A

Active version — the one published version of a workflow that actually executes. It is recorded separately from the versions themselves, in a pointer with an append-only activation history, and every trigger resolves through it. A workflow with published versions but none set active cannot be triggered.

Arming — the instance-wide switch in the header that gates every automatic trigger. While disarmed, schedules and pollers keep ticking but skip their work, inbound webhook calls are refused, and only manual runs execute. See Runtime arming.

Audit log — an append-only, hash-chained record of privileged actions. The chain is verified during startup and a chain that does not verify aborts the launch; there is currently no viewer for it in the interface, and its only presence there is the retention setting that ages entries out. See Security model.

B

Backup — a whole-instance archive, extension .kgbak, protected either by a passphrase or by this server's own credential key. A server-key backup restores only on the host that created it and only while that host's key is unchanged. See Backup and restore.

Bundle — a distributable archive, extension .kgbundle, holding several workflows together with the node packages they depend on. It carries both an authoring manifest and a resolved lock file recording exact versions, hashes and trust levels, which is verified at install. See Bundles.

C

Capability — a named privilege that a node declares it needs and that an administrator must grant instance-wide before any node holding it will run. Three are switchable — code execution, database access and the AI agent — and all of them are off by default, an unset policy meaning everything is denied. See Capabilities.

Condition — a node that evaluates a logical expression tree and routes the run down its true or false output port. It has a dedicated full-screen editor rather than a text field, because a condition is a structured tree and not a string. See Conditions and branching.

Correlation token — a per-run, hashed, single-use, expiring token issued when a run parks waiting for an external event. Presenting it is what authorises resumption, which is why the resume endpoint is otherwise anonymous — the token is the authentication.

Credential — a named secret stored encrypted in the database and referenced by nodes rather than embedded in them. The key that decrypts it lives beside the database in .credential-key; the two must be backed up together. See Security model.

Credential slot — a symbolic, secret-free placeholder for a credential requirement inside a portable artifact, written as slot:<key>. Exporting a template or bundle rewrites real credential references into slots and installing rebinds them; a slot left unbound blocks both publishing and running.

D

Dead letter — the triage view listing every run that ended in failure, so that failures are worked through deliberately rather than scrolled past. Discarding a run from it marks it handled; it is not a deletion. See Dead letter queue.

Diagnostics — the compiler's findings about the graph you are currently drawing: missing sub-flow references, unreachable nodes, incomplete conditions and the like. These are design-time messages about the workflow, not run-time errors and not application logs. See Diagnostics.

Discarded — the state a failed run moves to when you triage it away in the dead letter view. The run and its journal are kept in full; it simply stops being counted as actionable.

Draft — the single mutable copy of a workflow that the canvas edits. It lives in the database, not in a file, and it is the one thing in the system that never executes: publishing snapshots it into a version, and versions are what run. See Versions and publishing.

E

Edge — a connection from a named output port on one node to a named input port on another. Edges carry the flow of control and the data together, which is why deleting a node also deletes every edge touching it. See Core concepts.

Egress policy — the rules governing what the instance may connect out to, applied to every outbound request the engine makes and re-checked on every physical connection including each redirect. By default it refuses private, loopback and link-local destinations. See Security model.

Error workflow — a workflow nominated to run whenever any other workflow fails, seeded with context about what failed. It bypasses the execution queue limits, and it is a silent no-op if the workflow you nominated has no active version. See Error handling and alerts.

Execution — the internal and REST-API name for a run. The interface says "run" and the code says "execution"; they are the same thing, and you will see /api/executions in any API work.

Expression — a {{ … }} placeholder evaluated when a node runs. It can read an upstream node's output as {{ $node.<id>.output.<port> }} or a variable as {{ $variables.<name> }}, with nested paths, indexing, operators and a small function library. A field that is a single placeholder returns the typed value; anything else interpolates to a string. See Expressions and data.

F

Failure alert — the per-workflow routing of failure notifications, which can inherit the instance default, be switched off, or name its own channel. See Error handling and alerts.

File access policy — the allow-list governing the File Read and File Write nodes. It is deny-by-default and empty on a fresh instance; grants are made one directory at a time, apply recursively to everything beneath, and are scoped to reading, writing or both. See File access.

G

Group — two unrelated things share this word. On the dashboard a group is a folder that organises workflows; on the canvas a Group node is an inert visual container that frames a region of the graph and moves its members with it. See The canvas editor.

J

Journal — the append-only event log of a single run, recording what each node received, what it produced and what the variables looked like at each point. It is the system of record from which a run's status is reconstructed, and it is what makes replay, time travel and crash recovery possible. See Runs and the inspector.

M

Manual decision — the resolution a person supplies when a run was interrupted part way through an external effect and the system cannot safely determine whether that effect happened. Until it is answered, the node holds the run rather than guessing.

N

Node — one step in a workflow: an HTTP request, a branch, a database query, a log line. Every node is an instance of a node type whose behaviour, parameters and ports are declared by a manifest. See How to read this reference.

Node package — the registry entry for a node type: a manifest declaring its parameters, ports, capabilities, timeout and retry policy, plus optionally a compiled assembly implementing it. Around thirty-five first-party types are built in; further ones are installed or published into the database. See Custom node packages.

Node tier — how a node type's behaviour is supplied: declarative, compiled, or interpreted. It is a property of the type, not something you choose per node.

Notification channel — a configured destination for failure alerts, one of which may be marked as the instance default. See Error handling and alerts.

O

OpenAPI spec — an imported API description whose operations become callable nodes. Importing one is a distinct feature from the workflow importer, and lives under its own nav entry. See Importing OpenAPI.

Output port — a named socket a node emits from. Ports are semantic rather than positional: a Condition has true and false, an HTTP Request has success and error, and a plain data node has result. Some node types generate their ports from their configuration instead of declaring them in a manifest.

P

Pinned output — a sample payload frozen onto a node so that downstream nodes can be built and tested without re-executing what precedes them. A pin travels with the draft into the published version but is honoured only on manual runs; automatic runs ignore it. See The canvas editor.

Polling trigger — a trigger that fetches a source on an interval and starts a run only when something has changed, using an ETag, a last-modified header, a content hash or a cursor in the response. See Trigger nodes.

Publishing — compiling the draft and, if it compiles, snapshotting it as a new immutable numbered version. The toolbar's Save & Publish button also makes that new version active, so publishing and going live are one action in the common case. See Versions and publishing.

R

Recovery mode — whether a node type retries automatically after a failure or fails immediately. It is declared per node type and follows from the side-effect kind: nodes whose effects are safe to repeat retry, and nodes whose effects are not do not.

Replay — starting a new run seeded from a finished run's state at a chosen node, so that everything upstream is reused and that node onward re-executes. It is not a re-run from the start. You choose which version to replay against and whether to mock side effects. See Runs and the inspector.

Resource locator — a parameter whose choices are loaded live from the server at design time rather than typed, optionally cascading from another field, with a manual-entry fallback when the list cannot be loaded.

Retention — the ageing-out of finished runs, journals, version history and audit entries. Left unlimited the database grows without bound. See Retention and disk space.

Retry policy — the exponential backoff with jitter applied between attempts at a node that is eligible to retry. It is declared by the node type's manifest, not configured per node instance, and a run waiting between attempts is visibly in a waiting-for-retry state.

Run — one execution of one workflow version, recorded step by step in a journal. This is the interface's word; the code and the REST API call the same thing an execution. See Runs and the inspector.

S

Sandbox — the isolation applied to user-authored C#, meaning the Inline Code node and compiled custom packages. It runs that code either inside the main process or in pooled worker processes with memory, CPU and lifetime limits imposed by the operating system. See Sandbox.

Schedule — a persisted cron trigger attached to a workflow. Each individual firing is recorded separately as it is claimed, which is what stops two firings of the same occurrence from producing two runs. See Triggers.

Side-effect kind — whether a node's effect is safe to repeat. This single property drives two visible behaviours: whether the node retries automatically, and whether replaying a run warns you that it is about to fire for real.

Sub-flow — a workflow embedded as a single node inside another. It does not produce a separate run: the compiler splices the child's nodes into the parent's plan with namespaced identifiers, recursively and with cycle detection, so one sub-flow call is still one run. The child must be published before the parent will compile. See Sub-flows and grouping.

Suspended run — a run parked rather than executing, either waiting on a named external event or serving a delay. Suspension frees the worker, which is why long delays do not consume a concurrency slot. See Runs and the inspector.

T

Template — a shareable archive of one workflow, extension .kgtpl, stripped of secrets and carrying authoring metadata, declared credential slots and install-time parameters. Templates come either from a read-only built-in gallery or from the library of ones saved on this instance. See Templates.

Template parameter — a non-secret blank the template's author deliberately left for whoever installs it, referenced inside the workflow as {{ param:<Key> }}.

Time travel — stepping backwards and forwards through a finished run, one node at a time, seeing that node's inputs, outputs and the variable state as it stood when the node began. It reads the journal, so it works on a run that finished days ago. See Runs and the inspector.

Trigger — what starts a run. The implemented kinds are manual, cron schedule, inbound webhook, polling, an external device signal, and the error trigger that begins an error workflow. See Triggers.

Trigger origin — the recorded reason a particular run started, one of manual, schedule, webhook, poll, error, device event, replay or agent. Be aware that the dashboard collapses these into four labels and shows anything it does not recognise as "Manual", so the badge is less precise than the stored value.

V

Variable — a named value scoped to a run, written by the Set Variable nodes and read through {{ $variables.… }}. The editor's Workflow variables panel additionally tracks which node produces each one and which nodes consume it, so an unresolved variable is visible before you run anything. Credentials are a separate, encrypted store and are not variables. See Variables.

Version — an immutable numbered snapshot of a workflow, created by publishing, by restoring an older version, or by importing one. A version that fails to compile is never created. See Versions and publishing.

W

Webhook secret — an optional per-workflow shared secret sent in a request header by an inbound caller. It is checked before anything else about the request, so that an unauthorised caller cannot learn even whether the runtime is armed. A workflow with no secret configured accepts anonymous calls. See Triggers.

Work item — a durable queue row that brings a parked run back to life: resuming it after a delay or an event, retrying a failed node, or delivering a manual decision. It is the reason a suspended run survives a restart.

Workflow — the graph you draw, and the unit you save, publish, share, activate and enable. Enabling is per workflow and separate from instance-wide arming; a disabled workflow fires no triggers and has its in-flight runs cancelled, but can still be run by hand. See Core concepts.

Workflow importer — the wizard that reads another vendor's configuration file through a provider plugin and generates whole workflows from it, complete with a coverage report showing what mapped cleanly and what needs attention. Imported workflows install as inactive versions, so nothing goes live until you activate it. This is a different feature from the OpenAPI import. See Importing configurations.
