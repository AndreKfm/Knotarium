Versions and publishing

Three things share a name in casual conversation and must not be confused: the draft you are editing, the published versions that have been frozen from it, and the one version that is currently active and therefore actually runs. Almost every "my change did not take effect" report is a mismatch between those three, and this page is about keeping them straight.

The three states

StateWhat it isCan it run?
Draft The mutable graph in the canvas editor. One per workflow. Autosaves as you work. Never directly.
Published version An immutable snapshot of the nodes and edges, numbered and dated, kept forever unless retention prunes it. Only once activated.
Active version The single published version currently designated live. Recorded in an append-only activation log. Yes — this is what every trigger executes.

Publishing

Save & Publish in the canvas toolbar freezes the current draft into a new, numbered, immutable version. The button reports what it will do: it reads Saved when there is nothing new to publish, and when the graph has blocking diagnostics it turns amber and counts them, so you cannot publish a broken graph without noticing.

Publishing runs a compile and a runnability gate before writing anything. Three conditions block it outright, each with an explicit message rather than a cryptic runtime failure later:

  • Unbound credential slots. The version references a credential placeholder that is not bound to a stored credential.
  • Incomplete condition nodes. A Condition node was left half-configured.
  • Misconfigured device blocks. A reactive graph has wired-but-untargeted blocks or dead-end wires.

A version that fails to compile is refused with the compiler diagnostics attached, which the editor shows in its diagnostics panel. A version that publishes but still contains pinned test outputs succeeds with a warning naming those nodes — see the caution on the triggers page about what pins do on automatic runs.

Published versions carry an origin that says how they came to exist: Published from Save & Publish, Restored from a restore, and Imported from a bundle or template import. Imported versions are never activated automatically.

Activation

Publishing alone changes nothing about what runs. Activation is the separate act of designating one published version as live, and it is recorded in an append-only activation log with who did it, when, why, which version was active before, and — for a restore — which version it was copied from. That log is what lets the instance answer "what was live at 3 a.m. last Tuesday?" after the fact.

There are three ways to activate a version:

  • Pressing Run in the editor. Run activates the version selected in the toolbar dropdown and then triggers it, every time, so the selection is always what executes.
  • Set active on a row of the runtime-version dropdown. This promotes an existing version in place without running it and without creating a copy.
  • Restore this version from a preview, which copies an old version forward and activates the copy.

Activation applies the same runnability gate as publishing, so a version that was fine when it was published but references a credential that has since been unbound is refused with the reasons listed. If the version's triggers themselves are invalid — a cron expression that no longer parses, for example — activation is rolled back and reported. Two people activating at once produce a conflict rather than a silent last-writer-wins; the message asks you to reopen and retry.

The runtime-version dropdown

The toolbar's version control is a custom list rather than a plain dropdown, because the states it needs to show cannot be expressed by one. Its trigger button shows the selected version number and whether it is ACTIVE or merely being VIEWINGed. Inside, each row shows the version number, a relative timestamp, a dot indicating whether it has ever produced runs, and a badge marking the Active version or, failing that, the Latest one.

The hint at the top of the list names the two distinct actions, because conflating them is the classic mistake: clicking a row previews the version read-only and is completely reversible, while Set active is the commit that changes what runs. Lingering on a row for about a third of a second previews it automatically; closing the list without committing reverts to what you had selected. Selecting the active version simply returns you to the live editable draft.

Version history

Ctrl+Shift+H — Cmd+Shift+H on a Mac — opens the version-history drawer on the right edge of the editor. It fetches only while it is open, so it costs nothing in the background, and it lists metadata rather than whole graphs.

Each row shows the version number, an ACTIVE badge where applicable, the origin badge, the label if one was given, the creation timestamp and author, the node count, and the number of runs that version has produced. Clicking a row opens a read-only preview; hovering it for a moment does the same automatically. A Diff button on each row compares that version directly against your working draft without previewing it first. At the foot of the drawer, Diff draft vs active answers the most common question of all — what have I changed since the version that is currently live? — in one click.

The drawer and a preview are treated as one "version overview": closing the drawer also leaves the preview and returns you to the draft in a single action.

Read-only preview

Previewing a version renders it on the canvas behind a sticky banner reading Previewing version N with a READ-ONLY tag. Editing, autosave and publishing are all disabled while it is up; the live draft is untouched behind it and is never mutated by anything you do in preview.

The banner carries the actions that belong to the mode. Diff compares this version against the working draft. Restore this version makes it the current, live one — hidden when you are already previewing the active version, since there would be nothing to restore. Exit preview, or Esc, returns to the draft. The banner's subtitle changes accordingly: on the active version it just tells you how to leave.

Switching to a different workflow drops any preview or diff in progress, so a read-only snapshot can never leak onto the wrong canvas.

Diffing

The diff panel opens on the right and is titled with its two sides — for example active v3 → working draft. It is computed in the browser from the two payloads, using the same mapper that save and publish use, so the comparison is genuinely apples to apples.

Behavioural changes versus cosmetic ones

The diff enforces one hard rule: behavioural changes are shown, cosmetic layout changes are collapsed. A node that was only moved or resized is not a change to what the workflow does, and letting a tidy-up session drown out one edited field makes the diff useless.

Behavioural changes are nodes added or removed, a node's type changing, any configuration field changing, and connections added or removed. These are listed immediately, each with an added, removed or changed badge, the node identifier, and for a changed node the individual field paths with their before and after values struck through and highlighted. Connection changes name the source node and output port and the target node and input port.

Layout-only changes — position and size — are counted behind a collapsed disclosure reading N layout-only changes (cosmetic), each shown as a moved row. When nothing at all differs, the panel says so explicitly: "No differences — these two are identical (ignoring cosmetic layout)."

The comparison is normalised, and secrets are masked

Before comparing, both sides are canonicalised: object keys are sorted, the visual metadata blob is split out, and empty defaults — null, empty string, empty array, empty object — are dropped, so { retries: 0 } and { retries: 0, note: "" } do not read as a change. Connections are identified by source, output, target and input rather than by generated edge identifiers, so reordering wires reports nothing. Any field whose name looks like a credential, secret, token, API key, password or connection identifier has its value replaced with dots before it is ever rendered — you can see that a credential changed without the diff displaying it.

Restoring an old version

Restore is fork-forward, not rewind. It copies the chosen version's graph into a brand-new version at the top of the history and makes that copy live. Nothing is overwritten and no version is deleted — the history stays append-only, and the version you restored from remains exactly where it was.

The confirmation dialog states this plainly and adds the warning that matters most: a restore affects future executions only. It does not undo side effects already caused by runs of the newer version. Mail that was sent stays sent; rows that were written stay written. Restoring is a way to change what happens next, never a rollback of what already happened.

Confirming produces one of three outcomes:

  • Created version vN — now active. The copy compiled, passed the gate, and is live.
  • Created version vN — inactive forward copy. The copy was created but could not be activated, so it sits in the history as something you can open and fix first rather than leaving you with nothing.
  • An error. A compatibility or compile failure lists the diagnostics to fix; a concurrent activation by someone else reports that and asks you to reopen and try again.

A successful restore may also carry compatibility warnings, listed in the success view. These are the cases where the old graph still compiles against the current node catalog but something about it has drifted, and they are worth reading before you walk away.

After a restore the editor brings the restored graph into the draft as well, so what you are editing matches what is now live rather than silently diverging from it.

How many versions are kept

By default, all of them. Retention__MaxWorkflowVersionsPerWorkflow defaults to 0, which disables the cap; the setting is also editable at Settings › Retention, and the stored value wins over the configuration file. Setting it to a positive number lets the retention sweep keep the newest N versions per workflow and delete older ones.

The cap is deliberately not absolute. Three classes of version are preserved no matter how far past the limit they fall:

  • The active version of every workflow.
  • Anything referenced by the activation log — including the version a restore was copied from and the version that was previously active. These are foreign keys with no cascade, so deleting them would fail rather than corrupt the log.
  • Any version that a retained run executed, which is what keeps replay lineage working.

The practical consequence is that setting the cap to 5 on a busy workflow will not necessarily leave you with five versions. It leaves you with five plus everything still referenced, and the number falls as run history is pruned by Retention__RunHistoryDays. This is a feature: the cap can never delete a version you would need to explain a run you can still see.

Version history survives archiving

Archiving a workflow removes its draft but retains its versions, and the history, detail and active-version reads all keep working afterwards. Permanently deleting an archived workflow is what purges the version history and the activation log, and that is irreversible.

Common mismatches

SymptomCause
An edit has no effect on scheduled runs. The draft was saved but never published, or published but never activated. Use Diff draft vs active to see exactly what is missing.
Run is disabled and the tooltip mentions publishing. The workflow has no published versions yet.
A trigger answers 409 about a missing active version. Versions exist but none has been activated. Use Set active, or press Run once.
The graph in a run does not match the editor. Correct behaviour — the run renders the version it executed, not the current draft.
The diff looks empty after obvious edits. The edits were positional. Expand the layout-only disclosure to confirm.
Restoring did not undo the damage. Restore affects future runs only. Side effects of past runs need their own compensation.
