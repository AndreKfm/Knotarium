Users and sign-in

Cookie sign-in is on by default and the first person to open a new instance is asked to create an administrator. This page covers that first run, the unattended alternative for automated installs, the small user-management panel, the fixed properties of the session cookie, and what actually changes if you turn authentication off. It ends with an honest account of a gap: there is no central place to manage credentials.

First run

With authentication enabled and no accounts in the database, the sign-in screen becomes a setup screen. It is headed Create the first administrator and explains that the instance has no users yet. You supply a username, a password and a confirmation; the two must match or the form refuses with Passwords do not match. Pressing Create admin & continue creates the account, signs you straight in, and drops you into the application.

The account created this way holds the admin role. Setup is only permitted while zero accounts exist — once one exists the endpoint answers with a conflict, so the screen cannot be used to add a second administrator later.

Usernames are normalised to lower case, which makes sign-in case-insensitive and means Admin and admin are the same account rather than two. Passwords must be at least eight characters and are only ever stored as a salted hash. When the framework signals that a stored hash uses outdated parameters, a successful sign-in transparently rehashes it.

The unattended seed

An automated install has no browser to complete the setup screen with, so the first administrator can be seeded from configuration instead. Set both of:

SettingEffect
Auth__InitialAdmin__Username The username of the seeded administrator.
Auth__InitialAdmin__Password Its password. Subject to the same eight-character minimum.

The seed runs during startup, and only when authentication is enabled, both values are non-blank, and no accounts exist at all. When it fires, the log records that an initial admin was seeded from configuration. It is not a way to reset a forgotten password or to add an account to a running instance — on an instance that already has users it does nothing, silently.

A failed seed does not stop startup

If creating the seeded account throws — a name that is somehow taken, a password below the minimum — the failure is logged as a warning and startup continues. The instance comes up with no accounts and therefore shows the first-run setup screen instead. If an unattended install ends up asking a human to create an administrator, that warning in the log is the reason.

Supply the password through a secret store or an environment variable set for the service account rather than a checked-in configuration file. Both keys are listed alongside everything else read at startup in the configuration reference.

The user menu

Once signed in, the application header shows your username, a Users button and a Sign out button. There is no user section under Settings — accounts are reached from the header, which is a small thing worth knowing before you go looking in the wrong place.

The user-management panel

Users opens a modal with three sections.

  • Accounts — every account with its role, the current one marked · you, and a delete button on each row. Your own row's delete button is disabled with the explanation You cannot delete your own account.
  • Add user — a username and password pair with an Add button that stays disabled until the name is non-blank and the password is at least eight characters. Accounts created here are given the user role.
  • Change my password — a single field and a Change button, again gated on eight characters, confirming with Your password was changed.

Listing, creating and deleting accounts all require the admin role on the server, and the reason is direct: without that gate an ordinary user could create an administrator account for themselves and escalate to full control of the host. Changing a password is self-service because it only ever targets the caller's own account — there is no way for an administrator to set someone else's password from this panel.

Two deletions are refused outright. You cannot delete your own account while signed in, which guards against locking yourself out mid-session, and you cannot delete the last remaining account, which guards against locking everyone out permanently.

The panel offers no way to change an existing account's role. Roles are fixed at creation: the first-run administrator and the configuration seed create an admin, and the Add user form creates a user. Those are the only two roles the system recognises, and an attempt to persist any other value is rejected.

The role distinction buys less than it looks like it does

A per-role permission system is not implemented. Only user management and the backup and restore endpoints check for admin. Every other endpoint an authenticated session can reach is unrestricted — including the capability toggle and the Inline Code test endpoint. A user account can therefore enable code execution and run arbitrary code on the host. Treat every account as an administrator until the role model exists.

The session cookie

The cookie's properties are set in code and are not configurable. Knowing them explains several behaviours that otherwise look like faults:

PropertyValueConsequence
Name kg_auth What to look for in browser developer tools when diagnosing a session.
HttpOnly Yes Script on the page cannot read the session, limiting what a cross-site scripting flaw could steal.
SameSite Lax The cookie is not sent on cross-site sub-requests, which is the baseline request-forgery defence.
Expiry 7 days, sliding Continued use keeps a session alive indefinitely; a week of inactivity ends it.
Secure Always, outside development The cookie is never sent over cleartext HTTP in a real deployment.
Plain HTTP outside localhost will look like sign-in failing

Because the cookie is HTTPS-only outside development, a self-hosted instance reached over plain HTTP on a LAN address never keeps a session: the sign-in succeeds, the cookie is discarded by the browser, and the next request is unauthenticated. The symptom is being bounced back to the login screen immediately after signing in. The fix is TLS — normally a reverse proxy terminating it — not a setting.

Because this is an API rather than a server-rendered application, an unauthenticated request gets a plain 401 and a forbidden one a 403 instead of a redirect to a login page. Signing out clears the cookie server-side.

The sign-in rate limit

The sign-in endpoint is rate-limited to ten attempts per minute by default, in a fixed window partitioned by remote IP address, with nothing queued — an eleventh attempt in the same minute is refused with 429 rather than delayed. That throttles online password guessing without being tight enough to bother a person who mistyped twice.

Two caveats. The partition is the remote IP, so behind a proxy that does not preserve the client address every caller shares one bucket and a single noisy client can lock out the rest. And the limit is per minute, not cumulative — it slows guessing rather than locking an account, because there is no account lockout at all. Raise or lower it with Security__RateLimit__LoginPerMinute.

Turning authentication off

Auth__Enabled=false removes the authentication middleware entirely. Every endpoint becomes anonymous — not merely the ones a signed-in user could reach, but all of them, including the capability toggle, the backup and restore endpoints and the Inline Code test endpoint. There is no sign-in and no first-run setup, and the interface does not gate itself behind a login screen.

The admin-only gates become no-ops in that mode, which is consistent rather than a bug: there is no caller identity to check a role against, and every other endpoint is already open.

Because that posture is only defensible on a machine-local instance, startup refuses it on a non-loopback binding. The check, its wildcard handling and the override that lifts it are described on Security model. The short version: if disabling authentication makes the application fail to start, the guard is working and the answer is not to override it.

Credentials: the honest gap

Credentials — the encrypted secrets that nodes reference for API keys, connection strings and passwords — have no management screen. There is no list of them, no way to browse or rename or delete one from the interface, and nothing under Settings that corresponds to them. This is a real gap, not something hidden in a submenu, and it is worth describing exactly so you do not spend time looking.

Where a credential gets created

Inline, from the property form of a node that needs one. The clearest example is the HTTP Request node: choose an authentication type other than none and a field appears labelled Credential (secret) containing a dropdown of existing credentials and a New button whose tooltip reads Create a new credential.

Pressing it swaps the dropdown for a small inline form with two fields — a name, prompted with an example such as a service's API key, and the secret value in a masked field — plus Save credential and Cancel. Both fields are required. Saving stores the secret encrypted, derives an identifier from the name, refreshes the list and selects the new credential in the node you were editing, all without leaving the form.

A hint under the field states the important property: the secret is stored encrypted and referenced by identifier, so it never lives in the workflow definition. That is why exporting or sharing a workflow does not leak its secrets — the definition carries a reference, not a value.

The AI provider screen has the same inline affordance for the same reason: the API key it needs is an ordinary credential, and there is nowhere else to create one.

Where a credential gets used

Everywhere else, by selection only. Any node parameter declared as a credential reference renders as a dropdown labelled with the parameter name and the word Secret, offering Select credential… and the list of what exists. There is no create button on that generic form — if the credential you need does not exist yet, you have to go and create it somewhere that does have one, then come back.

What this means in practice

A secret created by mistake, or one belonging to a service you no longer use, stays in the list and stays in the database. There is no interface for removing it, no view of which workflows reference which credential, and no way to see when one was last used. Saving a credential under a name that derives to an existing identifier overwrites the stored value. Name credentials carefully the first time, because renaming and tidying up are not offered.

Two things do reach the whole set, and both are all-or-nothing. Credentials are carried in an instance backup — decrypted inside the encrypted envelope and re-encrypted on restore — so a restore replaces the entire credential store with the archive's. And every stored secret depends on the .credential-key file: lose it and none of them can be read again. Both are covered on Backup and restore.
