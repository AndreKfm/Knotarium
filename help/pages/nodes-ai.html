AI nodes

Five nodes put a language model inside a workflow: one that runs a single prompt, three that turn a model's judgement into a branch, and one that lets a model call your other workflows as tools. The three branching nodes are the interesting ones — the model does the linguistic work and returns structured data, but the decision about which edge to follow is made by ordinary deterministic code. This page documents every parameter, every port, and where the boundary between the model and the code actually sits.

What every AI node needs

All five nodes call the instance-wide provider configured at Settings › AI Provider — the vendor, the model and the encrypted API-key credential live there, not on the node. Until that is set up, every AI node fails at run time with the same message: "The AI provider is not configured. Choose a provider, model, and API-key credential in Settings › AI Provider." Nothing fails at design time, so a workflow containing AI nodes saves, publishes and looks healthy on an instance that has never been given a key.

Every AI node also declares the network capability, which is descriptive metadata and is not enforced. Outbound provider calls do go through the same egress guard as the HTTP Request node, so Security__HttpEgress__* applies to them — relevant if you point the instance at a locally hosted, OpenAI-compatible model, because DenyPrivateNetworks is on by default and will block it.

The first four are marked as idempotent side effects — a model call changes nothing on the far end — so the engine retries them after a transport failure, three attempts by default with exponential backoff. A retried call may of course return a different answer, which is something any workflow using a language model has to tolerate anyway. The AI Agent is deliberately excluded: its loop can fire side-effectful tools, so a half-finished loop is never re-run.

Every node offers the same two override fields, so they are documented once here rather than in five tables:

ParameterTypeDefaultEffect
model aiModel the configured model Overrides the instance model for this node only. Useful for sending a cheap classification to a small model while a summarization uses a larger one.
maxTokens number the configured cap Overrides the completion token cap for this node only. Values of zero or below, and anything unparseable, are ignored rather than treated as a limit of zero. (On the AI Agent this field is named maxTokensPerCall.)

Single-call nodes

AI Prompt

One model call over the incoming data. Reach for it when a step needs language understanding rather than logic: summarizing a ticket, extracting fields from free text, drafting a reply, classifying something into a value you will use as data rather than as a branch. If the answer needs to choose an edge, use AI Router instead — it is built for that and does not require you to compare strings downstream.

The node runs in one of two modes. Left alone it is a text node: the model's reply is emitted verbatim on result. Fill in jsonSchema and it becomes a structured node: the schema is appended to the system prompt with an instruction to answer with JSON only, the reply is parsed, and the parsed object is emitted instead of the raw string. Parsing tolerates a fenced ```json block, because models add fences often enough that rejecting them would waste the retry on cosmetics.

JSON mode gets exactly one repair pass

If the reply does not parse, the node sends the task again with the broken output and the parse error attached and asks for corrected JSON. If that also fails to parse, the node fails with "the model did not return valid JSON after a retry". The retry is capped at one because a node run is on the hot path — a schema the model reliably cannot satisfy will cost you two calls and then fail, every single run.

The schema is not enforced

A reply that is valid JSON but does not match your schema is accepted and passed downstream. If a downstream node depends on a field being present, check for it — do not assume the schema guaranteed it.

Branching nodes

AI Router, AI Verify and AI Semantic Diff are three of the seven node types in Knotarium that select a single outgoing branch rather than following every edge. Each emits an internal selectedPort value, and the engine schedules only the edges whose handle matches it. Draw one edge per branch you care about; branches with no edge simply end that path.

The selected port wins over every other routing rule. An ordinary node skips its error and failure handles when it succeeds, but that rule does not reach a node which routes by selected port, so an AI Router category you legitimately named error is followed like any other category.

AI Router

Classifies the incoming text into one of the labels you list, and routes the run down the matching branch. Reach for it when the decision is genuinely linguistic — "is this support email a bug report, a billing question or spam?" — and a Condition or a Switch would need a pile of brittle keyword matching to approximate it.

This node's output ports are dynamic

The manifest declares no outputs at all. The canvas derives the handles from the node's own categories property: one port per label, in the order you wrote them, followed by a fixed otherwise port. Editing the categories field re-draws the handles, and an edge attached to a label you deleted no longer has anywhere to come from. Because the manifest is output-less, the compiler skips socket validation for this node — a mis-wired router is not caught at publish time.

Labels are parsed by splitting on commas, semicolons and newlines, trimming each piece, dropping empty ones, and removing case-insensitive duplicates while keeping the first spelling you used. The canvas and the runtime use identical rules, which is what guarantees the handle you drew from is the port the run will actually take.

Matching is forgiving in the ways models are sloppy and strict everywhere else: the reply is trimmed, surrounding straight or curly quotes are stripped, a trailing period is removed, and the comparison is case-insensitive. The label is then reported back in the configured spelling, because that is what the canvas edges reference. Alongside the routing decision the node emits category (the matched label, empty when it fell through) and reply (the raw model text), which is what you inspect when a route looks wrong.

An unroutable answer is not an error

If the model answers with something outside the list, the node retries once with the off-list answer quoted back. If it still does not match, the run takes otherwise rather than failing — a wrong route is a routing concern, not an exception. Always wire otherwise to something; an unwired fallback silently ends that path.

AI Verify

An evidence gate. Give it a piece of content and the sources it is supposed to be based on, and it checks the content's factual claims against those sources claim by claim, then routes by the overall verdict. The obvious use is guarding an AI-generated draft before it is sent or published: generate with AI Prompt, verify against the retrieved source documents, and send only down the verified branch.

The verdict is code, not a second opinion

This is deliberately not "ask another model whether the first one looks right". The model is only asked to do what models are good at — extract each distinct claim and map it to source passages — and it must return structured JSON. Two rules are then applied in ordinary code:

The evidence rule. A claim the model labelled "verified" but backed with no evidence item marked as supporting is downgraded to unsupported. No evidence never means "probably true".

The aggregation rule. The overall verdict is the worst per-claim status present, by severity: contradicted beats unsupported, which beats uncertain, which beats verified. It is computed from the parsed claim list, never read from a summary label the model wrote. A reply containing no claims at all is uncertain, because nothing was actually checked.

ParameterTypeRequired{{ }}Effect
contentstringyesyesThe text whose factual claims should be checked — typically the output of an upstream AI Prompt node.
sourcesstringyesyesThe reference material. Plain text is treated as a single source with the id source-1. A JSON array of {id, content} objects gives each source a real id the model can cite; sourceId and text are accepted as alternative key names, and a bare array of strings becomes source-1, source-2 and so on.
instructionsstringnoyesDomain rules — what counts as a claim worth checking, what counts as material in your context.

Unlike AI Router, these four ports are declared in the manifest, so the compiler validates the wiring normally. Alongside the branch, the node emits the full audited record on result: the overall status, the model override string that was in effect (empty when no override was set — it does not report the instance-wide model), a promptVersion of verify-1 that pins which instructions did the judging, and the complete claims array with per-claim status and cited evidence. Because the engine journals node outputs, that record is the replayable verification trail.

A malformed reply is a failure, not a verdict

If the model does not return a JSON object containing a claims array, the node retries once with the parse error fed back and then fails. It never falls through to uncertain — a broken response is not evidence of anything, and treating it as a soft verdict would let a flaky model quietly gate your content.

AI Semantic Diff

Compares two versions of a document by meaning rather than by characters, and routes by whether anything meaningful actually changed. The use it is built for is watching something that gets re-published constantly with cosmetic churn — terms of service, a supplier price list, a policy page — and only waking a human when a deadline, a number or an obligation moves.

Identical input never reaches the model

Before anything else, the node compares the two inputs after trimming surrounding whitespace. If they are identical it routes straight to none with no model call at all — no tokens, no latency, no cost. For a poller that runs every few minutes on a page that rarely changes, that short-circuit is the difference between a workflow you can afford to run and one you cannot.

As with AI Verify, the routing decision is computed in code from the parsed lists: any material change means material; otherwise any ignored change means cosmetic; otherwise none. The auditable record on result carries changeType, impact (the highest impact among the material changes — high, medium, low, or empty when there are none), model, a promptVersion of diff-1, the materialChanges array (each with a snake_case type, the old and new values and an impact) and the ignoredChanges descriptions.

Unknown impact levels become "medium"

A change whose impact the model reports as critical or major is normalised to high, and minor or trivial to low. Anything else — including a blank or an invented level — becomes medium. So medium means both "genuinely medium" and "unclassified"; do not read too much into it when triaging.

The agent loop

AI Agent

A bounded tool-use loop where the tools are your own workflows. You give the agent a task and an explicit list of workflows it may call; on each turn the model either answers or asks to call one of those workflows with arguments, the workflow runs as a real journaled child run, and its projected outputs are fed back for the next turn. Reach for it when the sequence of steps genuinely cannot be drawn in advance — "find out why this order is late", where the answer might need the order lookup, or the shipment lookup, or both, depending on what the first one returned. When the sequence is known, draw it; a fixed graph is cheaper, faster and reproducible.

Off until an administrator turns it on

The node checks the aiAgent capability first and fails immediately with "AI Agent is disabled: the 'aiAgent' capability is off" when it is not enabled. Turn it on at Settings › Capabilities, where the row is labelled AI agent tool loop. It sits alongside code execution and database access as a privileged capability for a reason: enabling it means a model gets to decide which of your workflows run, and with which arguments.

A failure surfaces through the normal node-failure path, so an error edge or a workflow-level error handler catches it.

Defining a tool

Each entry in the allowlist binds one of your workflows to a model-facing name. The name must be 1–64 characters of letters, digits and underscores; duplicates and empty target workflows are rejected when the node starts rather than at the first call, so a misconfigured agent fails fast.

FieldEffect
target workflowWhich workflow this tool runs. Its published, active version is what executes.
nameWhat the model sees and calls. Letters, digits and underscores only.
descriptionThe only thing telling the model when this tool is the right one. Vague descriptions are the usual cause of an agent calling the wrong workflow.
parametersName, type (string, number, boolean; anything else is treated as string), required flag and description. Each validated argument is seeded as a global in the child run, so the tool workflow reads it as an ordinary variable.
outputsWhich globals are read out of the finished run and returned to the model. A name that does not exist comes back as null and is listed under __missing, so the model can react rather than silently seeing nothing.

Arguments are validated in code before a tool ever runs: keys the binding does not declare are dropped, every required parameter must be present, and types are checked, never coerced — the string "3" for a number parameter is rejected. A rejected call is not a node failure; it is returned to the model as a tool error it can correct on the next turn. The same is true of a tool that runs and fails: the model hears "it failed" and may retry differently or give up, while the failed child run is journaled and dead-lettered exactly like any other failed run.

What a workflow must look like to be a tool

Eligibility is checked at call time, not at design time, so an ineligible workflow shows up as a tool error in the run rather than as a validation message on the canvas. A workflow must:

  • have a published, active version — an unpublished draft is not callable;
  • exist, not be archived, and be enabled;
  • begin with a plain Start node, and contain no Webhook, Polling, Cron Scheduler or Error trigger. A tool has to be a callable function, not an event handler;
  • contain no AI Agent node of its own.

The no-nested-agent rule is enforced twice. The tool workflow's nodes are inspected before the child run is created, and separately, any run that was itself started as a tool is forbidden from spawning further tool runs. The recursion depth is therefore capped at one: your agent may call your workflows, and those workflows may not call agents.

Tool runs execute synchronously inside the parent's run slot rather than being queued, so an agent does not deadlock on an instance configured with a single concurrent run — but it does mean the child's cost is honestly charged to the parent's slot and its timeout. Results handed back to the model are capped at 16 KiB of UTF-8; an oversize result is replaced by a truncated preview with an explicit marker so a chatty tool cannot blow up the context.

Why an injected instruction is contained

Everything an agent reads is untrusted: the task may contain data from a webhook, and tool results come from workflows that fetched who-knows-what. The default preamble tells the model to treat all of it as data, but a prompt instruction is a mitigation, not a boundary — assume it can be talked around.

The actual containment is structural, and it is worth stating precisely because it is what makes the node safe to enable. An injected instruction can, at worst, steer the agent within the tools you listed and its iteration budget. It cannot introduce a tool that is not on the allowlist — an unknown tool name is answered with a tool error. It cannot pass an argument shape the binding did not declare, because arguments are schema-validated in code. It cannot reach a webhook- or schedule-triggered workflow, because those are ineligible as tools. It cannot recurse into another agent. And it cannot run forever, because maxIterations and tokenBudget are enforced by the loop rather than requested of the model.

Which turns the security question into a design question you can actually answer: if an attacker controlled the task text, what is the worst sequence of the tools I listed? Keep the allowlist to the smallest set that does the job, prefer read-only workflows as tools, and put anything irreversible behind a human approval step rather than behind a tool binding.

OpenAI reasoning models cannot drive the tool loop

Reasoning models such as the GPT-5 family reject function tools on the OpenAI Chat Completions API unless reasoning effort is switched off. Knotarium adapts automatically: it sends the request without the parameter, and on the specific rejection it retries once with reasoning effort set to none, remembering the model so later turns skip the wasted round-trip. If the call still fails while tools are in play, the node reports an actionable error rather than a raw HTTP status: the AI Agent needs a tool-capable model. Set a per-node override such as gpt-4o or gpt-4.1, or choose a non-reasoning model at Settings › AI Provider. Full reasoning-model tool support is a planned follow-up, not a current capability.
