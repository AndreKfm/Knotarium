Runtime arming

Arming is the one switch that separates design time from run time. While the runtime is disarmed, nothing starts a workflow except you; while it is armed, schedules, webhooks, polls and inbound device signals are all live. It is a single global switch — there is no per-workflow arming — and it is deliberately sticky: several things turn it off automatically, but nothing ever turns it back on for you.

Where the switch lives

The control is the pill button in the application header, to the right of the navigation. It has exactly three appearances: Armed in green with a filled shield while automatic execution is enabled, Disarmed in amber with a crossed-out shield while it is paused, and a muted Runtime… label during the brief moment after page load when the current state has not arrived from the server yet. The button is disabled while it is loading and while a change is in flight, so a double click cannot leave the interface and the server disagreeing.

Changing the switch is an administrator action. It is the master enable for anonymous webhook and external triggers, so a signed-in user without the administrator role is refused — the button is present but the request comes back denied. On an instance with authentication turned off the role check is a no-op and anyone can flip it.

What arming actually gates

Automatic execution requires two independent conditions to be true, and it is worth being precise about which is which. The runtime must be armed, and the individual workflow must be enabled. Disabling a single workflow does not disarm the instance, and disarming the instance does not disable any workflow — they are separate switches that both have to allow a run through.

Every automatic start path consults the switch:

Start pathBehaviour while disarmed
Cron scheduler The scheduling loop still ticks every ten seconds but skips schedule evaluation entirely. Nothing is queued and no schedule is advanced.
Polling trigger The polling loop skips evaluation the same way. No HTTP request is made, so the change-detection cursor does not move either.
Inbound webhook The request is rejected with HTTP 409 and the message "Runtime is disarmed. Arm the runtime to allow external triggers."
External device signal The provider subscription stays connected — the signal arrives and is then dropped without starting a run. Reactive rules that dispatch an effect straight back to the device are suppressed in the same way.

Manual start paths are not gated. Running a workflow from the editor, firing a scheduler node by hand from the run inspector, and firing a device pin from the Simulate signal dialog all work on a disarmed instance. That is the point of the switch: you can build and test freely without any chance of the same graph also firing on its schedule while you edit it.

The webhook secret is checked before the arming state

When a workflow has a webhook secret configured, an inbound request that presents the wrong secret is refused with 401 before the arming check runs. A caller who is not authorised therefore cannot use the difference between 401 and 409 to discover whether your instance is currently armed.

The state is stored in the database

When you flip the switch, the new value is written to the application settings table under the key that records runtime arming. On the next start-up — after the schema migration and before any worker begins evaluating anything — that stored value is read back and applied. An instance you armed once stays armed across restarts, upgrades and service recycles.

The precedence is worth memorising, because it explains almost every "why is my configuration being ignored" question about this setting:

  1. The persisted value, if one has ever been written by the switch.
  2. Otherwise the configuration seed Runtime__Armed.
  3. Otherwise disarmed.
Runtime__Armed is a first-boot seed, not a setting

Runtime__Armed=true exists so an unattended deployment can come up armed on its very first start without anybody opening a browser. The moment the switch is used once — by a person, or by the editor's automatic disarm described below — the stored value wins and the configuration key stops having any effect at all. Editing it on a running instance and restarting changes nothing, silently. If you need to force an instance back to a known state, use the switch, not the configuration file.

Opening the editor disarms the runtime

Navigating into the canvas editor automatically disarms the instance. The rule is precisely "on entering the editor from any other screen" — moving between workflows inside the editor does not re-trigger it, and leaving the editor does not undo it. Re-arming is always a deliberate, manual click on the header switch.

This is the behaviour that surprises people most, so it is worth stating its two consequences plainly. First, the automatic disarm goes through the same endpoint as a manual one, so it is persisted. If you open a workflow to read it, close the browser and never touch the switch, the instance is still disarmed the next morning and after the next restart. Second, because it happens on navigation rather than on editing, merely looking at a graph is enough to stop your production schedules.

Check the switch before you walk away

The single most common cause of "my scheduled workflow stopped running overnight" is an editor visit earlier that day. The header pill is the fastest way to confirm: if it reads Disarmed, no schedule, poll, webhook or device signal has started a run since it turned amber.

The editor makes the state visible where it matters. On an event-driven device graph, the Watch live runs button explains in its tooltip that the runtime is disarmed and that new live runs will not arrive until you arm it in the header. And when the instance transitions to armed while a graph is open, the canvas re-frames the whole workflow — arming is treated as a deliberate "go live" moment, so it shows you the entire thing you just made live.

The low-disk guard disarms and stays disarmed

A background guard samples free space on the volume holding the data directory. When free space falls below the floor, it disarms the runtime so that no new automatic run starts, and it logs at critical level: every run writes many journal rows, and a database that runs out of room mid-write is a much worse failure than a paused schedule.

The policy is read live from Settings › Retention on every check, so changing it applies from the next tick without a restart. Where nothing has been stored there, the configuration section supplies the fallback:

SettingDefaultEffect
Storage__MinFreeSpaceMb 256 Free-space floor in megabytes. Zero disables the guard entirely; the loop keeps running so that switching it back on later takes effect without a restart.
Storage__FreeSpaceCheckSeconds 60 How often free space is sampled. Values below 30 seconds are raised to 30. The first check happens one full interval after start-up, so a short-lived process never trips the guard.

Recovery is deliberately not automatic. When free space climbs back above the floor the guard logs a warning saying the instance was disarmed by the disk-space guard and that it is now safe to re-arm — and then does nothing else. Re-arming is an operator decision, because the guard has no way of knowing whether the space was freed by fixing the underlying problem or by something that will fill it again in an hour.

A guard disarm is not written to the database

Only the arming endpoint persists a value. The guard changes the in-memory state alone, on purpose, so that a transient low-disk blip cannot permanently disarm an instance. The visible consequence is that restarting the process restores the last state you chose explicitly: an instance you armed comes back armed, and if the disk is still full the guard disarms it again on its next check. Do not use a restart as a way to clear a disk-space disarm — free the space first.

Other things that read the switch

Restoring a backup is refused while the runtime is armed. The restore replaces all current state, so it insists that nothing can be firing mid-restore; the restore panel makes disarming the first of its guided steps and blocks the confirmation until the switch reads Disarmed. This is checked before any decryption or write, so a refused restore leaves the existing data untouched.

Reading the state without the interface

The current value is exposed as a plain read for monitoring. A one-field JSON response with an armed boolean is what the header pill itself renders, and it is the honest answer to "is this instance live?" — far more reliable than inferring it from whether runs are appearing.

Troubleshooting

SymptomLikely cause
Manual runs work, scheduled runs do not. Disarmed. Manual paths bypass the switch entirely, which is exactly what makes this symptom diagnostic.
A webhook caller gets HTTP 409 mentioning the runtime. Disarmed. A 409 that mentions deactivation or a missing active version is a different problem — the workflow is disabled or has never been published and activated.
The instance disarms itself repeatedly. Either the low-disk guard is tripping — check the logs for the critical free-space message — or somebody is opening the editor.
It came up disarmed despite Runtime__Armed=true. A persisted value exists and wins. Arm it once with the switch; that value then survives restarts on its own.
The switch does nothing when clicked. The signed-in account is not an administrator, or a previous request is still in flight and the button is temporarily disabled.
