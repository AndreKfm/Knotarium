Data nodes

Three nodes sit in the Data category, and the palette shows them under Data unchanged. Transform pulls one value out of a JSON payload, Merge concatenates two arrays, and Resource Picker turns a design-time choice from a remote system into a value the workflow can rely on. Only Resource Picker touches the network, and only it can fail for reasons outside your graph.

Reshaping data without a node

Before reaching for a node, remember that most extraction can be done inline. Any parameter whose Expr flag is set accepts {{ }}, and expressions already walk into objects and arrays: 

{{ $node.httpRequest-1.output.body }}
{{ $variables.customer.email }}
{{ $variables.rows[0].id }}

A Transform node earns its place when the extracted value is used by several downstream nodes, when you want the extraction to appear in the run inspector as its own step, or when a missing value should stop the run rather than quietly resolve to nothing.

Transform

transform · Data · timeout 10

Takes a JSON document and a path, and emits whatever the path selects. Reach for it to lift a record out of an API response before branching on it, to pull the array out of a paged envelope so a loop can iterate it, or to reduce a large payload to the one field a later node needs.

inputJson is expression-enabled, which is how the document gets in — normally a reference to an upstream node's output. If the value arrives as a JSON string it is parsed first; if it is already a structured value it is queried directly. A string that is not valid JSON is treated as a plain string literal, and any path into it then finds nothing.

jsonPath is not expression-enabled. It is a literal path, written once and fixed for the life of the node.

The path grammar

Despite the parameter name, this is not full JSONPath. It is a deliberately small dotted-path navigator, and knowing its exact shape saves a lot of guessing:

  • Segments are separated by . — data.customer.email.
  • A segment may be followed by [n] to index into an array — items[0], rows[12].
  • Indices are whole numbers only. There are no wildcards, filters, slices, recursive descent or string-key brackets.
  • There is no leading $. Writing $.data.items makes the navigator look for a property literally named $ and find nothing.
  • Every segment must resolve through an object. A path cannot begin by indexing a document whose root is an array: [0].name finds nothing, because the first step has no property name to follow.

Worked examples

A paged HTTP response, and the two extractions you almost always want from one — the array to loop over, and a cursor to decide whether to poll again: 

// inputJson — {{ $node.httpRequest-1.output.body }}
{
  "data": {
    "items": [
      { "id": 4711, "email": "ada@example.com", "state": "open" },
      { "id": 4712, "email": "grace@example.com", "state": "closed" }
    ],
    "nextCursor": "eyJwYWdlIjoyfQ"
  }
}

// jsonPath: data.items         -> the whole array, ready for a For Loop
// jsonPath: data.nextCursor    -> "eyJwYWdlIjoyfQ"
// jsonPath: data.items[0].email-> "ada@example.com"
// jsonPath: data.items[9].id   -> nothing: index out of range, the node fails
// jsonPath: $.data.items       -> nothing: no property named "$"

A Database Query result, where the useful value is one field of one row — a shape worth recognising because the rows array is nested inside the node's result object: 

// inputJson — {{ $node.dbQuery-1.output.result }}
{ "rows": [ { "id": 88, "owner": "team-a" } ], "rowCount": 1 }

// jsonPath: rowCount        -> 1
// jsonPath: rows[0].owner   -> "team-a"

And a mailbox poll, where the whole point is to reach into the first message: 

// inputJson — {{ $node.imapFetch-1.output.result }}
{ "messages": [ { "subject": "Invoice 2026-114", "from": "billing@example.com" } ], "count": 1 }

// jsonPath: messages[0].subject -> "Invoice 2026-114"
// jsonPath: count               -> 1

A path that selects nothing is an error, not an empty result. That is usually what you want — a renamed field in an upstream API stops the run at the node that noticed, instead of letting a null travel three nodes further and fail somewhere confusing.

ParameterTypeRequiredExprNotes
inputJsonstring Yes Yes The document to query. A JSON string is parsed; a structured value is used as-is; anything else becomes a string literal.
jsonPathstring Yes— A literal dotted path with optional [n] indices. No $ prefix, no wildcards.
PortTypeFires when
successobjectThe path resolved. Carries the selected value.
errorstringThe input or the path was missing, or the path selected nothing.
Transform has no executor in this build

No task implementation is registered for the transform type, so a run that reaches one fails the node with No task implementation registered for type 'transform'. The failure is loud and journalled, but it happens at run time — the workflow publishes and validates cleanly. Until that changes, do the extraction inline with a {{ }} expression on the consuming node's parameter, or in an Inline Code node when the reshaping is more than a single lookup.

Merge

merge · Data · timeout 10

Combines two arrays into one. Reach for it after a fan-out where two branches each produced a list and the continuation wants a single collection to iterate — results from two pages, two regions, two systems.

Both inputs are expression-enabled strings, which in practice means each holds a reference to an upstream array. Neither is required, so a node with one side wired is accepted rather than rejected. There is no key matching, no de-duplication and no field-level joining: this is concatenation, and two records describing the same entity stay two records.

When you need a genuine join — matching on an id, merging fields, de-duplicating — use Inline Code, where the rule can be written explicitly. For the common case of collecting the outputs of several branches that all ran, Join is the better fit: it waits for the branches and returns them in order, with nothing to configure.

ParameterTypeRequiredExprNotes
array1string No Yes The first array, normally a reference to an upstream output.
array2string No Yes The second array. Appended after the first; order is preserved.
PortTypeFires when
successarrayThe combined array.
errorstringAn input could not be read as an array.
Merge has no executor in this build

As with Transform and Switch, no task implementation is registered for the merge type, and a run reaching one fails with No task implementation registered for type 'merge'. Concatenate in an Inline Code node, or restructure the graph so a Join collects the branches instead.

Resource Picker

resourcePicker · Data · timeout 30 · capabilities network, credentials · retried automatically

Lets you choose a value from a live list on a remote system while you are editing, and then emits that choice at run time. Reach for it when a workflow needs a specific project, queue, folder or mailbox and you would otherwise paste an opaque identifier into three different nodes and hope it stays correct. Pick it once, promote the result to a workflow variable, and reference the variable everywhere.

The value it emits is not a stored copy. At run time the node re-resolves the saved stable key against the current list, so the value and label that reach the rest of the workflow are fresh. That is the whole design: a resource that has been deleted, renamed or has become ambiguous fails the node closed, with a message naming the problem, rather than passing a stale identifier to a system that will do something unexpected with it.

It fails closed for configuration too. No server configuration selected, no collection path, or nothing picked each stop the node with an explicit message before any request is made. Because its side effect is idempotent and its recovery mode asks for retry, a transient network failure is retried automatically — up to three attempts, two seconds apart, doubling.

labelField and valueField tell the loader which fields of each record to show and to store. They default to name and id respectively when left empty, which fits most REST collections. As everywhere else, the form shows them blank rather than pre-filled.

None of its parameters accept expressions. The point of the node is a choice made at design time against a real list; a computed path would defeat the picker and the design-time validation that comes with it.

ParameterTypeRequiredExprNotes
serverConfigIdstring No— Which configured server to query. Not flagged required in the manifest, but the node fails without it.
pathstring No— The collection endpoint to list. Also required in practice.
labelFieldstring No— Field shown in the picker. Defaults to name.
valueFieldstring No— Field stored as the stable key. Defaults to id.
selectionresourceLocator No— The chosen resource, held as a stable key plus a display label. Empty means the node fails with "nothing selected".
PortTypeCarries
resultobjectThe declared port, and the one the canvas draws a handle for.

The values themselves are exposed as three named fields, which is what you reference from another node's parameter:

FieldCarries
valueThe stable key — the identifier to send to the remote system.
labelThe display name, for logs and notifications.
recordBoth of the above in one object, for a node that wants the whole pick.
 
{{ $node.resourcePicker-1.output.value }}
{{ $node.resourcePicker-1.output.label }}
Reference the fields, do not rely on the wire

The node's declared port is result, but the values it publishes are named value, label and record. An edge drawn from result into a downstream input therefore carries nothing — the port name and the field names do not meet. Wire the edge for ordering if you like, but read the value with an explicit {{ $node.<id>.output.value }} expression, or promote it to a workflow variable and use that.
