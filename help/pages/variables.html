Variables

A variable is a named value that any node in the workflow can read, regardless of whether it is wired to the node that produced it. Variables are how data reaches a branch that control flow never touched, how a loop accumulates a result, and how a sub-flow hands something back to its caller. This page covers the two nodes that write them, the path syntax for nested writes, what the Variables panel is and — importantly — is not, and how far a variable's lifetime extends.

Scope: one run, not one installation

The word "global" appears throughout the interface, and it means global within this run. Every execution starts with its own variable bag, seeded by whatever started it, and nothing carries over from the previous run. There is no installation-wide key/value store behind this feature; if you need a value to survive between runs it has to live somewhere real, such as a file or a database.

The bag is snapshotted as the run progresses: the run record keeps the final state, and each node's journal entry records the variables as they stood immediately before that node executed. That is what makes the run inspector able to show you variable history after the fact.

Two places where the scope narrows further

Inside a sub-flow, variable names are silently rewritten with a per-call prefix so two uses of the same sub-flow cannot collide. A write inside a sub-flow is therefore invisible to the caller unless it is routed through the sub-flow's declared outputs — see Sub-flows and grouping. Inside a Parallel For Each body, each iteration gets its own copy of the variables, so writes made in one iteration are not seen by the others.

The Set Variable node

Set Variable (category Utility) writes one value. It has two fields:

FieldExpressionsEffect
variableName No The name to write, or a path into a nested structure. Taken literally — a {{ … }} expression here is not evaluated and becomes part of the name.
value Yes The value to store. Evaluated before the node runs, so it may be a literal or any expression.

A Set Variable node with an empty name does nothing at all and reports success — it is not an error. Writing null into a plain (non-path) name removes the variable rather than storing a null, which matters if a later node tests for its presence.

The Set Variables node

Set Variables writes several at once from a list of name-and-value rows. It exists so that initialising six values does not need six nodes in a chain. Each row's value is expression-enabled, and each row's name follows the same path rules as the single node.

Rows are applied in order, and the rules for a bad row differ depending on what is wrong with it:

  • A row with a missing or blank name is skipped silently. Nothing is written and nothing is reported.
  • A row whose write conflicts structurally with what is already stored fails the node — and the rows before it stay applied. There is no rollback, so a partially applied Set Variables node is a state you can genuinely end up in.

On success the node's result carries a count of the rows it wrote, which can be referenced as {{ $node.<id>.output.count }}.

Writing into a nested path

The name field is not restricted to a plain identifier. It accepts the same path grammar used for reading, so a single node can reach into a structure: 

# Head only — an ordinary variable
counter

# Member access, two equivalent spellings
myDict.name
myDict["name"]

# Array index
list[0]

# Chained freely
config.servers[2].host

The head — everything before the first . or [ — is the variable that actually exists. Writing myDict["name"] creates or updates a variable called myDict; there is no variable called myDict["name"].

What is created for you

  • Missing containers are built automatically, and their kind is inferred from the next segment: a following index makes an array, anything else makes an object. So config.servers[2].host against a variable that does not exist yet produces an object containing an array containing an object.
  • Arrays grow to fit. An index past the end is not an error — the array is padded with nulls up to that position. Writing list[1] into an empty array gives [null, value].
  • Siblings survive. Writing myDict["b"] when myDict already holds { "a": 1 } leaves a alone.

What fails

A write fails when it contradicts the shape already stored — asking for a member of a number, or an index of an object. The node fails with a message naming the variable and the conflict, for example Set Variable 'myVar["a"]': Cannot navigate by member: the variable's current value is not an object. The four conflict messages distinguish navigating by member versus by index, and at the head versus deeper in the path.

A malformed path is not an error — it becomes a name

If the path cannot be parsed at all — an unterminated bracket, a doubled dot, a negative or non-numeric index, a quoted key that is never closed — the write does not fail. It falls back to creating a variable whose literal name is the whole string you typed. So a typo like orders[0 quietly produces a variable called orders[0 that nothing will ever read. If a nested write appears to have done nothing, look for it as a flat name in the run's variable snapshot.

One consequence worth knowing: after any path write, the head variable is stored as a JSON structure. A plain write stores the raw value as it was. This is invisible in almost every case but explains why the same variable can read back slightly differently depending on how it was last written.

The Variables panel

The lower right panel of the canvas, titled Workflow variables, is the editor's view of the store. Each card shows a variable's name, a type sigil, its last known value, the node that produces it and the nodes that consume it.

SigilType
""string
#number
?boolean
{}dictionary
[]array

A variable is either awaiting run or resolved. Running the workflow from the editor fills the resolved values in place, without leaving the canvas.

Two kinds of entry

Declared entries carry a small declared badge. They are derived automatically from the Set Variable and Set Variables nodes on the canvas — and from a sub-flow's declared inputs and outputs while you are editing it — so they appear and disappear as you edit those nodes. They cannot be renamed or deleted from the panel; edit the node instead. A keyed write contributes its head container, with the object or array glyph inferred from the path syntax and no design-time value.

Promoted entries are ones you registered yourself by dragging a node's output pill onto the panel's drop zone. These can be renamed and deleted. Names must be unique (compared case-insensitively) and must look like an identifier — a letter or underscore followed by letters, digits or underscores. Rejected renames report Name cannot be empty, Invalid variable name or Name already exists, and a duplicate registration flashes the conflicting card red rather than adding a second entry.

The panel's list lives in your browser, not in the workflow

Promoted entries are stored in browser local storage, keyed by workflow. They are not part of the workflow definition, so they do not travel with an export, do not appear for a colleague opening the same workflow, and are lost if the browser's storage is cleared. Declared entries are safe because they are recomputed from the canvas every time.

What is saved into the workflow is the effect of using a variable: a reference bound onto a node's field, or a name written by a Set Variable node. Losing the panel entry does not break a running workflow — it only removes the pill from the editor.

Dropping an output into the store

Dragging an output pill from a node card onto the panel's drop zone — labelled Register New Variable, and Drop Node Output Here while you hover — promotes that output to a named variable. The proposed name is <nodeId>_<outputName>. Dropping the same output again returns the existing entry rather than duplicating it.

That naming convention is not cosmetic. When a variable cannot be found in the run's bag, the runtime falls back to interpreting its name as nodeId_outputName (split at the last underscore) and reads that node's recorded output directly. This is what makes a promoted output resolve at run time even though no node ever wrote it into the bag.

Renaming a promoted output breaks that fallback

Rename fetch-user_result to user and the fallback no longer matches: at run time user is looked up in the variable bag, finds nothing, and resolves to empty — unless a Set Variable node actually writes a variable of that name. Renaming also does not rewrite references that are already bound to nodes, so an existing binding keeps pointing at the old name and carries on working while any new binding to the renamed variable silently resolves to nothing.

If you want a friendly name, do not rename the pill — add a Set Variable node that writes user from {{ $node.fetch-user.output.result }}. That is a real write into the bag and behaves predictably everywhere.

Using a variable in a node

There are two ways to consume one, and they are not equivalent.

  • Drag the variable pill onto a node. This stores a structured reference on the node's primary input field. At run time it is resolved by looking the name up in the variable bag, including a dotted path into a structured value such as an inbound signal.
  • Type an expression such as {{ $variables.customerId }} into any expression-capable field, as described in Expressions and data.

Both work. The difference shows up in the editor: the dashed data wires drawn between a variable's producer and its consumers, and the Consumers list on the variable card, are built by scanning node properties for dropped references only. A variable used through a typed expression is read perfectly well at run time but is not counted as a consumer and draws no wire — so an empty consumer list is not evidence that a variable is unused.

The wires themselves are drawn dashed and coloured by type, with a value token or a small diamond at the midpoint depending on the data-wire density setting described in The canvas editor. Hovering a node, a variable card or a wire highlights the whole relationship; clicking pins it so it stays visible.
