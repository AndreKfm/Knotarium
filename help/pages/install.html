Install and run

Knotarium is one process with an embedded database, so installing it is mostly a question of how you want it started and where you want its data. There are five paths — a container, a Windows installer, a zip you unpack anywhere, a Linux service, and running from source — and they all end at the same place: a browser pointed at port 43120 asking you to create an administrator.

Choosing a path

The paths differ in who starts the process and whether anything is written outside the application folder. Nothing else about them differs — the same binary, the same database format, the same features.

One port to remember

43120 is the default everywhere — the Dockerfile's EXPOSE, the installer's service registration, the systemd unit, the launcher script written into the zip, and the development launcher all use it. When something is not reachable, the port is rarely the reason.

Container

The published image is multi-architecture — linux/amd64 and linux/arm64 are both built and pushed — so the same tag works on an ordinary server and on an ARM single-board machine. It is a framework-dependent build on the mcr.microsoft.com/dotnet/aspnet:10.0 base image, with the compiled React interface and this help site copied into wwwroot so everything is served from one origin. 

# Pull and run the prebuilt image
docker run -d --name knotarium -p 43120:43120 \
  -v knotarium-data:/data ghcr.io/andrekfm/knotarium:latest

The left half of -p 43120:43120 is the host side and is yours to choose. Serving the interface on port 8080 is a matter of writing -p 8080:43120; the application's own configuration does not change, and neither should it, because the container's internal port is baked into the image's environment.

Image tags

TagMoves when
:latestA stable version is tagged — one with no hyphen in it.
:edgeA pre-release is tagged, meaning a version containing a hyphen such as 1.0.0-rc.15.
:<version>Never. Every release publishes its exact version as an immutable tag.

While the project is in its pre-release phase, :latest can lag a long way behind :edge, because it only moves on a stable tag and there has not been one. Pin an exact version for anything you care about.

Compose

The docker-compose.yml in the repository root builds from source rather than pulling the published image — its service declares build: . and tags the result knotarium:local. That is the right thing when you have the repository checked out and want your working tree running, and the wrong thing when you just want the released build. Use the docker run above for the latter. 

# Build the working tree and run it
docker compose up --build

The Compose file understands three shorthand variables and translates them into real configuration keys. They are described in full on the configuration reference; the point worth repeating here is that the translation happens inside the Compose file, so those names mean nothing to any other install path.

Volumes and file ownership

The image sets Storage__DataDirectory=/data and declares /data as a volume, so the database and the credential key land there together. It also runs as the base image's non-root user, whose numeric identifier is 1654, and the image creates /data already owned by that user.

That ownership is why a named volume works with no setup: on first initialisation a named volume inherits the ownership of the mount point inside the image. A bind mount does not — it keeps whatever the host directory already has.

A bind mount fails on permissions, not on configuration

Mounting a host directory with -v /srv/knotarium:/data and leaving it owned by root gives you a container that starts and then cannot write its database. Either chown the host directory to 1654, or run the container with an explicit --user. A named volume avoids the question entirely and is the better default.

Windows installer

The installer is built with Inno Setup and its job is to turn the folder build into a service. It installs into %ProgramFiles%\Knotarium, registers an auto-starting Windows service named Knotarium bound to http://localhost:43120, starts it, and adds two Start Menu entries: Open Knotarium, which is an internet shortcut to the running instance, and Uninstall Knotarium. A non-silent install finishes with an optional checkbox to open the app in your browser.

Because it writes to Program Files and installs a service, the installer requires elevation. It also refuses to run on anything but 64-bit Windows, since the published build is win-x64 and there is no 32-bit build to fall back on.

Unattended install

# Install with no interaction
Knotarium-<version>-setup.exe /VERYSILENT /SUPPRESSMSGBOXES /NORESTART

# Remove it again
"%ProgramFiles%\Knotarium\unins000.exe" /VERYSILENT
The service account is not your account

The service runs under the service control manager, not your session. Environment variables you set interactively are invisible to it — this is the single most common reason a setting appears to be ignored after an installer-based install. Put configuration in appsettings.json next to the executable instead, which the application finds reliably because running as a service pins its content root to the executable's own folder.

winget

A winget manifest for the identifier AndreKaufmann.Knotarium exists in the repository under installer/winget/, prepared for submission. At the time of writing its InstallerSha256 is still a placeholder of zeroes and its InstallerUrl points at a specific pre-release tag, so it has not been submitted to the public index. Treat winget install as planned rather than available, and take the installer from the releases page.

Zero-install zip

The zip is the same published folder as the installer uses, compressed. Nothing is registered, nothing is written to Program Files, and no administrator rights are needed. Unpack it wherever you like and run Start.bat, a small launcher the build writes into the folder that pins the address, opens your browser, and then starts the executable in the foreground. 

# What Start.bat does
set ASPNETCORE_URLS=http://localhost:43120
start "" "http://localhost:43120"
"%~dp0Knotarium.Api.exe"

Closing the console window stops the server. This is a genuine difference from the installer path rather than a limitation: the zip build is a foreground application, so nothing runs when you are not running it.

The zip and the installer share their data

Both resolve the same machine-wide data directory, so a zip build and an installed service on one machine see the same database and the same workflows. That is usually convenient. It also means running both at once is a bad idea — two processes writing one SQLite file is not a configuration anyone tested.

Linux

The Linux release artifact is a .tar.gz rather than a zip, specifically so the executable bit on Knotarium.Api survives extraction. It is a self-contained build: the .NET runtime is inside it and there is nothing to install first.

The repository ships a hardened systemd unit at deploy/linux/knotarium.service. The install it assumes is /opt/knotarium for the program and /var/lib/knotarium for the state, running as a dedicated unprivileged knotarium user with no login shell. 

# Service account, directories, then unpack the release into /opt
sudo useradd --system --home /var/lib/knotarium --shell /usr/sbin/nologin knotarium
sudo mkdir -p /opt/knotarium /var/lib/knotarium
sudo tar -xzf Knotarium-<version>-linux-x64.tar.gz -C /opt/knotarium --strip-components=1
sudo chmod +x /opt/knotarium/Knotarium.Api
sudo chown -R knotarium:knotarium /opt/knotarium /var/lib/knotarium

# Install and start the unit
sudo cp deploy/linux/knotarium.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now knotarium

The unit sets Storage__DataDirectory=/var/lib/knotarium deliberately, because the platform default on Linux resolves to /usr/share — a directory a hardened service has no business writing to. Logs go to the journal, so journalctl -u knotarium -f is where you watch a run go wrong.

The hardening, and the one exception

The unit applies a broad set of systemd protections: NoNewPrivileges, ProtectSystem=strict with a single writable path for the state directory, ProtectHome, PrivateTmp, PrivateDevices, the kernel and control-group protections, and an address-family restriction that allows only IPv4, IPv6 and Unix sockets.

MemoryDenyWriteExecute must stay false

The unit sets MemoryDenyWriteExecute=false on purpose and the comment beside it says so. The engine compiles inline code and dynamic node packages with Roslyn while it runs, which needs memory that is writable and then executable. Turning this protection on looks like good hardening and silently breaks every workflow that contains an Inline Code node.

If you enable the process-isolated node sandbox, confining worker processes by CPU percentage on Linux needs a delegated control-group hierarchy. Grant it with Delegate=yes in a drop-in override; without delegation the sandbox falls back to a resource limit on address space and the CPU cap does not apply.

A stale caveat in the Linux notes

deploy/linux/README.md warns that the automated release publishes Windows artifacts only and tells you to build from source. That is no longer true — the release workflow has a Linux job that produces Knotarium-<version>-linux-x64.tar.gz with a checksum sidecar and attaches it to the same release. Prefer the published tarball.

From source

Two prerequisites: the .NET 10 SDK and Node 22 or newer. In development the backend and the interface run as two processes, because the Vite dev server provides hot reloading and proxies API calls to the backend. 

# Terminal 1 — the API, on http://localhost:43120
dotnet run --project Backend/Knotarium.Api

# Terminal 2 — the interface, on http://localhost:5273
cd Frontend && npm install && npm run dev

Open http://localhost:5273, not 43120, when running this way: the dev server is what serves the interface, and it forwards /api to the backend. On Windows, ./run.ps1 does both in separate windows, first stopping anything already listening on either port and elevating if it must. It takes -Clean to wipe build output first and -MockApi to also start a small local REST server used for testing resource lookups.

Development mode stores data somewhere else

When ASPNETCORE_ENVIRONMENT is Development, the machine-wide data directory is not used: the database falls back to a relative path and drafts go to the historical per-user location. Development mode also relaxes the HTTPS-only session cookie and refuses to auto-generate a credential key. A source run and an installed instance on the same machine therefore do not share data, which is exactly what you want while developing and a nasty surprise if you assumed otherwise.

Building a distributable

publish.ps1 produces the folder build that every Windows artifact is made from. It builds the interface with Vite, publishes the backend self-contained, copies the interface into wwwroot and this help site into wwwroot/help, and writes the launcher. 

# Folder build into ./publish/app
./publish.ps1

# Stamped version, plus the zip and the installer
./publish.ps1 -Version 1.0.0-rc.1 -Zip -Installer

# A different target platform
./publish.ps1 -Runtime linux-x64

Building the installer needs Inno Setup 6 on the machine; the script looks for ISCC.exe in the usual locations and fails with a clear message if it is missing. The -SingleFile switch exists but the script warns against it in red, and the warning is worth heeding: a self-extracting build unpacks to a temporary folder at launch, which antivirus products flag as a false positive far more readily than the folder build.

One stale line in the build output

When publish.ps1 finishes it prints that the SQLite database is created next to the executable on first run. That has not been true since persistence moved to the machine-wide data directory. The database is created in the data directory described below, not in the application folder.

Verifying what you downloaded

Every release artifact ships with a .sha256 sidecar next to it, generated from the final bytes of the file. The sidecar holds the hash and the filename separated by two spaces, which is the format the standard Unix tool expects. 

# Windows — compare the output against the .sha256 file
Get-FileHash .\Knotarium-<version>-win-x64.zip

# Linux — verify against the sidecar directly
sha256sum -c Knotarium-<version>-linux-x64.tar.gz.sha256

When the release pipeline signs artifacts, it regenerates the checksums afterwards, because signing changes the file's bytes and the pre-signing hash would be stale. The published checksum always describes the file you can actually download.

SmartScreen and code signing

Windows releases are not code-signed today. The build pipeline has two optional signing routes wired in — an Authenticode step in publish.ps1 driven by a certificate supplied through secrets, and an alternative server-side signing service — but both are opt-in and inert unless the corresponding secrets are configured. With neither configured the output is an ordinary unsigned build.

What an unsigned build looks like

Windows SmartScreen will report an unknown publisher, and heuristic antivirus scanners sometimes flag the installer outright. This is a reputation problem, not a detection of anything. The zip is affected noticeably less than the installer, because it does not self-extract. Verify the published SHA-256 before running either, and check the multi-engine scan links that the release notes carry when that scan is enabled.

First run

Open http://localhost:43120. The interface asks the backend whether the instance needs setting up, and the answer is yes exactly when sign-in is enabled and no accounts exist yet. In that state it presents a screen to create the first account.

That first account is created with the admin role and you are signed in immediately. The rules the server enforces are short:

  • The password must be at least 8 characters. There is no complexity rule beyond length, and no maximum.
  • The username is trimmed and lower-cased before it is stored, so sign-in is case-insensitive.
  • Setup is refused once any account exists. It is not a screen you can return to.

Passwords are stored only as salted hashes, and a hash written by an older algorithm is transparently upgraded the next time that user signs in successfully.

Unattended first admin

For an install with no browser in the loop, set Auth__InitialAdmin__Username and Auth__InitialAdmin__Password. They seed the first administrator at startup and are applied only while no accounts exist, so leaving them set does nothing on later starts. Supply the password from a secret store rather than a checked-in file.

If sign-in is turned off entirely there is no setup screen and no login, because every endpoint is already anonymous. Note that this configuration refuses to start when the instance is bound to anything other than loopback — see the configuration reference for why that check exists.

Where your data lives

One machine-wide directory holds everything that must outlive an upgrade: the SQLite database, the credential-encryption key, unpublished workflow drafts, and the export folder.

Install pathData directory
Windows installer or zip%ProgramData%\Knotarium
Container/data, set explicitly by the image
Linux with the shipped unit/var/lib/knotarium, set explicitly by the unit
Other platforms, unconfiguredThe platform's shared application-data folder, plus Knotarium
DevelopmentRelative paths beside the project; the setting is ignored

The reason this directory is machine-wide rather than per-user is that a Windows service and an interactive run start from different accounts and, without a fixed home, would each anchor their own database and never see each other's work.

Back up the key with the database

The .credential-key file in the data directory decrypts every stored password, token and API key. A backup of the database without it leaves you with credentials that can never be read again. Back up the directory as a unit, or not at all.

Upgrading

The database schema is created and migrated on startup, so no upgrade path has a manual migration step. What differs is how the old files are replaced.

Windows installer

Run the new installer over the old one. The application identifier is deliberately stable across versions, so an upgrade replaces the installation rather than sitting beside it. Before copying any file the installer stops the service and polls until it genuinely reports stopped — up to 45 seconds, because sc stop returns immediately while the application is still draining in-flight runs. It then deletes the service, force-terminates any surviving process including the sandbox worker child, replaces the files, and recreates and starts the service.

That polling exists because a fixed short wait let the file copy begin while the executable was still locked, which aborted the install with a file-in-use error.

Container

docker pull ghcr.io/andrekfm/knotarium:latest
docker rm -f knotarium
docker run -d --name knotarium -p 43120:43120 \
  -v knotarium-data:/data ghcr.io/andrekfm/knotarium:latest

Removing and recreating the container is the upgrade. The volume is untouched by both operations, which is where all of your state lives.

Linux

Stop the service, replace the contents of /opt/knotarium with the new release, restore the executable bit and the ownership, and start it again. Leave /var/lib/knotarium alone — that is the data, and nothing about an upgrade should touch it.

Uninstalling

The Windows uninstaller stops and deletes the service and removes the program files, but leaves %ProgramData%\Knotarium in place so that reinstalling keeps your workflows. If you want a genuinely clean machine, delete that directory yourself afterwards. The same principle applies on Linux: removing the unit and /opt/knotarium leaves /var/lib/knotarium untouched.

Confirming it works

A running instance answers GET /api/version with the version stamped into the assembly at build time, which is the quickest way to tell a freshly upgraded instance from a stale one that never restarted. The version is also shown on the dashboard. A plain docker build or an unstamped local publish reports 0.0.0, because the version is passed in by the release pipeline rather than derived.

If the page does not load at all, work through it in this order: is the process running, is it bound where you think, and is anything else holding the port. On Windows the service manager shows the first; on Linux systemctl status knotarium does. Container logs and the systemd journal both carry the startup errors, and startup failures in this application are deliberately loud — a misconfiguration that would be unsafe to run through, such as disabling sign-in on a non-loopback address, stops the process rather than warning.
