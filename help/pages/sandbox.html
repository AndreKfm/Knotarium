Sandbox

Settings › Sandbox decides where user-authored C# — the Inline Code node and compiled custom node packages — actually executes, and how hard the operating system confines it while it does. It is the companion to Capabilities: that screen decides whether code may run, this one decides how safely.

The two modes

The card offers a choice of two, presented as radio buttons.

In-process (compatible)

The default. Scripts run inside the backend process with full access, which is fast — there is no process to start, no data to marshal across a boundary — but means a runaway script can stall or crash the whole instance. An endless loop occupies a thread the engine needed; a memory bomb takes the engine's memory with it; an unhandled fault can take the process down.

The timeout is still enforced in this mode, but it is cooperative: a script has to observe the cancellation token it is given for a long operation to be interruptible. A tight loop that never checks will not stop when the timeout expires, because there is no boundary to kill.

Isolated process (recommended)

Scripts run in pooled worker processes with operating-system-enforced memory and CPU limits. Endless loops and memory bombs are killed hard and the backend stays up. This is the mode that makes the numeric limits below mean anything, and the only mode in which restricted tokens and credential proxying are available.

The trade-off is the one you would expect: a process boundary costs start-up time on a cold worker and marshalling on every call, and a script that relied on touching the host directly may stop working under a restricted token. That second point is the usual reason people leave in-process mode alone.

When to switch to process mode

Switch as soon as the code running on the instance is not exclusively yours — anything imported, anything generated from a description, anything written by someone whose mistakes you would rather contain. Switch also on any instance where uptime matters more than the milliseconds a process hop costs, because in-process mode gives a single bad script the ability to take the engine with it. Stay in-process only for a single-operator instance where you wrote every script and some of them legitimately need host access.

The toggles

Three checkboxes sit under the mode selector. Two of them are dimmed and disabled outside process mode, labelled isolated mode only.

Screen code before running

Rejects scripts that use banned APIs — filesystem, process control and similar — at run time, applying the same check the node editor applies while you are writing. It works in both modes, because it happens before compilation rather than during execution. On by default

This is a screening pass, not a sandbox. It stops the obvious calls; it is not a proof that a script cannot reach the host, and it should not be the only thing standing between an untrusted script and your machine.

Restricted worker privileges (Windows)

Runs workers with stripped privileges and low integrity: no access to user profiles, service data or most of the file system. Under the hood this launches the worker with a restricted token, restricting security identifiers, and a Low integrity level, which denies access to user- and admin-scoped filesystem and registry objects. On by default

It is best-effort: if the restricted launch fails, the worker starts normally and a warning is logged rather than the execution being refused. That is a deliberate availability choice, but it does mean the presence of the switch is not a guarantee the confinement is in force — check the log if it matters. The setting is Windows-only and the hint says so; disable it for legacy node code that genuinely must touch the filesystem.

Keep secrets out of the sandbox

Credential proxying. With it on, a script that asks for a secret receives an opaque placeholder rather than the value, and the host substitutes the real secret into a proxied outgoing HTTP request — the URL, the headers and a textual body — immediately before sending. Node code can use a credential but never read one. On by default

The interface's advice on turning it off is exact: disable it only for scripts that need the raw value for something other than an HTTP call, such as computing an HMAC signature. Turning it off puts decrypted secrets inside the worker process, which is most of the reason for running a worker process in the first place.

The worker limits

The numeric fields are grouped under Worker limits and dimmed outside process mode. The card is explicit that these apply only in isolated mode and have no effect in-process, with one exception noted on the screen: the timeout and hard kill are always enforced.

FieldDefaultRangeWhat it bounds
Worker processes 4 1–32 Pool size, and therefore the maximum number of concurrently sandboxed node executions.
Memory limit (MB) 512 64–16384 Hard per-worker memory cap, enforced by the operating system.
CPU limit (%) 100 5–100 Share of one core per worker. 100 means uncapped.
Max run (s) 300 1–3600 The ceiling applied when a node declares no timeout of its own.
Kill grace (s) 5 1–60 How long the cooperative cancel is given after a timeout before the process is killed.
Recycle after runs 100 1–10000 A worker is replaced after this many executions.
HTTP response cap (MB) 32 1–100 The largest proxied response body marshalled back into the sandbox.

Every value is clamped to its range on save, using the same clamping logic the configuration binder uses, so a number outside the range is silently corrected rather than rejected. If a field does not keep the value you typed, that is the clamp, not a failed save.

What the individual limits are actually for

Worker processes is a concurrency ceiling as much as a resource one. Four workers means at most four sandboxed node executions at a time; a fifth waits. Raising it raises both throughput and the total memory the pool can occupy, which is the memory limit multiplied by the worker count.

Memory limit and CPU limit are enforced at the operating-system level and are described on the screen as best-effort, using a Windows Job Object or a Linux control group. The card states the important caveat plainly: on Linux without cgroup v2 the CPU cap is not enforced. Do not plan capacity around a CPU cap you have not verified on the platform you deploy to.

Max run is a fallback, not an override. It applies when a node declares no timeout of its own; a node that declares one keeps it. This is why raising the figure does not extend an Inline Code node that already has its own timeout.

Kill grace is the window between the cooperative cancel and the operating system taking over. The script gets that long to unwind on its own; then the process is killed. Set it long enough for genuine cleanup, short enough that a script ignoring cancellation does not hold a worker hostage.

Recycle after runs bounds slow leaks and pinned state. A worker retired after a hundred executions cannot accumulate a hundred thousand executions' worth of leaked handles, and anything a script left behind in static state is discarded with the process.

HTTP response cap bounds what comes back across the process boundary. A script requesting a very large body gets it truncated at this ceiling rather than being allowed to marshal an arbitrary amount into the worker.

Saving, and the one thing that does not apply immediately

The card's description says changes apply immediately with no restart needed, and after a successful save the confirmation reads Saved — active immediately. That is true of the mode and of every toggle: saving rewrites the live options object the engine reads.

Worker count only sizes a new pool

This is stated in the field's own hint and is easy to miss: an already-running process pool keeps its current size until the application restarts. Lowering the worker count on a busy instance does not shrink the pool that is already up. The per-worker limits do apply to workers spawned after the save, so raising the memory limit takes effect as workers recycle rather than all at once.

A corrupt stored value never fails a read. If the persisted settings will not parse, the screen falls back to showing the live options — which are whatever configuration seeded at startup — and at startup a corrupt blob is ignored so the secure configuration defaults stay in force.

Configuration and precedence

These settings are seeded from the Security__Sandbox__* configuration keys at startup and, once you save this screen, are persisted in the database. From that point the stored values override the configuration file, and editing appsettings.json appears to do nothing. The restore happens during startup: if a persisted blob exists it is overlaid onto the configuration-bound options and the log notes that persisted sandbox settings were restored; if none exists, configuration stays authoritative.

The screen always reflects what is actually enforced rather than what is configured — it shows the persisted values when they exist and the live options otherwise. So if the screen and your configuration file disagree, the screen is right.

The full key list, with the same defaults and ranges expressed as configuration, is in the configuration reference. Note one wrinkle there: the banned-API screening flag travels with these settings through the interface but is applied to the compiler rather than to the options object, which is why it keeps working in in-process mode where the rest of the limits do not.

What the sandbox does not do

Worth stating so the confinement is not over-trusted. The sandbox is process isolation with operating-system resource limits — it is not a language-level sandbox and it does not make arbitrary C# safe. A script running in a worker still executes real code; what changes is how much of the host that code can reach and what happens when it misbehaves.

In particular: inline code and SQL are not sandboxed by design in the sense of being restricted in what they may express, because they need the runtime compiler and a real connection. The capability switch decides whether they run at all. The sandbox decides the blast radius. Neither makes an untrusted author safe — see Security model for the trust boundary that actually matters.
