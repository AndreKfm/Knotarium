Trigger nodes

A trigger is where a run begins. Which trigger fires is decided by the run's origin — manual, schedule, webhook, poll or error — matched against the trigger nodes the workflow actually contains. This page documents all seven nodes in the Triggers category, including End, which is filed here despite being a terminator rather than a starter.

How a trigger is chosen

Trigger nodes are marked trigger-only in the catalog, and most of them have no executor at all. When the run reaches one of those, the engine marks it complete immediately and fills its output port with a payload synthesised from the run itself — the schedule's fire time, the polled document, the failure context. Cron Scheduler, Webhook Trigger, Polling Trigger, Error Trigger and Manual Trigger all work this way, which is why their timeout is 0 and why none of them can fail.

Start is the exception: it is trigger-only but does have an executor, because it has real work to do at a subflow boundary. It runs like any other node, and its outputs are what that executor produced rather than a synthesised payload.

At the start of a run the engine walks the compiled plan's entry nodes and keeps the trigger-only ones whose type matches the origin: schedule selects Cron Scheduler, webhook selects Webhook Trigger, poll selects Polling Trigger, error selects Error Trigger, and everything else selects Start or Manual Trigger. If nothing matches, the run falls back to all of the plan's entry nodes rather than starting nothing — so a workflow with only a Cron Scheduler still runs when you press Run manually.

Automatic triggers need an armed runtime

Schedules, webhooks and polls only fire while the runtime is armed. While it is disarmed, the webhook endpoint refuses the call outright, and the manual Run button is the only thing that starts a workflow. A workflow also needs an active published version; without one the trigger has nothing to execute and the attempt is refused rather than queued.

Start

start · Triggers · trigger-only · timeout 0

The default entry point, and the node every new workflow is created with. Reach for it whenever a workflow is run by hand, tested from the editor, called as a subflow, or invoked by an AI Agent as a tool. It is also the fallback entry point for any origin the engine does not recognise, which makes it the safest thing to leave on a graph.

Start has no parameters of its own, yet it is not inert. When a workflow is used as a subflow, its Start node is where the caller's input bindings land: each declared input is written into a workflow variable before anything downstream runs. Every other input Start receives is passed straight through to its outputs, so a run started with input variables can read them immediately after the Start node. You declare a subflow's inputs on its Start node — the properties panel offers that interface editor rather than a generic form.

ParameterTypeRequiredExpr
None.
PortTypeCarries
resultanyWhatever the run was started with, minus the internal subflow-binding keys.

Cron Scheduler

scheduler · Triggers · trigger-only · timeout 0

Runs the workflow on a recurring clock. Use it for anything time-driven: a nightly export, a five-minute health probe, a Monday-morning digest. The properties panel gives you a builder with the common shapes — every N minutes, hourly, daily, weekdays, weekly, monthly — and drops to a raw expression field when the cron you have cannot be represented by the builder, so it never silently rewrites an expression you typed yourself.

Both parameters are required, and both are validated when the workflow is saved rather than when it fires. The expression must have five fields (minute hour day-of-month month day-of-week) or six when you want second precision. The time zone must be one the host recognises. Get either wrong and the save is rejected with an explicit message; a valid expression that has no future occurrence at all is rejected the same way.

Saving the workflow reconciles a persisted schedule row per scheduler node. Removing the node removes the schedule; changing the expression recomputes the next fire time. The next fire time is shown in the properties panel, which is the quickest way to confirm that a time zone is doing what you expect across a daylight-saving boundary.

ParameterTypeRequiredExprNotes
cronExpressionstring Yes— Five fields, or six to include seconds. Anything else is refused at save time.
timezoneIdstring Yes— A system time-zone identifier. The schedule is evaluated in this zone and stored in UTC.
PortTypeCarries
triggeredAtstringThe moment the run was created. Note the port is not called result.

Webhook Trigger

webhookTrigger · Triggers · trigger-only · timeout 0

Starts a run when an external system posts to the instance. Reach for it when something else owns the timing — a source-control hook, an alerting system, a form back end. The caller posts the workflow id and an optional bag of input variables; those variables become the run's globals and are readable downstream.

The endpoint is deliberately machine-facing and does not require a user session, so it is gated by three other things instead. The runtime must be armed. The workflow must be enabled and have an active version. And, if you have configured one, the caller must present the workflow's webhook secret in a request header — checked first, and in constant time, so an unauthorised caller learns nothing about the instance's state. Workflows with no secret configured stay open.

Two rejections are worth recognising. A full execution queue answers with "too many requests" rather than dropping the call silently, which means the sender can back off and retry. A workflow that fails compilation answers with the diagnostics, so a broken graph reports itself instead of failing invisibly at run time.

The payload parameter is a design-time convenience for describing the body you expect; it is not populated from the request. The actual inbound data arrives as the run's input variables.

ParameterTypeRequiredExprNotes
payloadstring No— A sample or description of the expected body. Not filled in from the incoming request.
PortTypeCarries
resultobjectPresent for wiring; the inbound values are reachable as run variables.

Polling Trigger

pollingTrigger · Triggers · trigger-only · timeout 0

Watches a source you cannot get a webhook out of, and starts a run when it changes. This is the node with the most configuration in the catalog, because it has to cover two kinds of source and five ways of deciding that something is new.

Saving the workflow creates one persisted polling trigger per node, carrying the interval, the source configuration and an opaque cursor holding what was last seen. The cursor survives ordinary edits — retitling the node, adjusting headers — but is reset whenever the source's identity changes, meaning any of sourceKind, url, serverConfigId, operationId or specVersion. That reset is deliberate: a cursor from a different endpoint would either suppress real changes or replay old ones. Expect one "everything looks new" poll after repointing the trigger.

The polling worker owns the cadence once the first poll has happened, so re-saving a workflow does not restart the clock. Deleting the node deletes its trigger row and its cursor with it.

Choosing a change-detection mode

  • etag and last-modified lean on the server's own validators. They are the cheapest and most accurate options when the source sets those headers correctly — and they detect nothing at all when it does not.
  • hash compares a digest of the response body. It works against any source, at the cost of transferring the whole body every time, and it reports a change whenever any byte moves — including a timestamp the server stamps into every reply.
  • json-cursor tracks a single value inside the response, named by jsonCursorPath. This is the right choice for a feed with a monotonic id or updatedAt, and the only one that ignores incidental churn elsewhere in the document.
  • always starts a run on every poll. Useful while building, and a good way to fill the run history by accident if left on.
ParameterTypeRequiredExprNotes
intervalSecondsnumber Yes— Seconds between polls. Must be a positive whole number; missing or zero makes the save fail with a message naming the node. The form offers 60 but stores nothing until you touch it.
sourceKindenum Yes— http — a URL you supply. openapi — an operation from an imported specification. Changing this resets the cursor.
changeDetectionenum Yes— etag, last-modified, hash, json-cursor, always. See above.
jsonCursorPathstring No— Path to the value to track. Only meaningful with json-cursor; ignored otherwise.
urlstring No Yes The endpoint to poll, for http sources. Part of the source identity — editing it resets the cursor.
methodstring No— HTTP method. The form shows GET; nothing is stored until you change it.
headersJsonstring No— Extra request headers as a JSON object. Not part of the source identity, so editing it preserves the cursor.
apiKeySecretRefstring No— Id of a stored credential to authenticate with. The form renders a credential drop-down even though the manifest types it as a plain string.
serverConfigIdstring No— Which configured server to call, for openapi sources. Part of the source identity.
operationIdstring No— The operation to poll, from the imported specification. Part of the source identity.
specVersionstring No— Which stored version of that specification to use. Part of the source identity, so re-importing and re-pointing resets the cursor.
PortTypeCarries
resultanyThe polled payload that was judged new. Absent if the run was started some other way.
The two source kinds share one parameter list

Only four of the eleven parameters are required, because the HTTP fields and the OpenAPI fields are alternatives rather than companions. The properties panel shows one set or the other according to sourceKind; the values you filled in for the other kind stay in the workflow and are simply ignored, so switching back restores them.

Error Trigger

errorTrigger · Triggers · trigger-only · timeout 0

The entry point of the global error-handler workflow. Reach for it once, in one workflow, and nominate that workflow as the instance's error handler; from then on any other workflow that fails starts a run of it with the failure context attached. It is the right place to put alerting, ticket creation or a dead-letter write, because it keeps that logic out of every individual workflow.

It has no parameters at all. There is nothing to configure because the routing is a global setting rather than a property of the node, and the payload shape is fixed by the engine. An error run is also linked back to the run it is handling, so the inspector can navigate from the handler to the failure that caused it.

Besides the whole failure context on result, the engine publishes eight individual fields as separate outputs so each can be promoted to a draggable variable in the editor and referenced directly from a Log or Send Notification node without unpacking the bundle first:

FieldCarries
errorWorkflowIdId of the workflow that failed.
errorWorkflowNameIts name, for a human-readable alert.
errorExecutionIdThe failed run, for linking back to the inspector.
errorFailedNodeIdWhich node failed.
errorFailedNodeTypeThat node's internal type id.
errorMessageThe failure message.
errorTriggerOriginHow the failed run had been started.
errorTimestampUtcWhen it failed.
ParameterTypeRequiredExpr
None.
PortTypeCarries
resultanyThe full failure context. The eight fields above are emitted alongside it.
The error handler needs an active version of its own

If the nominated error workflow has no active published version, the failure is not handled and nothing is queued — the failing run reports its own error and that is the end of it. Publishing and activating the handler is not optional, and it is the single most common reason error handling appears to do nothing.

End

end · Triggers · timeout 0 (5 seconds applied at run time)

A terminator, filed in the Triggers category alongside Start because the two form the workflow's interface. On an ordinary workflow it is optional — a path that runs out of wired successors simply ends. Reach for it when you want an explicit, readable finish, and reach for it always in a workflow used as a subflow.

That is because End is where a subflow's outputs are declared and copied back to the caller. Each declared output names a local variable and the caller-side name to write it to; without an End node a subflow computes results that never leave it. The properties panel shows that interface editor on the End node of a subflow.

End is the one node in this category that is not trigger-only, so it really executes — and because its manifest timeout is 0, the engine applies its 5-second fallback. That is ample for copying variables, and worth knowing only if you ever see an End node time out.

ParameterTypeRequiredExprNotes
payloadstring No Yes A final value to record. Accepts {{ }} expressions.
PortTypeCarries
None. End declares no outputs, so nothing can be wired downstream of it.

Manual Trigger

manualTrigger · Triggers · trigger-only · timeout 0 · Hidden from the palette

A manual entry point: no parameters, a single result port, and the same origin matching as Start. It is documented here only so that an older workflow containing one is not mysterious. It remains registered and executable, and such a workflow renders and runs exactly as before — but you cannot add a new one, because Start does the same job and having two manual entry points to choose between helped nobody.

The one behavioural difference is that Manual Trigger has no executor, so it emits nothing: where Start passes a run's input variables through to its outputs, Manual Trigger's result port is simply empty. It also cannot carry a subflow's declared inputs. If a workflow of yours reads values off its entry node, or is used as a subflow, replace the Manual Trigger with a Start node and re-wire its single output.
