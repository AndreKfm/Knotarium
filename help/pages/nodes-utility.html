Utility nodes

The small nodes that make a workflow legible and debuggable — writing to the run log, setting variables, and dropping to C# when the built-in nodes run out. Plus two nodes that never execute at all, because they exist purely to make the canvas readable, and the External Device block whose ports come from a plugin rather than from a manifest.

Everyday utilities

Log, Set Variable and Set Variables share a shape: no capabilities, no credentials, a ten-second default timeout, and a recovery mode of "fail immediately" — none of them is ever retried automatically, because none of them can fail for a transient reason. If one of these fails, running it again will fail the same way.

Log

Writes a message into the application log and the run journal. Reach for it while you are building — dropping a Log between two nodes is the fastest way to see what is actually flowing along an edge, and the message it wrote is preserved in the run history rather than only in the moment.

ParameterTypeRequired{{ }}DefaultEffect
message string no yes log message What to write. An empty or unset message logs the literal text log message rather than an empty line, so an unconfigured Log node is visible in the journal instead of invisible.
PortCarries
resultThe final message string, after expression evaluation and variable substitution. Wiring Log into a downstream node passes the text along, so it can double as a formatting step.

A value that is not already a string is rendered before logging: a JsonElement uses its own representation, a list or array is serialized to JSON, primitives use their normal string form, and anything else is serialized to JSON. So logging a whole upstream object gives you readable JSON rather than a type name.

Single braces are substituted too

After the usual {{ }} expression evaluation, the Log node performs a second, simpler pass: any occurrence of {name} — single braces — is replaced with the value of the global variable name, if one exists. This is convenient and occasionally surprising, because a message containing literal JSON braces can be rewritten when a key happens to match a variable name. Log entries appear in the run journal prefixed with [LOG], which is how you tell them apart from the generic "completed successfully" entries.

Set Variable

Writes one global variable. Use it to carry a value across a branch, to accumulate something in a loop, or to name an expression once instead of repeating it in five nodes. Its real power is that the variable name may be a path, so you can build up a structured object piece by piece rather than assembling JSON in a string.

ParameterTypeRequired{{ }}Effect
variableName string no no The variable to write, or a path into one. An empty name makes the node a silent no-op — it succeeds and writes nothing, which is the usual explanation for a variable that never appears.
value string no yes The value to store, evaluated before the write.
PortCarries
resultNothing. The executor returns success with no outputs, so this handle exists to continue the flow, not to pass data. Read the variable downstream instead.

Writing into a nested path

The name is parsed as a head followed by segments. The head is everything up to the first . or [, and it is the variable that actually gets stored. After that, .member descends into an object key, ["key"] or ['key'] does the same for a key that is not a bare identifier, and [0] indexes into an array with a non-negative integer. 

# All four are valid variableName values
config                     # a plain variable
myDict["name"]           # a key inside myDict
list[0]                   # the first element of list
config.servers[2].host    # nested object, array index, then a member

A path write materialises the head variable's current value into a mutable tree, sets the leaf, and stores the head back. Intermediate containers are created on demand, and siblings are preserved — writing config.servers[2].host does not disturb config.servers[0] or any other key under config.

A malformed path becomes a flat variable name

If the name does not parse as a path — an unterminated bracket, an empty member as in a..b, a trailing dot, a negative or non-numeric index — the node does not fail. It falls back to setting a variable whose literal name is the whole string you typed. You then have a variable called a..b that nothing downstream can read. A path that parses but conflicts structurally, such as indexing a value that is not an array, does fail the node, with a message naming the variable.

Set Variables

The same write, several times over, from one node. Reach for it at the top of a workflow to initialise everything the run needs in a single visible place, instead of a chain of five Set Variable nodes that makes the canvas harder to read than the logic deserves.

ParameterTypeRequired{{ }}Effect
variables keyValue no yes Rows of name and value. Each value is expression-evaluated before the node runs, so a row may be a literal or a reference to an upstream output or another variable.
PortCarries
resultA count field holding the number of rows actually written. Note that the value is published under count, not under result.

Names go through exactly the same path parser as Set Variable, so myDict["k"] and list[0] behave identically in either node. Rows are applied in order, which means a later row may overwrite an earlier one and a row may reference a variable a previous row set — but only if that reference was evaluated after the earlier write, which is not guaranteed. Do not chain dependent assignments within one node; use two nodes.

Rows with no name are skipped silently

A row whose name is missing, blank or not a string is ignored and does not count towards count, and the node still succeeds. If a variable you expected is missing, compare count against the number of rows you wrote before looking anywhere else. A structural conflict in a path, on the other hand, fails the node and names the offending row.

Inline Code

A short C# script typed straight into the node, filling the gap between an expression — which can only read — and authoring a whole custom node package. Reach for it when a transformation is genuinely awkward to express with the data nodes: parsing an unusual format, a computation with real branching, or reshaping a payload into something a downstream API expects. Anything you reach for repeatedly across workflows deserves to become a node package instead.

Off until an administrator turns it on

The node checks the code.execute capability before it compiles anything and fails with "Inline Code is disabled: the 'code execution' capability is off" when it is not enabled. Turn it on at Settings › Capabilities. It is the highest-privilege capability in the system: a workflow that can run arbitrary C# can do anything the Knotarium process can do, which on a service install may be a great deal more than you intended.

ParameterTypeRequired{{ }}DefaultEffect
language enum no no csharp The only value the manifest offers, and the only one the executor accepts — c# and an empty value are also treated as C#, anything else fails with "language '…' is not supported in v1". The field exists as the seam for adding another language later.
code code yes no none The script body. Deliberately not expression-enabled: the evaluator must never rewrite {{ }} that happens to appear inside source code. Reach your data through Input.Get instead. An empty script fails with "no script provided".
PortWhen it fires
resultThe script completed. Carries whatever the script returned.
errorThe node failed — a compilation error, a thrown exception, a timeout, or an explicit Fail(...). As with every non-branching node, this handle is also scheduled on success.

What the script can see

The body you type is wrapped in a method, so you write statements rather than a class. Inside it you have Input.Get<T>(name, defaultValue) for the node's inputs (deserialized case-insensitively, falling back to the default rather than throwing on a mismatch), Logger for structured logging, context for workflow state, HTTP and credentials, and cancellationToken. Two helpers end the script: Success(payload) and Fail(message). A script that never returns is treated as a successful side-effect-only run.

Returning an object spreads its properties into top-level outputs and exposes the whole value under result, so both output.myField and output.result resolve. Fail(message) produces an ordinary node failure carrying your message, which means an error or failure edge picks it up exactly like any other failure. Common usings are pre-declared, and duplicates you write are dropped rather than causing a compile error.

The timeout is thirty seconds, and how it bites depends on the sandbox

Execution is bounded at 30 seconds by default; the manifest's declared timeout is derived from the same shared constant, so the catalog and the executor can never disagree. A node-level timeoutSeconds property overrides the manifest value the engine uses. On expiry the node fails with "Inline Code timed out after 30s".

In-process, the timeout is cooperative

In the default in-process mode the deadline is a cancellation signal. A script that never observes cancellationToken — a tight loop, a blocking call — keeps running past the timeout even though the node has already reported failure. In process mode the runner additionally kills the worker at a hard deadline, which is the only configuration where a runaway script is genuinely stopped.

Where the code runs

Settings › Sandbox decides whether user-authored C# — this node and compiled custom node packages — runs inside the main process or in pooled worker processes with operating-system limits. The choice is read at every execution, so flipping it takes effect on the next run: no restart, no redeploy. The worker pool is created lazily on the first execution in process mode and kept alive afterwards.

ModeWhat it means for a script
InProcess Default The script runs inside the Knotarium process with its privileges. Fastest, and the posture assumes you trust whoever authored the workflow. A crash or a memory leak in a script is a crash or a leak in the engine.
Process The script runs in a pooled worker process with a memory ceiling, a CPU share, a hard kill deadline and worker recycling; on Windows the worker runs under a restricted token at low integrity. Credentials are proxied rather than handed over, so decrypted secrets never enter the worker.

Independently of the mode, a runtime analyzer is on by default and rejects code that calls banned APIs before it is allowed to compile — so a script reaching for something forbidden fails with a compilation error rather than at the moment it would have done damage. The exact limits, and the settings behind them, are in the configuration reference; note that the values stored by the settings screen override the configuration file.

Annotations that never execute

Two node types exist only to make the canvas readable. They have no parameters and no ports, they are never reached by the executor, and they are registered in the node catalog purely so the compiler recognises the type and they round-trip through save, version and restore like any other node. Neither appears in the palette: both are filtered out by id, because they are inserted from the canvas toolbar instead of being dragged.

Sticky Note

A free-text card you drop on the canvas to explain why something is wired the way it is. Use it for the reasoning that will not survive in your head — why this retry count, which team owns the endpoint, what the ticket number was.

The note button on the canvas toolbar inserts a card at the centre of the current viewport, already selected so you can start typing. It defaults to 220 × 150 pixels and is resizable. Five colours are available — amber (the default), green, blue, pink and slate — each rendered as a translucent wash so the canvas grid shows through rather than as a solid block. A note sits behind real nodes, so one used as a backdrop never intercepts a click meant for a node on top of it.

Text and colour live in the node's properties and its size in its style; both are persisted through the same metadata channel as node positions, so a note survives a version restore exactly as it was.

Group

A visual container that wraps a set of nodes into a labelled, collapsible box. Reach for it when a workflow has grown past the point where the shape is obvious — collapsing a finished sub-section removes it from view without removing it from the run.

Groups are created from the canvas toolbar's group action over the current selection, and at least two top-level nodes must be selected — the action does nothing with fewer. A group can later be collapsed or ungrouped, which restores its children to the top level.

Grouping is purely visual

Membership is carried by each child's metadata, not by the graph. The backend treats a grouped child as an ordinary top-level node, so putting nodes in a group changes nothing about execution order, scoping, error handling or variable visibility. It is a drawing, not a construct — if you want real containment, that is what a Sub-flow is for.

External Device and nodes from other packages

External Device

A generic, configuration-driven block representing one device or instance managed by an installed provider plugin. It is how a workflow reacts to something happening in the physical or third-party world: you pick a target, tick the signals you care about, and each ticked signal becomes a pin you can wire into ordinary nodes.

ParameterTypeRequiredOptions come fromEffect
targetId resourceLocator yes reactor.targets Which configured device or instance this block represents. Free-text entry is permitted as a fallback when the provider is unreachable at design time.
eventPins resourceLocator (multi) no reactor.events, depends on targetId Events raised by the device that you want to react to. Each selection becomes an output pin.
actionPins resourceLocator (multi) no reactor.actions, depends on targetId Incoming actions raised by the device that you want to react to. These are also output pins — see below.
The pins are dynamic, and they are all outputs

The manifest declares no outputs. The canvas derives the handles from the two pin selections: evt:<type> for each event and act:<name> for each action. Despite the name, action pins are source pins too — the block is a pure inbound surface that you react to, and it exposes no input handles at all. Sending a command to a device is a separate node, not an edge drawn back into this one. Removing a pin from the selection prunes the edges that were attached to it.

Because the manifest is output-less, the control-flow compiler skips socket validation for this node; the reactive layer validates the pin wiring instead. The picker values and the device branding come from a host plugin at run time, so on an instance with no such plugin installed the three pickers are empty and manual entry is the only way to fill them in.

Node ids supplied by external packages

The catalog you see in the palette is not fixed. Two separate extension folders add to it, and they do different things:

SettingDefaultWhat it contributes
NodeRuntime__WatchPath <app folder>/nodes Compiled node packages. Each brings its own node id, display name, category, parameters and ports, and executes through the same run path as a built-in node — a prebuilt binary executor rather than C# compiled from the database.
NodeRuntime__PluginsPath <app folder>/plugins Host plugins. These contribute long-lived capabilities rather than nodes: the external-signal provider behind the External Device block, the option loaders that fill its pickers, workflow import providers, and background loops. Discovered once at startup.

A node id that appears in your palette but is documented nowhere in this reference almost certainly came from a package in the watched folder. Fire Action — the counterpart that sends a command to a device, filed under a "Device Workflow" category — is one such node: it is not part of the built-in catalog and arrives with an external package.

Two palette behaviours worth knowing

A package manifest may set secondary to true, which moves the node out of its normal category into a single collapsed Advanced section — the convention for escape-hatch nodes you should not reach for first. Separately, palette search matches only what you can see (name, description, category) and deliberately not the internal node id, so searching for a node by its id will not find it.

Leave hot-reload off in production

NodeRuntime__DevMode reloads node packages when the watched folder changes. It is on in development builds and should stay off elsewhere: reloading swaps code that may be executing, and a package replaced mid-run is not something the engine can make safe for you.
