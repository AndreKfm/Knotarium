Backup and restore

Settings › Backup & Restore produces a single encrypted file containing everything this instance manages — including its secrets — and can replace the instance's entire state from one. Because a backup carries decrypted credentials inside its envelope, it is not a shareable artefact and it lives here under instance settings rather than alongside templates and bundles.

The file

A backup is a single file with the extension .kgbak, named knotarium-backup- followed by the creation timestamp in UTC — for example knotarium-backup-20260725-141203.kgbak. The browser downloads it directly; nothing is written on the server.

Inside the envelope is an ordinary zip with a stable layout: a manifest at backup.json, the workflow-group file, one JSON document per database aggregate under data/, and one file per workflow draft under workflows/. The zip is written in a canonical order with a pinned timestamp so the same content always produces the same bytes. You never see any of that — the whole zip is encrypted — but it is why an archive containing an entry the reader does not recognise is rejected outright rather than partially restored.

The encryption

The envelope is AES-256-GCM. Its header is cleartext — a magic marker, the envelope version, a byte recording how the key was derived, the iteration count and a random salt — and that header is fed to the cipher as associated data, so tampering with the key-derivation parameters makes authentication fail rather than silently changing how the file is read.

A wrong passphrase and a corrupted archive are indistinguishable by design: both fail the authentication tag and both produce the message Incorrect passphrase, or the backup archive is corrupt.

Creating a backup

The left card is headed Create a backup and tagged Safe. It offers two protection modes as a pair of buttons.

Passphrase

The default and the portable option. The key is derived from your passphrase with PBKDF2-HMAC-SHA256 at 600,000 iterations — the OWASP-recommended floor, chosen so guessing against a stolen archive is expensive. The iteration count travels in the header so it can be raised in future without breaking older files.

You type the passphrase twice. The card requires at least eight characters and a match before the download button enables, and shows a four-segment strength meter labelled Weak, Fair, Good or Strong based on length, mixed case with digits, and the presence of a symbol. A passphrase under eight characters is flagged Too short inline.

A warning above the field says plainly that the passphrase cannot be recovered. That is literal. There is no escrow, no reset, and no way for the server to open the file — lose the passphrase and the backup is permanently unreadable. Store the two together and safely.

This server's key

The key is derived with HKDF-SHA256 from this host's credential encryption key, domain-separated so it is not the same key used for anything else. There is no passphrase to remember and nothing to lose — but the archive only decrypts on a host whose credential key is unchanged.

That makes it right for automatic local snapshots and useless for migration, by design. If you restore it elsewhere the failure is explicit rather than confusing: a server-key backup only restores on the host that created it. It also means that replacing or losing the credential key makes every server-key backup you hold unreadable at the same moment it makes the live database's credentials unreadable — which is the opposite of what you want from a backup.

Which to choose

Use a passphrase for anything you keep as disaster recovery or intend to move to another host. Use the server key only for convenient snapshots taken before a risky change on a machine you are not leaving. If you keep only one kind, keep the passphrase kind.

What is in a backup — and what is not

The snapshot covers everything the instance manages as configuration and content:

  • Workflow definitions, their published versions, the active-version pointers and the activation log.
  • Workflow drafts from the file store, and the dashboard's workflow grouping.
  • Schedules and polling triggers.
  • Installed node packages with their versions.
  • Credentials and notification channels.
  • Application settings — which includes the capability policy, the file-access policy, the sandbox and retention settings, and the AI provider configuration.
  • Server configurations and imported OpenAPI specifications with their version history.
Three things are not in a backup

Run history is not carried. The manifest has a flag for it and the preview shows Not included, but the payload does not contain runs or journals today. User accounts are not carried either, so a restore does not change who can sign in — which is worth knowing before you assume a restore returns an instance to a known state in every respect. And the audit log is not part of the snapshot.

The interface exposes no option for run history; the underlying request has one but it defaults to excluded and the screen does not offer it.

How secrets travel

This is the part that dictates everything else about the format. Credential values and notification-channel configurations are stored in the database encrypted under this host's at-rest key, which is not in the database. A raw copy of those ciphertexts is undecryptable on a host with a different key — so a backup carries them decrypted inside the encrypted envelope, and the restore re-encrypts them under the target host's key.

That is what makes migration between hosts possible at all. It is also exactly why the archive itself must be encrypted and why a backup is not something to leave in a shared folder. Anyone who can open the file has every secret the instance held in plaintext.

Restoring

The right card is headed Restore from a backup and tagged Destructive, because it is: restoring replaces all current state with the backup's contents. The flow is deliberately stepped so there is no single click that does it.

Step one — choose the file

Drop a .kgbak on the drop zone or browse for one. As soon as a file is selected the first six bytes are read in the browser to check the magic marker and read the key-source byte, so the card can tell you whether it is passphrase-protected or server-key encrypted without a round-trip and without decrypting anything. The file chip shows the size in megabytes alongside that verdict.

Step two — inspect

For a passphrase backup you enter the passphrase used when it was created. For a detected server-key backup the field is replaced by a note saying no passphrase is needed and the file opens only on this host.

Inspect backup decrypts the archive and parses the manifest only — nothing is written. The preview shows when the backup was created, the engine version with the format version and database provider, and per-aggregate counts: workflows and versions, schedules and polling triggers, credentials and channels, whether run history is included and the file size, and how the archive was encrypted.

Read this before going further. It is the only opportunity to confirm you have the file you think you have, and the credential and workflow counts are the fastest sanity check that the archive is not from the wrong instance or a much older date than expected. Changing the file or the passphrase invalidates the preview so a stale manifest can never be the thing you confirm against.

An archive whose format version this build cannot read is rejected as incompatible rather than partially applied.

Step three — the two checks

A guard block headed Before restoring — 2 checks appears with the preview.

  • Disarm the runtime. Until it is disarmed the step is open and offers a Disarm now button that flips the same shared state the header pill shows. Once disarmed it reads Runtime disarmed — no live triggers will fire during the restore.
  • The safety backup is automatic. This step is always shown as already done, because the current state is snapshotted before any change is made.

The disarm requirement is enforced on the server, not just in the interface. A restore attempted while the runtime is armed is refused before any decryption or write, and the card reports Restore is blocked while the runtime is armed. Disarm the runtime and try again.

Step four — type to confirm

A field asks you to type RESTORE to confirm the irreversible replace. The field is disabled until the runtime is disarmed, and the Restore this instance button only enables when the preview is present, the runtime is disarmed and the confirmation matches. The server independently requires an explicit confirmation flag and refuses without it, so the typed word is not merely a client-side speed bump.

What the restore actually does

In order: it resolves the key, decrypts and reads the archive, and checks format compatibility. Then it writes a pre-restore safety backup of the current state, encrypted in the same mode as the incoming archive so it can be opened the same way. Then it decodes every aggregate from the archive up front, so a malformed document fails before anything is deleted.

Only then does it open a transaction, clear the managed tables in child-to-parent order, and re-insert everything in parent-to-child order — re-encrypting credentials and channel configurations under the current host's key as it goes. Run history is left untouched, since it was never in the archive.

On success the card reports how many workflows and credentials replaced the previous state, shows the path of the pre-restore safety backup, and reminds you to re-arm the runtime when ready. Re-arming is manual and deliberate.

Where the safety backup really goes

The guard step describes it as auto-pre-restore.kgbak. The file is actually written into the operating system's temporary directory with a generated name beginning knotarium-pre-restore- followed by a unique identifier and the ordinary backup file name. The reported path in the success message is the real one — copy it somewhere durable straight away if you might need it. Pre-restore backups older than seven days are deleted by the next restore, and a temporary directory is not a place to keep anything you care about.

Note also that the safety backup is encrypted in the same mode as the archive you restored. If you restored from a passphrase backup, opening the safety backup needs that same passphrase.

Who may do this

All three operations — create, inspect and restore — require the admin role, because a full-instance backup contains every secret in re-encryptable form. This is one of the few places the role check is actually enforced; see Security model for why you should not read more into that than it deserves. On an instance running with authentication disabled the check is a no-op, consistent with every other endpoint being anonymous in that mode.

How this relates to a file-level backup

Copying files off the disk is a perfectly reasonable backup strategy, and for a stopped instance it captures more than a .kgbak does — run history and user accounts included. But it has one failure mode that loses data permanently, and it is the single most important thing on this page.

The database and the credential key must be backed up together

Knotarium.db holds every credential as ciphertext. .credential-key — sitting beside it in the data directory — is what decrypts them. A copy of the database without that key leaves you with credentials that can never be read again: not by you, not by the application, not by anyone. Restoring such a backup gives you an instance whose workflows all reference credentials that will not resolve, and the only repair is to re-enter every secret by hand. Back up the whole data directory as a unit.

The trap is easy to fall into because the key is a dotfile that a naive copy of *.db silently misses, and because nothing goes wrong until the day you restore. It is also why Database__ConnectionString deserves care: setting it moves only the database and leaves the key in the data directory, so the two can drift apart without anyone intending it.

The comparison in full:

A .kgbak snapshotA file-level copy
SecretsCarried decrypted inside the envelope, re-encrypted on restoreCarried as ciphertext — useless without the key file
Portable to another hostYes, with a passphrase backupOnly if the key file travels too
Run historyNoYes
User accountsNoYes
Audit logNoYes
Needs the instance stoppedNoYes, for a consistent copy
Restore is guardedYes — disarm, preview, type to confirm, safety backupNo — you are copying files over a live database

In practice the two complement each other. A passphrase .kgbak is the thing you keep off-site and the thing you use to move an instance; a copy of the whole data directory, taken with the process stopped, is the thing that gets you back exactly where you were including history. What neither of them survives is a database backed up without its key.

Where the data directory is, what else lives in it, and how to move it are covered in the configuration reference.
