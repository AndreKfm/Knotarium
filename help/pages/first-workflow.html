Your first workflow

This walkthrough starts at a running instance you have never signed into and ends with a workflow that calls a real HTTP endpoint, logs what came back, and runs on a schedule. It takes about fifteen minutes. Nothing here needs a credential, a capability switched on, or an AI provider — the whole path works on a default install.

Before you start

You need a running instance. If you do not have one yet, the install page covers every way of getting one, and all of them end at the same address. The rest of this page assumes you are looking at http://localhost:43120 in a browser.

Create the administrator

The first screen is the sign-in page, but on a fresh instance it is in setup mode: instead of Sign in to continue it says Create the first administrator, and explains that the instance has no users yet. This mode appears only while sign-in is enabled and no account exists, so it is a one-time screen.

Fill in Username, Password and Confirm password, then press Create admin & continue. The account is created with the admin role and you are signed in immediately.

The length rule is enforced on the server, not in the form

The password must be at least eight characters. The browser only checks that the two password fields match — the length rule lives in the backend, so a short password produces the server's error message after you submit rather than stopping you as you type. There is no complexity requirement beyond length, and usernames are stored lower-cased, which makes signing in case-insensitive.

What you are looking at

You land on the dashboard, headed Workflow Control Center. On a brand-new instance the workflow list is replaced by a welcome panel that reads Welcome — let's build your first workflow, offering a blank canvas or a sample to install. That panel disappears for good once you have a workflow, which is why the rest of this page navigates explicitly rather than relying on it.

The bar across the top is the whole navigation. There are no addresses to type — the interface keeps its current screen in memory rather than in the URL, so bookmarking a particular view is not possible and the browser's back button does not move between screens.

On the right-hand side of the same bar are the runtime arming switch, a Tour button that replays the guided introduction, a Help link that opens this documentation in a new tab, and the signed-in user menu. The wordmark on the left carries the build version and returns you to the dashboard.

Install a starter template

Building the first workflow by hand teaches you the editor slowly and badly. Installing a starter and taking it apart is faster. Open Templates › Browse — the Templates screen has four tabs, Browse, Library, Import and Export, and the first is the built-in gallery.

Sixteen starters ship with the product, all authored by the project and all in the starter category. The ones worth knowing before you pick:

TemplateWhat it contains
Hello WorldA start node, one Log node, an end node. The smallest thing that runs.
Set and Use a VariableStores a value, then logs it back through a variable reference.
Delay Then LogWaits two seconds and logs. Shows the non-blocking Delay node on the timeline.
Fetch from an APIAn HTTP request whose success and error branches are logged separately.
HTTP POST a PayloadThe same shape with a method, a body and headers.
Scheduled API FetchA cron schedule driving an HTTP request and a log.
Webhook ReceiverLogs the JSON payload of every inbound webhook call.

The remaining starters are the AI ones — summarisation, support triage, evidence checking, semantic diff and two that demonstrate the agent node. All of them need an AI provider configured first, so they are the wrong place to begin.

Pick Fetch from an API. It is the one this walkthrough follows, and it is the most honest representative of real work: a call goes out, something comes back, and the two outcomes are handled separately.

Click the card's Use template button. The card expands to show a Workflow name field pre-filled with the template's name, and the button becomes Create workflow. Change the name if you like, then confirm. The button reports Created when it is done. There is also a Preview toggle on each card if you want to see the graph before committing to it.

Installing a template creates a draft, not a running workflow

What you get is a fresh, unpublished draft. It is yours to edit and it will not run on its own — a template can never quietly start doing things on your instance just because you installed it.

Reading the canvas

Open the new workflow. The editor has three regions: the node palette on the left, the canvas in the middle, and the property inspector on the right.

The important detail is the pair of edges leaving the HTTP Request node. Most nodes have a single output; this one has success and error, so a failed call is a branch you handle rather than an exception that kills the run. The starter logs both, which is why there are two Log nodes.

Click the HTTP Request node. The right-hand panel changes from Property Inspector to HTTP Request Node Properties and shows the fields: URL, Method, an Authentication section whose Type offers no authentication, a bearer token, basic authentication or a custom API-key header, and then Headers and Body.

Now click one of the Log nodes and look at its message. It contains something in the shape of {{ $node.<id>.output.<field> }} — that is how a node reads what an earlier node produced, and it is the single most important piece of syntax in the product. The core concepts page explains it properly.

The toolbar above the canvas

Along the top of the editor are Back, the workflow's name as an editable field, a readout of the latest and active version numbers, a runtime-version picker, and the two buttons that matter: Save & Publish and Run. Neither has a keyboard shortcut.

A separate floating toolbar sits at the top right of the canvas itself with layout tools — Center, Tidy, Grid, Note, Template, Group, Extract, Ungroup and History. Tidy auto-arranges the graph left to right and is the fastest way to make an imported workflow readable. The question-mark button at the end opens the shortcut list, which you can also reach by pressing ?.

Publish, then run

Press Save & Publish first. This is not optional housekeeping — it is a precondition. Publishing freezes the current draft as an immutable numbered version, and the version readout in the toolbar updates to show it.

If the graph has problems, the button reports the count instead — publishing fails until they are fixed, though saving still keeps your draft. When there is nothing to publish, the button reads Saved.

The canvas is never what executes

Every run executes a published version, including the one you start by hand. The draft you are editing is not runnable — there is no code path that executes it. Pressing Run first activates the version selected in the toolbar's runtime-version picker, then starts a run of it; the button's tooltip says exactly that. On a workflow that has never been published there is nothing to activate, so the button is disabled and its tooltip reads Publish a version (Save & Publish) before running. If you edit the canvas and press Run without publishing again, you re-run the old version and see none of your changes.

Now press Run. A notification appears reading Run started. with a View execution button. Click it.

A manual run does not need the runtime armed

The arming switch in the header gates automatic triggers — schedules, polling and the like. Pressing Run yourself always works, armed or not. That separation is deliberate: you can build and test all day on an instance that will not fire anything on its own.

Watching the execution

The Execution Visualizer shows the same graph with live state on it, plus an Execution Timeline panel listing the nodes in the order they ran with a duration for each. The header carries the workflow name, a Live run badge while it is still going, and a truncated run identifier.

Nodes on the canvas pick up a status badge as they finish: Completed, Failed, Waiting, Retrying, Manual or Cancelled.

There is no badge for a node that is running

A node that is currently executing, or one that has not started, carries no badge at all — the in-progress state is conveyed by the node's styling and by the timeline, not by a label. If you are watching a fast workflow you will simply see badges appear. Note also that the timeline labels a finished run Success where the node badge says Completed; they mean the same thing.

For the Fetch from an API starter you should see the HTTP Request node complete, the success branch's Log node complete, and the error branch's Log node never run at all. That is branching working correctly — an untaken branch is skipped, not failed.

Stepping through afterwards

Press Step Through. This is the feature worth learning early: it opens an inspector that walks the run node by node, showing a Step counter and three panels — Inputs, Variables at this step and Outputs.

This is a recording, not a live debugger. It works just as well on a run from last week, because every run is journaled as it happens. When someone reports that a workflow did the wrong thing on Tuesday, you open Tuesday's run and read what each node actually received.

Make it yours

Go back to the editor. The starter points at a public endpoint; point it at something you care about instead.

  1. Select the HTTP Request node and replace the URL with your own endpoint. Leave Method on GET for now.
  2. If your endpoint needs a key, set Type under Authentication and attach a credential. The secret is stored encrypted and referenced by the node — it is never written into the workflow itself, which is what makes a workflow safe to export.
  3. Press Save & Publish, then Run again, and use Step Through to confirm the response looks the way you expected.

The Headers field accepts either a JSON object or one Key: Value pair per line. The Body field is sent as JSON unless a header says otherwise, and it accepts expressions — which is how you send data that an earlier node produced.

Add a trigger

So far the workflow only runs when you press a button. To make it run on its own you add a trigger node from the palette on the left, in the section headed Trigger. Click a palette entry to drop it on the canvas, or drag it — dragging one onto an existing wire inserts it into that connection.

Palette entryStarts a run when
StartYou press Run. This is the manual entry point, and it is what the starter already has.
Cron SchedulerA cron expression matches, in a time zone you choose.
Webhook TriggerAn inbound HTTP call arrives.
Polling TriggerA source it watches has changed.
Error TriggerAnother workflow fails. This is the entry point of a global error handler.
Do not look for a "Manual Trigger" node

The catalog does contain a node called Manual Trigger, but it is deliberately hidden from the palette because it duplicates what Start already does. Both are manual entry points. Use Start.

Add a Cron Scheduler and connect it to the HTTP Request node. Its property panel offers a Frequency helper alongside the raw Cron expression and Time zone fields, both of which are required. Set it to something frequent while you are testing.

Three switches, all of which must agree

A scheduled workflow that never fires is almost always one of these, and they are independent:

  1. Publish and activate a version. Every run executes the active published version, so adding the scheduler to the canvas changes nothing until you publish. Pressing Run activates the version in the toolbar picker as a side effect, which is a fast way to make the version you just published the active one — and an easy way to activate the wrong one without noticing.
  2. Enable the workflow. The per-workflow enabled flag gates schedule, webhook and polling triggers. Disabling it also cancels runs already in flight. Manual runs can still be started either way.
  3. Arm the runtime. The global switch in the header gates automatic triggers across the whole instance.
Editing disarms the runtime

The runtime disarms itself when you are editing, so that half-finished work cannot fire. It also disarms when the disk drops below its free-space floor, and it does not re-arm on its own afterwards. If nothing has run for a while and you cannot see why, check the arming switch before anything else.

Watching it fire

With all three switches set, wait for the schedule. New runs appear on the dashboard's operations timeline, and each workflow row also has a play button — its tooltip reads Trigger Run — so you can start one from the list without opening the editor.

What to learn next

You now have the loop that everything else builds on: draw, publish, run, inspect, adjust.
