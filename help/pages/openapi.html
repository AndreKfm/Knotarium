Importing an OpenAPI specification

Point Knotarium at an API's own description and it generates a node for that API — one node per specification, with every operation available as a dropdown value. This is the fastest route from "we have an internal REST service" to "a workflow calls it", and it replaces hand-assembling URLs, headers and authentication in an HTTP Request node. The screen is API Importer.

How the screen is laid out

API Importer is split into a narrow left panel and a main area, with two modes selected by the panel's own tabs:

  • APIs — the list of imported specifications, with an Import Spec button above it. Selecting one fills the main area with its operation browser.
  • Server Configs — the manager for the base URLs and authentication settings the generated nodes call through.

The two halves are separate on purpose. A specification says what an API can do; a server configuration says which instance of it you are talking to and with what credential. One imported specification can be pointed at staging and at production by selecting a different server configuration per node, with no re-import.

Importing a specification

Import Spec opens a dialog offering three routes, all of which end in the same parse. OpenAPI 3.0, OpenAPI 3.1 and Swagger 2.0 are accepted, in either JSON or YAML.

TabUse it when
Paste ContentYou have the document in your clipboard. This is the default tab.
Upload FileYou have a file. Click the drop zone or drag a file onto it; the picker filters to .json, .yaml and .yml.
From URLThe API publishes its own specification. Enter an absolute http or https URL.

Fetching by URL

The fetch happens on the server rather than in your browser, which is what makes cross-origin specification URLs work at all — most API hosts do not send the CORS headers a browser would demand. A URL that is not absolute, or that uses a scheme other than http or https, is rejected before any request is made, and a non-success response or an empty body is reported as an import failure rather than being stored.

Because the request goes out from the server, it goes through exactly the same egress policy as an HTTP Request node. With the default Security__HttpEgress__DenyPrivateNetworks setting left on, a specification hosted on a private, loopback or link-local address is blocked — which is a common surprise when the API you want to import is on the machine next to you. Paste or upload the document instead, or change the egress policy deliberately; see the configuration reference.

The URL tab also offers Allow self-signed / untrusted certificate. It applies to that one fetch and skips TLS certificate validation entirely, which is reasonable for a development or LAN server using its own certificate and unreasonable anywhere else. Egress rules still apply when it is ticked — it relaxes certificate checking, not the network policy.

The spec ID field

Every import accepts an optional Spec ID. Left blank, the identity is derived from the specification's title: lower-cased, with every run of characters outside a–z and 0–9 collapsed to a hyphen and leading and trailing hyphens trimmed. An explicit value is slugified by the same rule.

Two APIs with the same title merge into one version history

The identity is the title slug, so importing two genuinely different APIs that both call themselves "API" makes the second one look like a new version of the first. Nothing warns you; the earlier specification simply becomes an old version of a spec now named after the newer one, and the generated node's operation list is replaced. Setting an explicit Spec ID on at least one of them is the only way to keep them apart, and it has to be done at import time.

Browsing what was imported

Selecting a specification in the left panel shows its title, its declared API version, and the current internal version number, above a browser with two tabs. Each tab carries a count badge.

Operations

Operations are grouped by their OpenAPI tag, with one collapsible section per tag showing how many operations it holds. Every group starts expanded. Each row shows the HTTP method as a colour-coded badge — green for GET, blue for POST, amber for PUT, red for DELETE, violet for PATCH, grey for HEAD and for anything unrecognised — followed by the path template and, where the specification supplies one, the operation's summary.

Operation rows are draggable. Dragging one onto the canvas creates a node of the generated package with that operation already selected and an empty argument object, which is the quickest way to wire up a call. If the drop lands inside a loop node, the new node is parented to that loop.

When the specification declares servers, a strip above the list shows the first one with a Use this spec's server button. Pressing it switches to Server Configs and opens the create form pre-filled with that base URL and the name Spec Server — a shortcut, not an automatic configuration. You still have to choose a security scheme and save it.

Schemas

The Schemas tab lists the named schemas the specification defines, one card each, showing the schema name and its description. View JSON expands the card to show the schema pretty-printed; if the stored text is not valid JSON it is shown verbatim rather than failing. The tab is read-only — it exists so you can check the shape of a request body or response while authoring, without leaving the application.

What an import generates

Importing does two things: it stores the parsed specification as a new version, and it generates a node package so the API shows up in the palette. The package is generated deterministically from the specification — the same document always produces the same package.

The generated package

The package id is openapi. followed by the specification's slug with every character outside a–z, 0–9 and - stripped out. A specification whose slug reduces to nothing becomes openapi.spec. Its manifest is fixed apart from the operation list:

No C# is generated and nothing is compiled. Every openapi.* node runs through one pre-compiled interpreter that reads the stored specification at run time, which is why importing a large API is fast and why these packages carry no source and no signature.

Side effects are assumed, not inferred

The manifest marks the whole package as a non-idempotent side effect regardless of which operations it contains. A specification of nothing but read-only GET endpoints is still treated as unsafe to replay blindly, because the classification is per package and the operation is chosen per node at author time. That is the conservative direction to be wrong in, but it does mean recovery behaviour is not tuned to the individual call.

The node's four parameters

ParameterRequiredExpression?Meaning
operationIdYesNo Which operation to call. The manifest carries the specification's full list of operation ids as the allowed values, so this renders as a dropdown rather than a free-text field.
serverConfigIdYesNo Which server configuration to call through — the base URL, its authentication, and its variables. A run fails immediately if it is empty or names a configuration that no longer exists.
specVersionNoNo Pins the call to a specific stored version of the specification. Left blank, the latest version is used.
argumentsNoYes The call's inputs — path parameters, query parameters, body — as a JSON object. This is the only parameter that accepts expressions, so it is where upstream data is threaded in. It defaults to an empty object.

Because operationId is an enumerated value drawn from the manifest, an operation removed from the API in a later import disappears from the dropdown — but a node already configured with it keeps the stored value. That node will fail at run time rather than at author time, which is the case specVersion exists to rescue: pin the node to the version that still contains the operation while you migrate it.

Server configurations

A server configuration is the other half of every generated call. Each one carries a name, a base URL, a security scheme, an optional linked credential, an insecure-certificate flag, and any number of server variables. New Config creates one; each card offers Edit and Delete, with a confirmation on delete.

FieldNotes
NameRequired. Shown in every picker that offers server configurations.
Base URLRequired. The origin the operation's path template is appended to.
Allow self-signed / untrusted certificateSkips TLS validation for calls to this server. The egress policy still applies.
Security SchemeOne of None, API Key, Bearer Token, Basic Authentication, or OAuth2 Client Credentials.
Linked Secret / CredentialThe stored credential whose value the scheme uses. For Bearer, the secret value is the token itself, sent as an Authorization: Bearer header.
Server VariablesKey-and-value pairs substituted into a templated base URL, for specifications that parameterise their server — a region, a tenant, an environment.

The credential dropdown lists secrets that already exist, and + New secret creates one inline without leaving the form: give it a name and paste the value, and it is stored encrypted with only the name visible afterwards. This is the recommended route — a token typed into a node property is an ordinary string, while a token stored as a credential is encrypted at rest and can be swapped without touching any workflow.

Deleting a configuration breaks the nodes that referenced it

Nodes store the server configuration's id, and nothing checks whether any node is using a configuration before deleting it. The confirmation dialog warns only that the action cannot be undone. Every node pointing at the deleted id then fails at run time with a message that the configuration was not found — at run time, not at publish time. Recreating a configuration with the same name does not help, because a new id is minted.

Re-importing and version history

Importing a specification whose id already exists does not replace the previous one. A new specification version is stored, its number increments, and the node package is upserted with a new package version numbered 1.0.<spec version> — so the third import of a specification produces package version 1.0.3. The left panel shows the latest version number next to each entry.

Keeping the history is what makes specVersion meaningful: a node pinned to an older version keeps calling the API the way that version described it, even after a re-import changed paths or parameters. Nodes that leave specVersion blank pick up the new version immediately, with no republish and no warning — convenient when the API added an endpoint, dangerous when it changed one.

Capping the history

Version history grows without bound by default. The retention sweep can cap it:

SettingDefaultEffect
Retention__MaxOpenApiSpecVersionsPerSpec 0 The number of specification versions kept per specification. Zero disables the cap and keeps every version forever. Any positive value keeps that many of the highest-numbered versions and deletes the rest.

The cap is applied per specification, by version number rather than by age, during the same periodic sweep that prunes run history — so a change takes effect on the next sweep rather than immediately. As with the other retention settings, the value shown under Settings › Retention is stored in the database and overrides the configuration file once it has been set there.

The cap deletes versions that nodes may be pinned to

Nothing consults specVersion before pruning. Setting the cap to 3 on a specification you have imported ten times deletes versions 1 through 7, and any node pinned to one of them starts failing. If you rely on pinning, either leave the cap at zero or set it high enough to cover every version still referenced.

Deleting a specification

The delete button on a specification row asks for confirmation and warns that it removes the specification and all its imported versions permanently. Workflows that reference the generated package are not consulted.

Polling an imported operation

The Polling Trigger can call an imported operation on a schedule instead of hitting a raw URL. Set its Source Kind to openapi and the form swaps its HTTP fields for three OpenAPI ones:

  • Server Config — required; the same list the generated nodes use, each entry showing its name and base URL.
  • API Spec — required; which imported specification to draw operations from.
  • Operation — required; every operation across every tag of that specification, labelled with its method, its path template and its operation id.

Only the server configuration and the operation are saved on the node. The specification selection is interface state used to populate the operation list, which has a visible consequence: reopening the form makes it scan the imported specifications to work out which one owns the saved operation id. If two specifications happen to define the same operation id, the first match wins and the dropdown may show the wrong specification — the saved operation id is still correct, but do not trust the spec picker as a record of your intent.

The rest of the form is shared with the HTTP source. Interval (seconds) defaults to 60 with a minimum of 1. Change Detection decides when a poll counts as something new and offers five strategies:

StrategyFires when
etagThe response's ETag differs from the last one seen.
last-modifiedThe response's Last-Modified header moved.
hashThe response body hashes differently. The default, and the one that works without server cooperation.
json-cursorA field inside the response changed. Selecting this reveals a required JSON Cursor Path field taking a JSONPath expression such as $.data.cursor.
alwaysEvery poll fires, whether anything changed or not.

Choosing always on a short interval turns the trigger into a scheduler that starts a run every interval regardless of the API's state, which is occasionally what you want and more often an accident. If the concern is that the API sends no useful cache headers, hash is the strategy to reach for.
