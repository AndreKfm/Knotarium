REST API

Everything the user interface does, it does over this API — there is no private channel and no second protocol. That makes the whole product scriptable, and it makes the API surface a security boundary worth understanding before you expose an instance to anything. This page enumerates the routes that exist, the authentication rules that apply to them, and the handful of responses that mean something other than "your request was wrong".

Base address and shape

Every route below is rooted at /api on the instance's own address — by default http://localhost:43120. Requests and responses are JSON except where a route is explicitly noted as multipart upload or file download. There is no API version prefix and no published OpenAPI document for Knotarium's own API; the routes here are the contract.

One route sits outside /api: GET /help serves this documentation and is anonymous, so the manual is readable from the sign-in screen.

Authentication

Authentication is a session cookie named kg_auth, issued by POST /api/auth/login. It is HttpOnly, SameSite Lax, HTTPS-only outside development, and slides forward on a seven-day expiry. There are no API keys and no bearer tokens: a script authenticates by logging in and keeping the cookie.

With Auth__Enabled at its default of true, every endpoint requires an authenticated user unless it explicitly opts out. An unauthenticated call gets 401 and an authenticated-but-unauthorized one gets 403 — this is an API, so neither redirects to a login page. A subset of routes additionally requires the admin role; those are marked below. 

# Sign in and keep the session cookie in a jar
curl -s -c jar.txt -X POST http://localhost:43120/api/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"admin","password":"…"}'

# Then use it
curl -s -b jar.txt http://localhost:43120/api/workflows

The anonymous routes

Exactly five endpoints opt out of authentication, and each has its own reason:

RouteWhy it is anonymous
GET /api/auth/statusThe interface must be able to ask whether an admin exists before anyone can sign in.
POST /api/auth/setupCreates the first administrator on an unconfigured instance. Only works while no accounts exist.
POST /api/auth/loginObviously. Rate-limited — see below.
POST /api/executionsThe machine-facing webhook trigger. Guarded by the arming switch, the workflow's enabled state, and an optional per-workflow secret rather than by a session.
POST /api/executions/resumeResumes a suspended run. Authenticated by the per-run correlation token, not by a session.
Turning authentication off removes the distinction

Setting Auth__Enabled=false makes every endpoint anonymous, including the capability toggle and the inline-code test — which together are remote code execution. Startup refuses to proceed in that configuration on a non-loopback binding for exactly that reason. The admin-role checks below become no-ops as well.

Rate limits

Two fixed-window limiters exist, both partitioned by remote IP address, both with no queue — past the limit the request is rejected immediately with 429.

  • POST /api/auth/login is limited by Security__RateLimit__LoginPerMinute, default 10 per minute, which is what blunts online password guessing.
  • POST /api/executions and POST /api/executions/resume share a limit set by Security__RateLimit__AnonymousMachinePerMinute, default 60 per minute. A busy webhook source behind a single NAT address is the realistic reason to raise it.

Nothing else is rate-limited, because everything else needs a session first.

Same-origin enforcement

Security__EnforceSameOrigin is Off by default. When enabled, an authenticated POST, PUT, PATCH or DELETE carrying an Origin header that matches neither this host nor a configured CORS origin is rejected with 403 and the body {"message":"Cross-origin state-changing request rejected."}. A request with no Origin header at all passes, which is why command-line clients are unaffected.

It is off by default because a reverse proxy that rewrites Host produces false rejections. On a directly bound instance it is worth turning on: it is defence in depth over the SameSite cookie.

CORS

With Cors__AllowedOrigins empty — the default — any origin may call the API but credentials are refused, so a session cookie cannot be replayed from another origin. Listing origins switches to an allow-list that does permit credentials. Configure it only when a separate front-end origin genuinely needs to call this API; the bundled interface is same-origin in production and reaches the backend through the Vite proxy in development.

Status codes worth recognising

CodeWhere you meet it
202A run was accepted. The Location header points at the new execution.
401No session — or, on the webhook trigger, a missing or wrong X-Knotarium-Webhook-Secret.
403Authenticated but not an administrator, or the same-origin check rejected the request.
409State conflict: the runtime is disarmed, the workflow is deactivated, it has no active version, or a bundle install hit a same-version/different-hash collision.
422A bundle install was refused by the package verification gate.
429A rate limit, or the execution queue is full — see below.
Two different 429s

Past Execution__MaxQueueDepth (default 1000 pending runs) the webhook trigger answers 429 with a body naming the limit — "Execution queue is at capacity (1000 pending runs). Retry later." That is back-pressure from the engine, not the rate limiter, and it means the instance is accepting work faster than Execution__MaxConcurrentRuns can retire it. Backing off is the right response; raising the queue depth only delays the same conversation.

Triggering a workflow by webhook

This is the request most integrations actually need. It is anonymous, so no cookie is involved. 

curl -i -X POST http://localhost:43120/api/executions \
  -H 'Content-Type: application/json' \
  -H 'X-Knotarium-Webhook-Secret: 7f3c…' \
  -d '{
        "workflowDefinitionId": "invoice-sync",
        "inputVariables": { "orderId": "A-1029", "amount": 41.5 }
      }'

HTTP/1.1 202 Accepted
Location: /api/executions/6f1c0c8e-1a4d-4d21-9a9b-2c9a1f0e77b2

workflowDefinitionId is required; inputVariables is an optional object whose entries become the run's starting variables. The header is only required when a secret is configured for that workflow — workflows without one stay open, which preserves the older machine-facing contract. The secret is compared in constant time and is checked first, before arming and enabled state, so an unauthorized caller cannot learn anything about the instance from the response.

The request body is capped at Security__WebhookMaxBodyBytes, default 1 MiB, and the limit is enforced during the read so an oversized payload is never buffered.

Four things must all be true for a 202: a secret check that passes, an armed runtime, an enabled workflow, and an active published version. Each failure has its own 409 message, so the body tells you which one it was. A workflow that fails compilation answers 400 with a diagnostics array.

Why user management is admin-only

Without that gate any signed-in user could create an administrator account for themselves, then use it to enable the code-execution capability and run arbitrary C#. The escalation path from "can create users" to "owns the host" is that short.

Version probe

GET /api/version returns { "version": …, "buildTimeUtc": … }. The version comes from the assembly, with the git hash that source-link appends stripped off; the build time is the assembly file's last-write timestamp, which changes on every rebuild even when the version string does not. That second field is the reliable answer to "am I looking at the build I just deployed?". It is omitted when the assembly location is unavailable, which is the case for a single-file publish.
