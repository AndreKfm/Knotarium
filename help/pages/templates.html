Templates

A template is one workflow packaged as a portable file with its credentials removed. Use the built-in gallery to start from a working example, save your own workflows into a library you can reinstall later, and hand a .kgtpl to a colleague knowing it cannot possibly contain one of your passwords. This page covers all four tabs of the Templates screen.

The four tabs

Templates opens on Browse and offers four tabs, in this order:

TabWhat it is
Browse The read-only gallery of starter templates shipped with the application. Nothing you do here can change it.
Library Templates you saved on this instance. Stored in the database, installable and deletable.
Import Upload a .kgtpl from somewhere else, inspect it, and create a workflow from it.
Export Package one of your workflows as a .kgtpl, or save it straight into the Library.

Choosing Export as template from the editor jumps to this screen with the Export tab already selected and the workflow preselected, so you rarely reach Export by clicking through the tabs.

What is inside a .kgtpl

A template file is a zip with the extension .kgtpl and the media type application/vnd.knotarium.template+zip. For the current format — schema version 1 — the archive contains exactly two entries and nothing else:

EntryContents
template.jsonThe manifest: name, author, description, tags, category, template version, creation timestamp, the workflow checksum, the declared credential slots and the declared parameters.
workflow.jsonThe exported workflow graph, with every credential reference already replaced by a slot: placeholder.

The closed entry set is enforced on read: an archive carrying a third file, a duplicate entry, or a schema version other than 1 is rejected outright rather than partially imported. This is deliberate anti-smuggling, and it is why editing a .kgtpl by hand and adding a stray file makes it unusable.

A template is not a bundle

A template is a single workflow with no node packages, no dependency lock and no signature. If you need to ship node packages alongside workflows, or you need the recipient to be able to verify who published the file, that is a bundle — see Bundles.

Content limits

Reading a template bounds the work before anything is deserialized into live types, so a hostile file fails fast instead of exhausting memory:

LimitValue
Maximum JSON nesting depth64
Maximum nodes in the workflow2000
Maximum properties on one node200

After those checks, the checksum recorded in template.json is recomputed from workflow.json and compared. A mismatch reports that the archive may be corrupt or tampered with, and the import stops. Note what this check does and does not buy you: it detects accidental corruption and casual edits, but since the checksum travels inside the same file as the content, anyone who edits the workflow can recompute it. A checksum is not a signature.

Browse — installing from the gallery

The gallery is built from reviewable, unzipped sources shipped next to the application rather than from committed binaries, and each entry is packed into a consistent archive on demand. Every built-in template in the current build carries the category starter, the author Knotarium, and version 1.0.0:

Search matches against the name, the description and the tags at once; the category chips beside the search box filter to one category, with All as the default. Because every built-in template is currently in the starter category, the chips are of limited use until you have imported templates of your own.

The AI starters need setting up first

All six AI templates install and open happily with no configuration, but they will fail at run time until a provider is configured under Settings › AI Provider. The Order Concierge template needs more than that: the aiAgent capability enabled under Settings › Capabilities, and the companion Tool: Order Status Lookup template installed and published so it can be selected as the agent's tool.

The install form

Each card shows the name, the author, the template version, the description, its tags, and a count of how many credential slots it declares. The first click on Use template does not install anything — it expands the card into the install form. The button then reads Create workflow, and that second click is the one that creates something.

The form has up to three parts, and only the first is always present:

  • Workflow name — prefilled with the template's name and editable.
  • Parameters — one input per declared parameter, shown only when the template declares any.
  • Credential slots — one binding row per declared slot, shown only when the template declares any.

None of the built-in templates declare parameters or credential slots, so installing a gallery starter is a matter of accepting or changing the name and pressing Create workflow. Parameters and slots become relevant the moment you import someone else's template or export one of your own.

The new workflow is created as an inactive draft under a freshly minted workflow id, so installing the same template twice gives you two independent copies rather than overwriting the first. If a workflow with the chosen name already exists, the new one is saved with a numeric suffix — a second Hello World becomes Hello World (2). From the gallery, a successful install takes you straight to the new workflow on the canvas.

Parameters

A parameter is a non-secret value the template's author left blank for you to supply: a channel name, a base URL, a polling interval. The workflow references it with a {{param:<key>}} token, and the token is replaced with your value as the workflow is created. Four types exist, and each renders a different input:

TypeInputAccepted
stringText boxAnything.
numberNumber boxParsed with invariant culture, so the decimal separator is a full stop regardless of your locale.
booleanDropdowntrue or false.
enumDropdownOne of the options the author declared.

Required parameters are marked with an asterisk, and the install button stays disabled until every one of them has a value. Optional parameters are guaranteed to have a default — a template declaring an optional parameter without one is rejected at export time, which is what makes the value map complete at install time.

When a property's entire value is a single token, the substituted value keeps its declared type: a number parameter produces a JSON number, not the string "30". A token embedded in a longer string is interpolated as text instead. Two things are rejected rather than substituted: a value that is itself a slot: token, and a value containing a {{param:…}} token, both of which would otherwise let a supplied value inject a placeholder into the credential-binding pass that runs immediately afterwards.

An undeclared parameter fails the install

If the graph references {{param:foo}} but the manifest never declares foo, the install is refused with an error naming the undeclared key. This is treated as an authoring bug, not a "configure it later" state, because a workflow persisted with a literal token in it would silently do the wrong thing at run time. An unbound credential slot, by contrast, is allowed through — see below.

Credential slot binding

This is the mechanism that makes sharing a workflow safe. When a workflow is exported, every node property whose value is one of your credential ids is replaced with a symbolic token slot:<key>, and the manifest declares one slot per distinct credential. The slot carries a display name and, optionally, a description and a required credential type. It never carries the credential itself, the credential's id, or anything derived from its secret value.

Slot keys are derived from the credential's display name by lower-casing it and replacing every run of non-alphanumeric characters with a hyphen, so Billing API becomes billing-api. The key must start with a letter and is at most 64 characters; a name that would produce a key starting with a digit is prefixed with c-, and a name that produces nothing usable falls back to credential. Colliding keys — including collisions that differ only in case — get a numeric suffix. Several nodes referring to the same credential collapse into a single slot, so a workflow with eight HTTP nodes on one API asks you to bind once, not eight times.

In the binding form each slot is a row showing its display name, its required credential type when the author declared one, the slot: token itself, and a dropdown of your own credentials. The row's icon and token turn from amber to green once bound.

Required credential type is advisory today

A slot may declare a requiredCredentialType, and it is displayed next to the slot name — but nothing enforces it. Credentials carry no type in the current schema, so there is nothing to match against, and binding a slot marked as needing an API key to a username-and-password credential is accepted without complaint. It will fail later, at run time, in the node that tries to use it.

What is validated on install is that every slot key you supply a binding for was actually declared by the manifest, and that every credential id you bind to still exists. Either failing rejects the whole install with a field-level error list, and nothing is written — the install runs inside a single database transaction, so there is no half-imported workflow to clean up.

Leaving a slot unbound is permitted from the gallery and library, though the Import tab disables the install button until every slot has a binding. An unbound slot leaves the slot: placeholder in the saved workflow, and the install result reports Configuration required together with the names of the open slots. Such a workflow is stored as an inactive draft and cannot be published or run until you bind the remainder on the workflow itself.

Previewing before you install

The expanded card carries a Preview button that renders the template's graph as a read-only mini-canvas: one card per node showing its label and its node type, laid out left-to-right, with the edges drawn between them. It is deliberately inert — no dragging, panning, zooming or selecting.

The preview is generated from the template with your current parameter values already substituted, so it shows what you are about to create rather than the raw template. It does not create a workflow, and it is fetched fresh each time you open it. Pressing the button again hides it.

Import — installing someone else's template

The Import tab takes a .kgtpl by clicking the drop zone or dragging a file onto it. The file is inspected immediately, before anything is created: the manifest is parsed, the checksum verified, the graph compiled to assess compatibility, and the node types scanned for privileged capabilities. Nothing is written to the database during inspection.

The inspection panel then shows:

  • The template's name, author and version.
  • A compatibility badge, either Runs here or Check compatibility.
  • The number of credential slots, and that it installs as a draft.
  • The privileged-node acknowledgement, when applicable.
  • The workflow name, the parameter form and the slot binding rows.

Compatibility is assessed by compiling the graph rather than by comparing version numbers alone, because a workflow can reference node types that simply do not exist on this instance. An unknown node type marks the template as not runnable here; other compiler diagnostics — including the expected complaint about a still-unbound credential slot — are surfaced as warnings but do not block anything. A template flagged as not runnable can still be imported as a draft so you can open it and see what it wanted.

If a workflow of the same name already exists, a live hint under the name field tells you the import will be saved with a (2) suffix rather than silently merging into or replacing the existing one.

Three buttons sit at the bottom of the panel. Preview behaves exactly as it does in the gallery. Save to library stores the uploaded archive under the Library tab without creating a workflow — useful when you want the template available for later but do not want a draft right now. Create workflow performs the install. That last button stays disabled until every credential slot is bound, every required parameter is filled, and the privileged-node acknowledgement (if shown) is ticked; the reason it is disabled is spelled out in text beside it.

The privileged-node acknowledgement

Inspection resolves every distinct node type in the template against its package manifest and collects the ones declaring a privileged capability — filesystem access, code execution, or database access. If any are found, an amber panel appears listing each privileged node by its display name together with the capabilities it carries, followed by a checkbox reading I understand and want to install this template.

Until that box is ticked, Create workflow stays disabled and a line beside it reads that you must acknowledge the warning. The prompt appears on the Import tab only, because that is the only place a template of unknown provenance enters the system — the built-in gallery ships with the application and the library contains templates you already accepted once.

The acknowledgement is a speed bump, not a sandbox

Ticking the box does not grant anything, and leaving it unticked does not revoke anything: it exists so that installing a workflow which can write to your disk or execute code is a deliberate act rather than an accident. The capabilities themselves stay disabled until you enable them under Settings › Capabilities. The corollary is the uncomfortable one — a template from an untrusted source that you install and whose capabilities you then enable has exactly the access those capabilities describe. Read the graph before you enable anything.

Export — packaging a workflow

Export packages a workflow's currently published state. This matters: unsaved canvas edits and unpublished drafts are not what gets exported, and a workflow that has never been published has nothing to export — the attempt reports that no version is available.

The form collects the metadata that will be shown to whoever installs the result:

FieldDefault when left blank
WorkflowRequired; there is no default.
Template nameThe workflow's own name. Also determines the file name.
AuthorEmpty.
DescriptionEmpty.
TagsEmpty. Entered as a comma-separated list.
Categoryuncategorized.
Version1.0.0. Must be a valid semantic version or the export is refused.

A live manifest preview beside the form shows the file name that will be produced, derived from the template name and the version. The name is lower-cased and every run of non-alphanumeric characters becomes a hyphen, so a template named Nightly DB Backup at version 1.3.2 downloads as nightly-db-backup-1.3.2.kgtpl. 

# Template name and version determine the file name
"Nightly DB Backup" + "1.3.2"  →  nightly-db-backup-1.3.2.kgtpl

Below the manifest preview sit three counters — nodes, slots and secrets. The secrets counter is a constant zero, and it is honest: portabilization runs before the archive is written, and the export walks every node property at every depth, including inside nested objects and arrays. Any string whose whole value matches one of your credential ids is rewritten to a slot: placeholder. Once the export completes, the panel lists each credential that was lifted, showing the original credential's display name and the slot token it became, and the confirmation banner states plainly that the file is safe to share.

Only credential references are stripped

Portabilization replaces values that are credential ids. A secret you typed directly into a node property — an API key pasted into a header field instead of stored as a credential, a password inside a connection string, a token in a URL — is an ordinary string as far as the exporter is concerned, and it travels in the file. If a workflow has any hand-entered secrets, move them into credentials before exporting it.

The Export template button downloads the file. Save to library packs the same archive and stores it on this instance instead of downloading it. Both are disabled until a workflow is selected, and both clear their confirmation banner as soon as you change any field, so a stale "Exported" message can never sit above a form you have since edited.

Library — your own saved templates

The Library tab lists templates saved on this instance, most recently saved first. Templates arrive there in two ways: Save to library on the Export tab, which packs one of your workflows, and Save to library on the Import tab, which stores an archive someone sent you. In both cases the archive is verified before it is stored, so a corrupt file is refused rather than persisted.

Each library card installs exactly like a gallery card: Use template expands the install form, Create workflow creates the draft, and Preview renders the graph. Each card also carries a Delete button, which removes the saved template and nothing else — workflows already created from it are untouched.

Saving is an upsert, keyed to the source workflow

A template's id is derived from the workflow it was exported from, so saving the same workflow to the library a second time replaces the existing entry rather than adding a second one. This is what you want for keeping a library entry current, and a surprise if you expected two versions side by side: to keep both, export the older one to a file first.

Library entries live in the database, which means they are covered by a backup of the data directory and, equally, that they do not travel with the application if you move to a new instance without bringing the database. Anything you want to keep independently of this instance should be exported to a file.

What installing never does

Two properties are worth stating explicitly, because they bound the risk of accepting a template from someone else:

  • An install always creates a new workflow under a new id. It never modifies, overwrites or deletes a workflow you already have, even when the names collide.
  • The imported workflow is created inactive. Nothing about installing a template causes anything to run: you still have to publish it, enable it, and have the runtime armed.
