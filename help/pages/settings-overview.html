Settings overview

Everything an administrator changes at runtime lives on one screen, split into eight sections. This page is the map: what each section is responsible for, how quickly a change takes hold, and the one rule that catches people out — several of these screens write their values into the database, where they permanently outrank the same settings in appsettings.json.

Finding the screen

Open Settings from the application's navigation rail. The screen has its own left-hand sub-navigation headed Instance Settings, and a breadcrumb at the top of the content area reading Instance Settings / <section> so you can always tell which section you are on. Throughout this documentation a location is written as a click path — for example Settings › Sandbox — because the screens are React state and have no address of their own.

The screen opens on Notifications. There is one exception: when you arrive by pressing Grant access in File Access settings on a failed run, the screen opens directly on File Access with the denied path already filled in as a new grant. That shortcut is described on the File access page.

The eight sections

The sections are listed in the order the interface shows them. Two of them — Notifications and External Systems — are about integration rather than security; the other six are the ones that decide how much of the host a workflow can reach.

Notifications

Two cards. Error Workflow nominates one workflow to run automatically whenever any other workflow fails; it receives the failure context — the workflow, the failed node and the error — on its Error Trigger node. An error workflow is never re-triggered by its own failures, so a broken alerting workflow cannot spiral. Select None (disabled) to switch the mechanism off entirely.

Below it, the channel manager holds the delivery endpoints a failure alert can be sent to. Three transports exist: a generic webhook that posts the alert payload as JSON, a Slack incoming webhook, and e-mail over SMTP. A channel's configuration — including its URL, token or SMTP password — is stored encrypted, which is why channels live here under instance settings rather than inside a workflow.

AI Provider

Picks the vendor and model used by Generate with AI and the AI nodes, and points at the encrypted credential that holds the API key. Four vendors are offered: Anthropic, OpenAI, Azure OpenAI, and Google Gemini. Azure is the one that requires a base URL, because the endpoint is specific to your resource; for the others the base URL is optional and only needed to reach a proxy or a compatible gateway.

The key itself never enters this configuration — it is stored in the credential store and resolved server-side at the moment a request is made. If you have switched the egress policy to an explicit allow-list, remember to add the provider's host, or every AI call will be refused. The generator's token and length limits are separate startup settings, listed in the configuration reference.

File Access

Deny-by-default directory grants for the two file nodes, a free-space reserve that blocks writes which would fill the drive, and an escape hatch that grants unrestricted access. On a fresh instance nothing is granted, so every file operation fails until you allow a path. See File access.

Capabilities

Master switches for the privileged capabilities that have no finer-grained policy of their own. Turning one on is an instance-wide grant: every workflow can use it, including workflows that arrived by import or were generated by a language model. See Capabilities.

Sandbox

Complements Capabilities. Where that screen decides whether user-authored C# may run, this one decides how safely: in the backend process, or in pooled worker processes with operating-system limits on memory, CPU, run time and privileges. See Sandbox.

Retention

Two cards on one page. Data retention prunes old finished runs and their journals, and optionally caps version histories and the audit log. Disk-space guard is the backstop underneath it: when free space on the data volume drops below a floor, the runtime is disarmed so no new runs start. See Retention and disk space.

External Systems

This section manages the connection targets of an installed external-signal provider — the plugin that lets workflows react to events from an outside system and send actions back to it. For each target you configure a name, host, port and optional user with a stored password, and the manager adds three operations: Test checks connectivity before you save, Sync refreshes the live catalog of channels, events and actions that the canvas editor offers, and delete removes the target after a confirmation. Edits apply live; nothing needs restarting.

The section is deliberately vendor-neutral. Its heading, and even the noun it uses for a target, come from the installed provider's own descriptor rather than being hard-coded, so the same screen serves whichever connection manager you have. With no such plugin installed the section shows No configurable integration installed and nothing else — that is the expected state on a stock instance, not a fault.

Stored passwords behave the way you would want on an edit: leaving the password field blank keeps the secret already on file, and typing a value replaces it. There is no way to read an existing secret back out of the form.

Backup & Restore

Not a settings screen at all, but instance-level data management: it downloads a complete encrypted snapshot of the instance including its secrets, and performs the destructive restore. It is deliberately kept on its own page rather than sharing a screen with a webhook test button. See Backup and restore.

When a change takes effect

Nothing on this screen requires a restart, but "immediately" means different things depending on what is doing the reading.

  • Read on every use. The capability policy, the file-access policy and the AI provider configuration are fetched at the moment a node needs them. A capability you switch off stops the very next node execution that wanted it.
  • Applied to a live object. Saving the sandbox settings rewrites the running options object, so the execution mode changes for the next sandboxed run. The one caveat: worker count only sizes a new pool. An already-running worker pool keeps its current size until the application restarts, though the per-worker limits do apply to workers spawned afterwards.
  • Read at the top of a background cycle. Retention is re-read on every sweep and the disk-space policy on every check, so a change lands on the next tick rather than instantly. The retention sweep interval defaults to sixty minutes and the disk check to sixty seconds, with a thirty-second floor on the latter.
The first sweep is one interval late, on purpose

Both background workers wait a full interval before their first pass. A process that starts and stops quickly therefore never prunes anything and never trips the disk guard — which is what you want during upgrades and short-lived test runs, but does mean you cannot verify a new retention setting by restarting and watching.

These screens override the configuration file

This is the single most confusing behaviour in the product, and it is worth reading twice. Four groups of settings are persisted into the database the moment you save them, and the stored value then wins over the configuration file forever after. Editing appsettings.json or the matching environment variable afterwards appears to do nothing at all, and it fails silently — there is no warning at startup that a stored value is shadowing your configuration.

ScreenShadows the configuration section
Settings › Sandbox Security__Sandbox__*
Settings › Retention Retention__* and the disk-guard half of Storage__*
The arming switch in the header Runtime__Armed
Settings › AI Provider No configuration equivalent — the provider is database-only by design

The precedence is one-directional and only ever applied at startup. If no value has been stored, the configuration section stays authoritative — which is why a fresh instance that never opens this screen behaves exactly as its appsettings.json says. Once you save the screen once, that ceases to be true.

There is no "reset to configuration" button

Nothing in the interface clears a stored override and hands control back to the configuration file. The practical remedy is to set the value you want on the screen itself rather than in the file. Treat the configuration keys as the seed for a fresh install, and the screens as the steady-state control surface.

Two policies are stored in the database and have no configuration-file counterpart at all: the capability policy and the file-access policy. You cannot pre-seed them from appsettings.json, and an unset or unreadable stored value is treated as deny-everything rather than allow-everything. That is deliberate: the secure state is the one you get by doing nothing.

What is not on this screen

Several things administrators expect to find here live elsewhere, and knowing that saves a search:

  • Users and sign-in — the user list is reached from the Users button in the application header, not from Settings. See Users and sign-in.
  • Runtime arming — the armed/disarmed pill sits in the header so it is visible and reachable from every screen.
  • Credentials — there is no central credential manager. Credentials are created inline from the node property form that needs one, and selected by reference elsewhere. The honest account of that gap is on Users and sign-in.
  • Everything read at startup — the data directory, the database connection, the binding address, egress rules, execution concurrency, package signing keys. Those are in the configuration reference.
