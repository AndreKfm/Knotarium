Diagnostics

The diagnostics panel in the bottom-left corner of the canvas is the editor's report on whether the graph you have drawn can actually be compiled. This page lists every check that exists, which of them stop you publishing and which merely warn, how to jump from a message to the node or wire that caused it, and — just as usefully — which plausible-sounding checks do not exist, so you do not go looking for warnings that will never appear.

Where the messages come from

There is no rule engine in the browser. Every message you see is produced by the backend compiler and sent to the editor, which only presents and navigates them. That matters because it means the editor and the publish step agree by construction: what the panel shows is what publishing will decide.

Two streams feed the panel:

  • A live pass runs about half a second after the graph stops changing. It compiles the current canvas without saving anything and returns every diagnostic, including non-blocking ones. It is keyed to the graph's meaningful shape, so moving a node or changing the selection does not re-trigger it.
  • A blocking list is written whenever Save & Publish or Run is refused. Those diagnostics are the reason the operation failed.

The two are merged, de-duplicated, and sorted most severe first. If the same problem arrives from both streams it appears once.

A graph with no edges is never validated live

The live pass is skipped entirely when the canvas has no connections at all. A brand-new workflow with a few unwired nodes therefore shows an empty panel, not a clean bill of health. The checks run as soon as the first wire exists.

Reading the panel

The panel renders nothing when there is nothing to report — an empty corner means a clean graph. When it does appear, its header summarises the counts by severity, colour-coded red for errors, amber for warnings and blue for information, and the whole panel is bordered in the colour of the worst thing in it. Clicking the header collapses it to that summary bar, so it never has to be in your way.

Each row shows the diagnostic's code in brackets, its message, and where it applies — either · edge or · node followed by the node id. Clicking a row centres the canvas on the offending element and selects it, which also brings its properties up in the inspector. A row that names an edge frames the midpoint between that edge's two nodes; a row that names a node frames the node. A diagnostic pointing at something that no longer exists simply does nothing when clicked.

Edges with problems are also marked on the canvas itself, with a short label such as ⚠ type mismatch, ⚠ field type, ⚠ missing field, or ⚠ 3 issues when a single wire has several.

Errors and warnings

Severity is what decides everything. Only Error blocks. A warning never prevents a save, a publish or a run — it rides along with the successful response and stays visible in the panel. The severity model also has an Info level, but the compiler never produces one, so in practice you will only ever see errors and warnings.

Errors — the structural checks

CodeRaised when
ERR_MISSING_START_NODEThe workflow contains no trigger entry point at all. Entry points are nodes the manifest marks trigger-only, plus the built-ins Start, Manual Trigger, Webhook Trigger and Scheduler. A graph built from external device blocks is exempt.
ERR_INVALID_NODE_TYPEA node's type has no installed package manifest — usually a workflow imported from an instance that had a node package this one does not.
ERR_TRIGGER_WITH_INCOMING_CONNECTIONSSomething is wired into a trigger node. A trigger starts a run; nothing can lead to it.
ERR_MISSING_REQUIRED_PARAMETERA required parameter is absent, null, or blank.
ERR_INVALID_PARAMETER_TYPEA parameter declared as a number or a boolean holds something that is neither.
ERR_INVALID_EDGE_SOURCE · ERR_INVALID_EDGE_TARGETAn edge names a node that is not in the graph.
ERR_INVALID_SOCKET_MAPPINGAn edge is attached to an output or input port the node type does not declare.
ERR_CYCLE_DETECTEDThe graph loops back on itself. Loop-back edges into a For Loop or Parallel For Each container are expected and are not reported.
ERR_MISSING_SUBFLOW_ID, ERR_SUBFLOW_NOT_FOUND, ERR_SUBFLOW_MISSING_START, ERR_SUBFLOW_MISSING_END, ERR_RECURSIVE_SUBFLOWSub-flow resolution problems, covered in Sub-flows and grouping.

Two details are worth knowing because they explain surprising silences. A parameter whose value is an expression — a string that starts with {{ and ends with }} — is exempt from the type check, because the compiler cannot know what the expression will produce. And the generic input port names in and payload are always accepted on any node, whether or not the manifest mentions them.

The checks also short-circuit. Sub-flow inlining runs first and stops everything if it fails; if any node or edge error was found, cycle detection is skipped; and if a cycle was found, the missing-trigger check is skipped. So fixing one error can reveal a second one that was there all along. Clearing the panel usually takes a couple of rounds.

Warnings — the typed-socket checks

Three warnings compare what an output declares against what the input it feeds expects. They exist because a mismatch is usually a mistake, but they are advisory: the declared types come from manifests that cannot describe every real payload, so blocking on them would be wrong.

CodeRaised when
WARN_TYPE_MISMATCHAn output's declared type is not assignable to the input's declared type.
WARN_MISSING_FIELDThe input requires a named field that the output does not declare.
WARN_FIELD_TYPE_MISMATCHBoth sides declare the field, but with incompatible types.

The assignability rules are deliberately generous. There are six recognised types — string, number, boolean, object, array and any — and an enumeration or a credential reference counts as a string. Any type name the compiler does not recognise is treated as any and is never flagged at all. Beyond that: any on either side always passes, anything may flow into a string, a string may flow into a number or a boolean because it might parse, and object and array accept only themselves.

A wire with no matching parameter is not type-checked

The typed comparison only happens when an edge feeds a declared output into a declared, typed configuration parameter. Wires into the generic in or payload sockets have no parameter to compare against and are treated as untyped, so they never warn. Most control-flow wiring falls into this category.

Device-block diagnostics

Graphs containing an external device block are checked by a second, separate validator, whose results are merged into the same panel. It has exactly two rules and returns nothing at all when the graph has no device block:

CodeSeverityMessage
DEVICE_NO_TARGET Error Device block has wired pins but no target selected — its rules cannot run. Pick a target.
DEAD_END_WIRE Warning An event is wired but its path reaches nothing that runs — the wire does nothing.

Device pins are dynamic — they come from the block's configuration rather than from a manifest — so the ordinary socket checks skip them entirely and this validator covers them instead.

What actually blocks Save & Publish

Publishing runs four gates in order, and stops at the first that fails. Only the last of them produces the compilation diagnostics described above; the first three are separate checks with their own messages.

  1. Unbound credential slots. A workflow inserted from a template can carry placeholder credential references. Publishing refuses until each one is bound to a real credential, and names the slots.
  2. Incomplete Condition nodes. A Condition with neither valid logic nor a legacy operator cannot produce a definite branch. The message names the node ids and tells you to open and complete them in the editor. See Conditions and branching.
  3. Misconfigured device blocks. Only the error-severity device rule blocks; a dead-end wire warning does not.
  4. Compilation. Any diagnostic of severity Error refuses the publish, and the full diagnostic list comes back with the failure.

The same first three gates run when you activate an existing version, with slightly different wording, and restoring a version can only activate it if it compiles cleanly.

Save, publish, run — which are gated

ActionGated by
Saving the workflow definitionCompilation errors only.
Saving a draft versionNothing. Work in progress always saves.
Publishing · activating a versionAll four gates.
Triggering a runCompilation errors.
Importing a workflowNothing. Diagnostics come back as warnings and the imported version is left inactive.

In the editor, the Save & Publish button turns amber and counts the blocking errors — Save & Publish (2 errors) — but stays clickable, because pressing it still saves your draft. Only the publish half will be refused.

Checks that do not exist

It is worth being explicit about this, because these are the warnings people expect from a graph editor and then quietly assume are passing:

  • There is no orphan-node check. A node connected to nothing publishes cleanly and simply never runs.
  • There is no reachability analysis. A branch that can never be entered is not reported.
  • There is no duplicate-id check.
  • Expressions are never validated. A reference to a node that does not exist publishes without complaint and resolves to nothing at run time, as described in Expressions and data.

A clean diagnostics panel means the graph compiles, not that it is correct. The tools for correctness are a manual run and the run inspector.
