Expressions and data

Edges carry control, not values. When a node needs something an earlier node produced, it asks for it by name inside a {{ … }} expression. This page covers the two reference forms that exist, how a path into nested data is written, what happens when a reference does not resolve, and the two design-time tools — the Node I/O inspector and pinned outputs — that let you build a downstream node before the upstream one is finished.

The two reference forms

There are exactly two roots. Everything else you may have seen in other automation tools — $trigger, $env, $json, $item — does not exist here. 

# Read a named output field of a specific node
{{ $node.fetch-user.output.statusCode }}

# Read a variable from the workflow's variable store
{{ $variables.customerId }}

$node references are addressed by the node id, which is shown under the title in the property inspector — not by the node's display name. The literal .output. in the middle is required; without it the reference resolves to nothing. Node ids containing hyphens are fine.

A bare identifier inside the braces is also accepted and is treated as a variable name, so {{ customerId }} means the same thing as {{ $variables.customerId }}. The explicit form is worth preferring: it survives being read by somebody else, and it is the form the editor's own tools insert.

The root tokens are case-sensitive

$node. and $variables. are matched as exact lowercase text. Writing {{ $Node.a.output.b }} does not resolve to nothing — it fails to parse, and an expression that fails to parse throws and fails the entire run, not just the node. There is no diagnostic for it and nothing catches it, so the symptom is a run that dies at that step with a parser message rather than a node-level failure you can retry.

Reaching into nested data

Both forms share one path grammar. The head is everything up to the first . or [; after that you may chain member and index segments freely.

SegmentMeans
.nameA member of an object.
["name"] or ['name']The same, but the key may contain dots or other awkward characters.
[0]An element of an array. The index must be a non-negative whole number.
 
{{ $node.fetch-user.output.payload.user.age }}
{{ $node.fetch-user.output.payload[0].email }}
{{ $variables.config.servers[2].host }}
{{ $variables.lookup["order.id"] }}

Every part of a reference is matched exactly, including case: the node id, the output name, and each member name. A reference is read until the first delimiter, and whitespace is a delimiter — so {{ $variables.lookup["my key"] }} is cut short at the space and resolves to nothing. So is a hyphen appearing inside the path, though a hyphen in the node id itself is safe because the id is located by the surrounding .output..

Whole value or interpolated text

This distinction decides whether a field receives a real object or a piece of text, and it catches people out.

When a field's value is nothing but one expression, the result keeps its type: an object stays an object, an array stays an array, a number stays a number. When the expression is embedded in surrounding text, everything is converted to string and concatenated.

Field valueNode receives
{{ $node.a.output.payload }}The object itself.
Order {{ $node.a.output.id }} receivedA string.
 {{ $node.a.output.payload }}A string — the leading space makes it interpolation.
One stray space changes the type

A single space before or after the braces is enough to demote a whole-value expression to string interpolation. If a downstream node complains that it received text where it expected an object or a number, check the field for surrounding whitespace before looking anywhere else.

One further typing note: every JSON number arrives as a floating-point value, so 30 in a payload becomes 30.0. That is invisible most of the time but matters when a value is concatenated into text or compared against a string.

When a reference does not resolve

A syntactically valid reference that points at nothing — an unknown node, an output that node never produced, a member that is not there, an array index past the end — does not raise an error. It resolves to nothing, and how that lands depends on the shape of the field:

  • As a whole value, the parameter is null.
  • Embedded in text, it contributes an empty string, so Order {{ … }} received becomes Order  received.

This is a deliberate design — a run should not die because one optional field was absent — but it means a typo in a reference is silent. A node that suddenly logs a blank where a value should be, or an HTTP request whose body has an empty field, is usually a misspelled node id or output name, not a data problem.

References are never checked before a run

Publishing validates the graph's structure, not its expressions. In fact a value wrapped in {{ … }} is exempted from the parameter type check, because the compiler cannot know what the expression will produce. A reference to a node that does not exist publishes cleanly and fails quietly at run time. The Node I/O inspector and a manual run are the tools that catch it.

More than references

The space between the braces is a small expression language, not just a reference slot. It supports string literals in single or double quotes, numbers, true, false and null, parentheses, the arithmetic operators + - * /, the comparisons == and !=, and the logical && and ||. The + operator concatenates when either side is a string and adds otherwise. Division by zero yields zero rather than failing.

Four functions are available, and only these four — anything else is rejected outright:

FunctionReturns
now()The current UTC time as a round-trip formatted string.
uuid()A fresh identifier.
coalesce(a, b, …)The first argument that is neither null nor an empty string.
length(x)The length of the argument.
There is no escape sequence

{{ always opens a placeholder; it cannot be escaped, doubled or quoted out. A string literal inside a placeholder has no escapes either, so a quote character cannot appear inside a quoted literal. If you genuinely need the characters {{ in a value, the only reliable way is to make sure the value never contains a matching }} — a value with an opening brace pair and no closing pair is passed through untouched.

Discovering references in the editor

You rarely need to type any of the above by hand. Four affordances produce correct references for you.

Autocomplete inside a field

Typing {{ in an expression-capable field opens a list of the workflow's known references — promoted node outputs and variables — filtered by whatever you type after the braces. Arrow keys move, Enter or Tab inserts the complete {{ … }} expression, and Esc closes the list.

The Insert data reference chips

Near the top of the property inspector, a panel titled Insert data reference lists every upstream node — every ancestor, not just the immediate predecessor — grouped by node, with one chip per data field it exposes. Clicking a chip copies the full expression to the clipboard, ready to paste into any field. Control and branch ports such as true and false carry no payload and are left out.

On graphs started by an external device or an event or action trigger, a second panel offers the fields that signal carries. Those are scoped to the run rather than shared, which is why they appear per node rather than in the workflow-wide variable store.

Dragging an output chip

Each node card shows its outputs as small draggable pills. Dragging one has two useful destinations:

  • Onto another node — binds that output to the target node's primary input field, as a stored reference rather than as typed text.
  • Onto the Workflow variables panel — promotes the output to a named entry in the variable store, described in Variables. While you drag, a hint reading Drop output into the global store appears at the bottom of the canvas.

A promoted output is proposed with the name <nodeId>_<outputName>, which you can rename afterwards. Promoting the same output twice returns the existing entry rather than creating a duplicate.

The Node I/O inspector

At the bottom of the property inspector, the Input / Output section answers "what does this node actually produce?" without leaving the canvas. It loads the workflow's most recent run and shows the selected node's recorded inputs, the variables as they stood, and its outputs. A Refresh button re-reads the latest run.

Before a node has ever run there is nothing recorded, and the section says so. It then falls back to the declared outputs from the node package's manifest — each output's name, its type, and the field names it declares — so you can still see the shape of what the node will emit and write a reference against it.

Read the last run, then write the reference

The most reliable way to get a deep path right is to run the workflow once, select the producing node, and read the real recorded output. Guessing at the shape of somebody's JSON and relying on a silent miss to tell you when you are wrong is how an afternoon disappears.

Pinned outputs

Building the third node of a chain usually means running the first two over and over. A pinned output short-circuits that: the node stops executing and returns a sample you supply, so everything downstream can be built and re-run immediately.

The Pinned output control sits at the very bottom of the property inspector. Clicking Pin output opens a JSON editor and a port field; the port defaults to result. The payload must be valid JSON — invalid text is reported inline and is not stored. Clear pin removes the pin entirely.

A pin is honoured on manual runs only — the Run button in the editor and a manually started run elsewhere. Scheduled runs, inbound webhooks, pollers, device events, error workflows, agent tool calls and replays all ignore it and execute the node normally. The run journal records that the node was pinned and returned its pinned output instead of executing.

A pin is saved into the published version

Pins live on the node like any other property, so they are saved with the draft and published into the runtime version. They are not stripped. Since manual runs execute the active version, anyone pressing Run on that workflow — including on a production instance — gets your sample instead of the real step, indefinitely, until the pin is cleared.

Publishing a workflow that has pins returns a warning naming the pinned nodes: "…node(s) have pinned test output. A manual run returns the pinned sample instead of executing; automated (webhook/schedule) runs ignore pins. Clear the pins when done testing." It does not block publishing.

That warning is not currently shown in the editor

The warning is returned in the publish response, but the canvas does not display it — the status bar only reports the version number that was published. In practice that means nothing on screen tells you a pin is still active except the amber Pinned output (active) label on the node's own property panel. Clear pins deliberately when you are finished testing; do not expect to be reminded.
