Capabilities

Settings › Capabilities holds the master switches for the privileged things a node can do. They are off on a fresh instance, and a node that needs one fails with a clear message until an administrator turns it on. Each switch is instance-wide: enabling it grants the capability to every workflow on the instance, not to the one you were looking at.

What a capability is

Every node package declares a list of capability tags in its manifest — short strings naming the privileged resources it touches. The tags are an open vocabulary shared with binary and custom node packages, so a package you write declares its own. The host uses them for two purposes: to warn you before installing an imported bundle that reaches beyond ordinary data flow, and to gate execution.

Not every tag is a switch. The full vocabulary is wider than what this screen controls:

TagMeaningHow it is treated
code.execute Executes arbitrary code on the host. The highest privilege there is. Switchable
database Runs arbitrary database queries. Switchable
aiAgent Runs a language-model tool-use loop that can invoke other workflows as tools. Switchable
filesystem.read Reads local files. Own policy
filesystem.write Writes local files. Own policy
network Makes outbound network calls. Descriptive
credentials Resolves stored credentials and secrets. Descriptive

The two filesystem tags are deliberately excluded from this screen because they have something better: a per-directory policy on File access. A single on/off switch would be a worse control than granting one folder at a time, so the coarse switch was left out rather than duplicated.

The network and credentials tags are older, informal markers. They are descriptive metadata that a future permission model will build on — nothing enforces them today. Outbound network access is instead constrained by the egress policy described on Security model.

The screen

The card is headed Privileged capabilities and lists each switchable capability as a row with a name, a one-line description and an on/off checkbox. There is no save button — a toggle writes immediately, showing an ellipsis in place of the On/Off label while the write is in flight.

There are three rows, one per switchable capability, and they are the same three the engine enforces: Inline code execution, Database access and AI agent tool loop. Nothing on this screen is read-only and nothing enforced by the backend is missing from it, so a capability you cannot find here is one that is not switchable at all — look for it among the filesystem and descriptive tags in the table above.

As soon as any capability is on, an amber banner appears at the bottom of the card reminding you that every workflow on the instance can now use it and suggesting you turn it back off when you no longer need it. That banner is not a warning about something going wrong; it is a standing reminder that the instance is in a more permissive state than its default.

What each capability unlocks

Inline code execution

Tag code.execute. Off by default

This one switch governs everything that compiles and runs user-authored C#:

  • The Inline Code node, which declares code.execute as its only capability.
  • The Inline Code node's design-time Test run in the editor. Turning the capability off does not leave you a safe way to experiment — the test path is gated by the same check as the real execution, which is the correct behaviour but sometimes surprises people debugging a workflow.
  • Compiled custom node packages. A custom node in the compiled tier runs arbitrary C# in the host process and is gated by exactly the same capability. The install-time signature check governs what may be installed; this switch governs whether the operator has opted in to running compiled code at all. Custom nodes in the declarative tier are unaffected.

This is the highest-privilege switch on the screen. C# compiled at runtime in the host process can do anything the host account can do, and no capability check constrains it once it is running. The Sandbox screen is what limits the damage afterwards.

Database access

Tag database. Off by default

Unlocks the Database Query node, which opens a connection to Postgres or SQLite and runs the SQL you give it. The node's manifest declares both network and database; only the latter is gated.

The connection string is not typed into the node — it is held as an encrypted credential and referenced, then resolved at run time. That means enabling this capability does not by itself tell a workflow which database to reach; it still needs a credential that someone created. It does mean that any workflow can use any credential that exists, so the two together are the grant.

AI agent tool loop

Tag aiAgent. Off by default

Unlocks the AI Agent node, which runs a language-model tool-use loop and — this is the part that makes it privileged — can invoke other workflows as tools. A model deciding which of your workflows to run, with arguments it chose, is a materially different risk from a model producing text, which is why it is gated like code execution rather than treated as an ordinary AI node. The node also declares network.

The row's own description makes the sharpest version of the point: the task text handed to the agent and the results the tools return are untrusted input, so the allowlist should contain only workflows you would be willing to let that data invoke. The allowlist is edited on the node, but this switch is what decides whether any allowlist runs at all.

What happens to a workflow that needs a disabled capability

It fails loudly, at the node, at run time, with a message that names both the capability and where to enable it. It does not fail at design time, at publish, or at the start of the run — the check happens when that node executes.

NodeFailure message
Inline Code Inline Code is disabled: the 'code execution' capability is off. An administrator can enable it under Settings › Capabilities.
Database Query Database Query is disabled: the 'database' capability is off. An administrator can enable it under Settings › Capabilities.
AI Agent AI Agent is disabled: the 'aiAgent' capability is off. An administrator can enable it under Settings › Capabilities.
Compiled custom node Custom node '<type>' runs compiled code, which is disabled: the 'code execution' capability is off. An administrator can enable it under Settings › Capabilities.

The practical consequences are worth spelling out. The run reaches the node, fails there, and the rest of the workflow follows whatever error handling you configured — so a capability that was switched off after a workflow was published shows up as an ordinary node failure in the run inspector, not as a configuration error at the top of the screen. Anything the workflow did before that node is already done and is not rolled back.

Because the check reads the policy at execution time, turning a capability off takes effect on the very next node execution. There is no cache to wait out and nothing to restart. The same is true turning it on: a run that failed a minute ago will succeed if you re-run it after flipping the switch.

Failing closed

Every path through the policy defaults to denial rather than permission, which is worth knowing because it means a corrupted or missing setting is safe rather than dangerous:

  • No stored policy at all means the empty set — everything off.
  • A stored value that will not parse as JSON is treated as the empty set, not as an error that halts anything.
  • Only recognised switchable capabilities are persisted. An unknown tag, or one of the filesystem tags, is silently dropped on save, so stale entries cannot accumulate and cannot be smuggled in.
  • A host wired without the settings-backed policy store falls back to an implementation that reports every capability as disabled.

The policy is stored in the database as a single application setting. It has no appsettings.json counterpart, so there is no way to pre-seed it for an unattended install and no configuration key to check when you are wondering why a node is refused. This screen is the only source of truth.

The decision you are actually making

Enabling a capability is not "letting this workflow do this thing". It is "letting every workflow on this instance do this thing, now and in the future". That includes:

  • Workflows other account holders create, since there is no role model that would stop them.
  • Workflows imported from a template or bundle, including ones imported after you flipped the switch.
  • Workflows generated from a natural-language description by a language model.

Enabling code execution in particular is functionally equivalent to granting everyone who can edit a workflow the ability to run arbitrary code as the host account. That is a legitimate thing to do on a single-operator instance you run yourself; it is a poor thing to do on a shared instance whose users you would not hand a shell to.

Turn it on, do the work, turn it off

Because the policy is consulted per execution and changes need no restart, treating these switches as temporary is genuinely practical. If a scheduled workflow needs inline code once a week, there is nothing forcing you to leave the capability on for the other six days — and the standing amber banner is there precisely to remind you it is still on.

Enabling a capability also changes what a hostile import can achieve. The bundle installer will still make you acknowledge privileged nodes before installing, but the acknowledgement and the capability are independent: acknowledging an import never enables anything, and an enabled capability means an acknowledged import runs the moment it is triggered. See Security model for the import gate.
