Retention and disk space

Settings › Retention holds two cards that solve the same problem from opposite ends. Data retention bounds how large the database can grow by pruning on a schedule. Disk-space guard is the backstop underneath it: when free space runs out anyway, it disarms the runtime so nothing new starts writing. Neither needs a restart, and neither takes effect instantly.

Why this screen exists

Every run writes a journal — one entry per step — and that is what makes the run inspector able to replay a run that finished days ago. It is also the fastest-growing table in the product. A once-a-minute schedule adds roughly half a million schedule-fire rows a year on its own, before any journal entries. On a long-lived instance with no retention configured, the SQLite file grows without bound until the disk is full.

A full disk does not crash the engine — SQLite starts failing writes and the product degrades rather than falls over — but that is a bad place to arrive at. These two cards are the mechanisms for not arriving there.

Data retention

The card's description is accurate about the essential guarantee: old finished runs are deleted along with their logs, and in-flight runs are never touched. Concretely, only runs in a terminal state are eligible — completed, failed, cancelled or discarded. A run that is pending, running, suspended or waiting to retry is excluded no matter how old it is, so a long-suspended run is never deleted out from under the executor.

The two primary fields

FieldDefaultRangeEffect
Run history (days) 30 0–3650 Deletes finished runs and their logs older than this. Zero keeps everything forever.
Sweep interval (minutes) 60 1–10080 How often the cleanup runs. The first sweep is one interval after startup.

Deleting a run cascades. The database removes that run's journal entries, node states, work items, retry states and correlation tokens in the same statement, so there is no orphaned wreckage left behind and no second pass needed.

The same age window also prunes the schedule-fire log — the append-only record of every scheduler tick. It has to be pruned separately because its link to a run is nulled rather than cascaded when the run goes, which means run-history retention would otherwise never reach it. Before this was added, that table was never reclaimed at all.

Setting run history to zero shows an amber warning on the card stating that the database will grow without bound as runs accumulate. It is a legitimate choice on an instance where every run is an audit record, but it is a choice to make deliberately.

The optional caps

Under Version history & audit caps sit three more fields. All default to zero, meaning nothing here is deleted unless you opt in.

FieldDefaultRangeEffect
Max versions / workflow 0 0–100000 Keeps the newest N published versions per workflow. Zero keeps all.
Max OpenAPI versions / spec 0 0–100000 Caps the re-import history of each imported specification. Zero keeps all.
Audit log (days) 0 0–3650 Rolls over audit entries older than this. Zero keeps them forever.

The version cap is more careful than "keep the newest N" suggests, and the extra care is what makes it safe to turn on. Beyond the newest N, a version is only deleted if nothing refers to it. Three things count as a reference and protect a version permanently:

  • It is the currently active version of its workflow.
  • The append-only activation log mentions it — as an activated version, as the version something was restored from, or as the previously active version.
  • Any retained run executed it, which is what preserves replay lineage.

The practical consequence is that the cap prunes less than the number suggests, and that is correct. Setting it to five does not guarantee five versions remain; it guarantees that at least the newest five, plus everything still referenced, remain. Run-history retention interacts with it: once old runs are pruned, the versions those runs pinned become eligible on a later sweep.

The audit roll-over rewrites the tamper-evident hash chain

The audit log is a hash chain, each entry linked to the one before it, and startup verifies the chain. Deleting old entries would break that link — so after the roll-over the surviving entries are re-anchored: the chain is rebuilt so the new first entry links to genesis and verification still passes. That is what makes trimming possible at all, and it is also exactly what a tamper would look like. The card says so in a red banner when the field is non-zero. Enable this only if losing the ability to verify the surviving entries against the original chain is acceptable for your compliance needs.

The roll-over is logged as a warning, not an informational message, naming how many entries were removed and over what window. If you are auditing an instance, that log line is the record of when the chain was re-anchored.

How a sweep runs

The worker loops forever. Each cycle re-reads the sweep interval, waits, then re-reads the whole policy and sweeps. Two consequences follow from that shape:

  • The first sweep is one interval after startup. A process that starts and stops quickly never prunes anything, which is deliberate — an upgrade or a short-lived test run should not silently delete history.
  • The loop never exits when retention is disabled. With everything at zero the sweep returns immediately, but the worker keeps cycling so that turning retention on later is picked up without a restart.

When a sweep actually deletes something, the space is reclaimed rather than left at high-water mark: the write-ahead log is checkpoint-truncated, and freed pages are returned to the operating system with an incremental vacuum. The latter is a no-op unless the database was created in incremental auto-vacuum mode, which happens at first startup — so on a very old database the file may not shrink even though rows were deleted, while the freed space is still reused for future writes.

A sweep that throws is logged as an error and retried on the next interval rather than killing the worker. Retention failing is therefore quiet: the symptom is a database that keeps growing, and the evidence is in the log.

Saving the card confirms with Saved — applies on the next sweep, which is precise. If you have just set the interval to a week, the next sweep is a week away.

The disk-space guard

The second card is the hard backstop. When free space on the data volume falls below the floor, the runtime is disarmed so no new runs start — each run writes many journal rows, so pausing new runs is the fastest way to stop the write pressure. Retention only prunes on a schedule and is time-based, so nothing else in the product reacts to a disk approaching full.

FieldDefaultRangeEffect
Minimum free space (MB) 256 0–10000000 Disarms the runtime below this. Zero disables the guard entirely.
Check interval (seconds) 60 30–86400 How often free space is sampled. Values below thirty seconds are raised to thirty.

The volume watched is the one holding the data directory. Free space is read as the drive's available free space; if it cannot be determined the check logs a warning and does nothing rather than guessing.

Setting the floor to zero shows a red banner on the card warning that nothing will stop new runs as the disk approaches full and that SQLite will start failing writes, and suggesting a positive floor such as 512 MB. Take that seriously on any instance you are not watching by hand.

What happens when it trips

When free space falls below the floor and the runtime is currently armed, the guard disarms it and logs at critical severity, naming both the observed free space and the threshold, and instructing you to free up space and re-arm manually. The pill in the application header changes to Disarmed, and from then on only manual runs execute — scheduled workflows and automatic triggers stop firing.

It never re-arms on its own

When space is recovered, the guard logs a warning saying so and noting that the runtime was disarmed by the disk-space guard and can be re-armed when you are ready. It does not re-arm. Recovering disk and returning to automatic execution is a deliberate operator action, taken from the arming switch in the header — because the guard cannot know whether you have actually fixed the underlying cause or merely deleted something temporarily.

Note what this means for an unattended instance: a disk that fills at three in the morning leaves the runtime disarmed until a person notices. The critical log line is the alert, and it is worth wiring into whatever watches your logs.

Like the retention worker, the guard runs its first check one interval after startup, keeps looping even when the floor is zero so that enabling it later is picked up, and re-reads the policy on every cycle. If reading the policy fails it falls back to 256 MB and sixty seconds and logs the error. Saving the card confirms with Saved — applies on the next check.

The two free-space controls are different

It is easy to confuse this floor with the reserve on File access, and they do different jobs:

Disk-space guardFile-access reserve
WatchesThe volume holding the data directoryThe drive each write targets
Triggered byA periodic checkAn individual write, before it happens
EffectDisarms the whole runtimeDenies that one write
RecoveryManual re-armAutomatic once space exists

On an instance whose workflows write large files to the same volume as the database, configure both. The reserve stops a single workflow eating the headroom; the guard stops the accumulated journal doing it slowly.

Configuration and precedence

Both cards are seeded from configuration — the Retention__* keys and the disk-guard half of Storage__* — and both persist into the database once saved, after which the stored values override the configuration file. An instance that never opens this screen keeps behaving exactly as its appsettings.json says; one that has saved the screen once ignores that file for these values from then on.

The workers read the policy through the same store the screen writes, on every sweep and every check, which is why changes need no restart. The full key list is in the configuration reference.

A reasonable starting point

For a production instance that keeps a quarter's worth of run history and has a comfortable margin on disk: run history 90 days, sweep interval 60 minutes, version and OpenAPI caps left at zero, audit log left at zero, minimum free space 1024 MB. Then revisit the run-history figure once you know how large the database actually gets — it is far easier to shorten the window later than to reconstruct history you pruned.
